# 유닉스·리눅스 보안 기초

> 자동 생성 — 원본은 `cards/unix.js`. 직접 수정 금지.

## 리눅스·유닉스 특징 — OS Characteristics

`시스템 보안`  `다중 사용자` `다중 작업` `계층적 파일시스템` `이식성` `오픈소스`

**한줄:** 다중 사용자·다중 작업·계층적 파일시스템·이식성·오픈소스 / 보안 관점=여러 사용자·프로세스가 공유하니 권한·접근통제·격리가 필수

**정의 (특징→보안으로 연결해 기억)**

유닉스 계열 OS의 기본 특징들. 시험엔 '특징이 **아닌** 것?' 정도로 가볍게 나오지만, 진짜 핵심은 **이 특징들이 왜 보안을 필요하게 만드는지**다. 아래처럼 특징마다 '그래서 무엇이 필요한가'로 엮어 외운다.

**핵심 특징 + 보안 연결**

- **다중 사용자(Multi-user)** — 여러 사용자가 한 시스템을 공유 → 그래서 **UID/GID·파일 소유권·접근통제(rwx)**가 필수. **리눅스 보안의 출발점.**
- **다중 작업(Multi-tasking)** — 여러 프로세스 동시 실행 → **프로세스 격리·자원 통제** 필요.
- **계층적(트리) 파일시스템** — 최상위 `/`(루트)부터 아래로 가지치기. 하나의 트리.
- **이식성(Portability)** — 대부분 **C 언어**로 작성 → 다양한 하드웨어로 옮기기 쉬움.
- **오픈소스·공개** — 소스가 공개 → 다수가 검증(장점)이자 **취약점도 공개**되는 양날의 검.
- **셸(Shell)** — 명령 해석기 + 스크립트로 자동화.

**왜 시험에서 중요한가**

**다중 사용자·다중 작업**이라서, 한 사용자·한 프로세스의 침해가 **시스템 전체로 번질 수 있다**. 그래서 **최소 권한·격리·접근통제**가 리눅스 보안의 뼈대이며, 뒤에 배울 **파일 권한(rwx)·SetUID·PAM·로그**가 전부 이 특징에서 파생된다.

> **시험 한줄정리:** 리눅스 특징 = **다중 사용자·다중 작업**·계층적 파일시스템·이식성(C)·오픈소스 / 보안 관점: 여러 사용자·프로세스가 **공유** → 권한·접근통제·격리가 필수(그래서 UID/GID·rwx가 존재)

_관련 개념: uidgid · symlink_

## 리눅스 구조 (커널·셸·파일시스템) — Kernel · Shell · File System

`시스템 보안`  `커널=자원관리 핵심` `셸=명령 해석기` `사용자→셸→커널→HW` `시스템 콜` `파일시스템=/ 트리`

**한줄:** 안쪽부터 하드웨어→커널(자원관리 핵심)→셸(명령 해석기)→사용자 / 커널이 핵심, 셸은 사용자와 커널을 잇는 다리

**계층 구조 (양파처럼)**

리눅스는 안쪽부터 **하드웨어 → 커널 → 셸 → 사용자·응용**의 계층 구조. 안으로 갈수록 핵심·강력하고, 바깥일수록 사용자와 가깝다.

**각 층의 역할 (어원으로 기억)**

- **커널(Kernel, 알맹이·핵)** — OS의 **핵심**. 프로세스·메모리·파일시스템·장치(하드웨어)·네트워크를 **직접 관리**. 부팅 시 메모리에 올라와 상주.
- **셸(Shell, 껍데기)** — 사용자 명령을 받아 **해석해 커널에 전달**하는 **명령 해석기**. 커널을 감싼 껍데기라 이 이름. 스크립트로 자동화.
- **파일시스템(File System)** — 데이터를 **계층적 트리**로 관리. 최상위 `/`(루트) 하나에서 시작하며, **모든 것을 '파일'로 취급**(장치도 파일).

**함정 · 보안 연결**

사용자 프로그램은 하드웨어에 직접 못 대고 **시스템 콜**로만 커널에 요청한다. 셸은 사용자↔커널의 **다리**라, 셸 접근·셸 스크립트가 곧 **공격 표면**(웹셸·셸쇼크 등).**[시험 함정]** '**커널**=명령 해석기'(X, 그건 셸) · '**셸**=자원 관리'(X, 그건 커널)처럼 **둘의 역할을 뒤바꿔** 낸다.

> **시험 한줄정리:** 안쪽→바깥: 하드웨어→**커널**(자원관리 핵심)→**셸**(명령 해석기=커널의 껍데기)→사용자 / 파일시스템=`/`부터 트리, 모든 게 파일 / 함정: 커널↔셸 역할 바꿔치기

_관련 개념: linuxfeat · shelltypes · process_

## 셸 종류 (bash·sh·csh·ksh) — Shell Types

`시스템 보안`  `sh=본셸(원조)` `bash=리눅스 기본` `csh=C 문법` `ksh=콘셸` `로그인 셸=/etc/passwd`

**한줄:** sh(본셸 원조)→bash(리눅스 표준)·csh(C 문법)·ksh(콘셸)·zsh / 사용자 로그인 셸은 /etc/passwd 마지막 필드

**정의**

**셸(Shell)**은 사용자가 입력한 명령을 **해석해 커널에 전달**하고 그 결과를 돌려주는 **명령어 해석기(command interpreter)**다. 사용자와 운영체제(커널) 사이의 **대화 창구** — 프롬프트에 `ls`를 치면 셸이 해석 → 커널이 실행 → 결과를 화면에 표시. 명령을 모아 **셸 스크립트**로 자동화도 한다.**[왜 종류가 여럿?]** 이 명령 해석기가 여러 개 만들어졌고 문법·기능이 조금씩 다르다. 시험엔 **약자 풀네임**과 '리눅스 기본 셸이 무엇인가'가 잘 나온다.

**종류 (풀네임=곧 유래)**

- **sh** = **Bourne Shell**(본 셸) — 스티브 본이 만든 **최초의 표준** 유닉스 셸. 다른 셸의 뿌리.
- **bash** = **Bourne Again SHell** — sh를 확장·개선. **리눅스의 기본 셸**, 가장 널리 쓰임.
- **csh** = **C Shell** — **C 언어 문법** 스타일. 빌 조이 작.
- **ksh** = **Korn Shell**(콘 셸) — sh 호환 + csh 기능. 데이비드 콘 작.
- **tcsh**(csh 개선), **zsh**(강력한 기능, 요즘 macOS 기본).

**확인·설정 (실무/시험)**

현재 셸 확인 `echo $SHELL` · 사용 가능한 셸 목록 `/etc/shells` · 사용자별 **로그인 셸**은 `/etc/passwd`의 **마지막 필드**(예: `/bin/bash`).

**보안 포인트**

로그인이 필요 없는 **서비스·시스템 계정**은 로그인 셸을 `/sbin/nologin`이나 `/bin/false`로 지정해 **셸 접근을 차단**한다(계정 잠금·공격 표면 축소).

> **시험 한줄정리:** sh=원조 본셸 / **bash=리눅스 기본**(Bourne Again SHell) / csh=C 문법 / ksh=콘셸(sh+csh) / 로그인 셸=`/etc/passwd` 마지막 필드, 차단은 `nologin`

_관련 개념: linuxarch · uidgid_

## bash 환경 설정 파일 — .bash_profile · .bashrc · .bash_logout

`시스템 보안`  `로그인 시 .bash_profile` `셸마다 .bashrc` `로그아웃 .bash_logout` `전역 /etc/profile` `자동실행=지속성 표적`

**한줄:** .bash_profile=로그인 시 1회 / .bashrc=셸 열 때마다 / .bash_logout=로그아웃 시 / 자동 실행이라 백도어 지속성 표적

**정의**

사용자 홈 디렉터리(`~`)에 있는 **숨김 파일**(이름이 `.`으로 시작=닷파일). 셸이 **시작·종료할 때 자동으로 읽어** 환경(변수·alias·함수)을 설정한다.

**언제 실행되나 (핵심)**

- `~/.bash_profile` — **로그인 시 1회** 실행(login shell). 환경변수·`PATH` 설정. (없으면 `.bash_login`→`.profile` 순으로 대체)
- `~/.bashrc` — **셸을 열 때마다** 실행(새 터미널·서브셸 등 비로그인 인터랙티브). alias·함수·프롬프트. 보통 `.bash_profile`이 `.bashrc`를 불러 준다.
- `~/.bash_logout` — **로그아웃 시** 실행. 정리 작업(임시파일 삭제·`clear` 등).
- 전역: `/etc/profile`(시스템 전체 로그인), `/etc/bashrc`(전체 셸).

**시험 함정 — 로그인 vs 비로그인**

**로그인 셸**이 읽는 건 `.bash_profile`, **인터랙티브 비로그인 셸**(터미널 새 창 등)이 읽는 건 `.bashrc`. 이 둘을 뒤바꿔 내는 문제가 많다.

**보안 — 지속성(persistence) 표적**

로그인·셸 시작 때 **자동 실행**되므로, 공격자가 `.bashrc`·`.bash_profile`에 악성 명령을 심으면 **재접속·셸 실행 때마다 다시 실행**된다(백도어 **지속성** 확보). 그래서 이 파일들의 **무결성·이상 항목**이 점검 대상이다.

> **시험 한줄정리:** `.bash_profile`=**로그인 1회** / `.bashrc`=**셸 열 때마다** / `.bash_logout`=**로그아웃 시** / 전역=`/etc/profile` / 자동실행이라 백도어 **지속성** 표적

_관련 개념: shelltypes · uidgid_

## 심볼릭 링크 · 하드 링크 — Symbolic / Hard Link

`시스템 보안`  `바로가기=경로` `ln -s` `inode` `하드=같은 실데이터` `심링크 공격(TOCTOU)`

**한줄:** 심볼릭 링크=경로를 가리키는 바로가기 파일(원본 삭제 시 깨짐) / 하드 링크=같은 inode(실데이터) 별칭 / 심링크는 TOCTOU 공격 도구

**정의**

하나의 파일을 다른 이름으로 가리키게 하는 **링크**에는 두 종류가 있다. 보안에서는 **심볼릭 링크**가 자주 문제된다(경쟁 조건 공격의 도구).

**심볼릭 vs 하드 (구분해서 암기)**

- **심볼릭 링크 (소프트 링크)**: **다른 파일의 경로(path)를 적어 둔 별도의 작은 파일** = 윈도우 '바로가기'. `ln -s 원본 링크`로 생성. 원본이 지워지면 **깨진 링크(dangling)**가 됨. 다른 디스크·디렉터리도 가리킬 수 있다.

- **하드 링크**: **같은 `inode`(실제 데이터)를 가리키는 또 다른 이름**. 원본을 지워도 데이터는 남는다(연결 수가 0이 될 때 실제 삭제). **같은 파일시스템 안**에서만 가능.

**[inode란]** 파일의 **메타데이터·데이터 위치**를 담은 관리 구조. 파일 '이름'(디렉터리 항목)과 '실체(inode)'는 별개 — 하드 링크는 여러 이름이 한 inode를 공유하는 것.

**보안 — 심볼릭 링크 공격**

**경쟁 조건(TOCTOU)**에서, 권한 있는 프로그램이 파일을 **검사한 뒤 사용하기 직전**에 공격자가 그 파일을 **심볼릭 링크로 바꿔치기**해 엉뚱한 파일(예: `/etc/passwd`)을 가리키게 만든다 → 권한 상승·파일 훼손. (경쟁 조건 카드와 연결)

> **시험 한줄정리:** 심볼릭 링크=경로를 가리키는 바로가기(`ln -s`, 원본 삭제 시 깨짐) / 하드 링크=같은 `inode` 별칭(같은 FS) / 심링크는 **TOCTOU 바꿔치기** 공격 도구

_관련 개념: race · uidgid_

## UID · GID (사용자·그룹 식별) — User ID / Group ID · RUID/EUID

`시스템 보안`  `root=UID 0` `RUID(실제)·EUID(유효)` `/etc/passwd` `SetUID로 EUID 변경` `권한 판정`

**한줄:** 유닉스는 사용자=UID·그룹=GID 숫자로 식별(root=0) / 권한 판정은 EUID(유효)로 / SetUID 실행 시 EUID가 소유자로 바뀜

**정의**

유닉스·리눅스는 사용자를 이름이 아니라 **숫자 ID**로 관리한다. **UID(User ID)**=사용자 번호, **GID(Group ID)**=그룹 번호. **root=UID 0**(슈퍼유저). 계정 정보는 `/etc/passwd`, 그룹은 `/etc/group`, 비밀번호 해시는 `/etc/shadow`.

**RUID vs EUID (시험 핵심)**

한 프로세스는 여러 UID를 가진다.**[구분]** **RUID(Real UID, 실제)**=이 프로세스를 **실제로 실행한 사용자**('나 누구냐'). **EUID(Effective UID, 유효)**=**지금 권한 판정에 실제로 쓰이는** UID('지금 뭘 할 수 있냐'). 평소엔 둘이 같지만, **SetUID** 프로그램을 실행하면 **EUID가 파일 소유자(주로 root)로 바뀐다** → 일반 사용자가 잠깐 root 권한. (Saved UID도 있음)

**SetUID/SetGID와의 연결**

**SetUID(Set User ID)** 비트가 붙은 실행 파일은 실행되는 동안 **EUID = 파일 소유자**가 된다. 예: `passwd`는 일반 사용자가 실행해도 `/etc/shadow`를 고쳐야 하므로 **root 소유 SetUID**로 설정돼 있다. 이 '잠깐 올라간 권한'이 **권한 상승·경쟁 조건**의 무대다.

**방어**

**SetUID 프로그램을 최소화**(공격 표면 축소)하고, 권한이 필요한 작업이 끝나면 **EUID를 원래대로 낮춘다(drop privileges)**. 불필요한 SetUID 비트 제거, 권한은 **최소 권한 원칙**으로.

> **시험 한줄정리:** 유닉스는 사용자=**UID**·그룹=**GID** 숫자로 식별(root=0) / 권한 판정은 **EUID(유효)** / **SetUID 실행 → EUID=소유자**(잠깐 root) → 권한 상승·경쟁조건의 무대

_관련 개념: race · symlink_
