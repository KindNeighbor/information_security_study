# 유닉스·리눅스 보안 기초

> 자동 생성 — 원본은 `cards/unix.js`. 직접 수정 금지.

## 리눅스·유닉스 특징 — OS Characteristics

`시스템 보안`  `다중 사용자` `다중 작업` `계층적 파일시스템` `이식성` `오픈소스`

**한줄:** 다중 사용자·다중 작업·계층적 파일시스템·이식성·오픈소스 / 보안 관점=여러 사용자·프로세스가 공유하니 권한·접근통제·격리가 필수

**정의 (특징→보안으로 연결해 기억)**

유닉스 계열 OS의 기본 특징들. 시험엔 '특징이 **아닌** 것?' 정도로 가볍게 나오지만, 진짜 핵심은 **이 특징들이 왜 보안을 필요하게 만드는지**다. 아래처럼 특징마다 '그래서 무엇이 필요한가'로 엮어 외운다.

**핵심 특징 + 보안 연결**

- **다중 사용자(Multi-user)** — 여러 사용자가 한 시스템을 공유 → 그래서 **UID/GID·파일 소유권·접근통제(rwx)**가 필수. **리눅스 보안의 출발점.**
- **다중 작업(Multi-tasking)** — 여러 프로세스 동시 실행 → **프로세스 격리·자원 통제** 필요.
- **계층적(트리) 파일시스템** — 최상위 `/`(루트)부터 아래로 가지치기. 하나의 트리.
- **이식성(Portability)** — 대부분 **C 언어**로 작성 → 다양한 하드웨어로 옮기기 쉬움.
- **오픈소스·공개** — 소스가 공개 → 다수가 검증(장점)이자 **취약점도 공개**되는 양날의 검.
- **셸(Shell)** — 명령 해석기 + 스크립트로 자동화.

**왜 시험에서 중요한가**

**다중 사용자·다중 작업**이라서, 한 사용자·한 프로세스의 침해가 **시스템 전체로 번질 수 있다**. 그래서 **최소 권한·격리·접근통제**가 리눅스 보안의 뼈대이며, 뒤에 배울 **파일 권한(rwx)·SetUID·PAM·로그**가 전부 이 특징에서 파생된다.

> **시험 한줄정리:** 리눅스 특징 = **다중 사용자·다중 작업**·계층적 파일시스템·이식성(C)·오픈소스 / 보안 관점: 여러 사용자·프로세스가 **공유** → 권한·접근통제·격리가 필수(그래서 UID/GID·rwx가 존재)

_관련 개념: uidgid · symlink_

## 리눅스 구조 (커널·셸·파일시스템) — Kernel · Shell · File System

`시스템 보안`  `커널=자원관리 핵심` `셸=명령 해석기` `사용자→셸→커널→HW` `시스템 콜` `파일시스템=/ 트리`

**한줄:** 안쪽부터 하드웨어→커널(자원관리 핵심)→셸(명령 해석기)→사용자 / 커널이 핵심, 셸은 사용자와 커널을 잇는 다리

**계층 구조 (양파처럼)**

리눅스는 안쪽부터 **하드웨어 → 커널 → 셸 → 사용자·응용**의 계층 구조. 안으로 갈수록 핵심·강력하고, 바깥일수록 사용자와 가깝다.

**각 층의 역할 (어원으로 기억)**

- **커널(Kernel, 알맹이·핵)** — OS의 **핵심**. 프로세스·메모리·파일시스템·장치(하드웨어)·네트워크를 **직접 관리**. 부팅 시 메모리에 올라와 상주.
- **셸(Shell, 껍데기)** — 사용자 명령을 받아 **해석해 커널에 전달**하는 **명령 해석기**. 커널을 감싼 껍데기라 이 이름. 스크립트로 자동화.
- **파일시스템(File System)** — 데이터를 **계층적 트리**로 관리. 최상위 `/`(루트) 하나에서 시작하며, **모든 것을 '파일'로 취급**(장치도 파일).

**함정 · 보안 연결**

사용자 프로그램은 하드웨어에 직접 못 대고 **시스템 콜**로만 커널에 요청한다. 셸은 사용자↔커널의 **다리**라, 셸 접근·셸 스크립트가 곧 **공격 표면**(웹셸·셸쇼크 등).**[시험 함정]** '**커널**=명령 해석기'(X, 그건 셸) · '**셸**=자원 관리'(X, 그건 커널)처럼 **둘의 역할을 뒤바꿔** 낸다.

> **시험 한줄정리:** 안쪽→바깥: 하드웨어→**커널**(자원관리 핵심)→**셸**(명령 해석기=커널의 껍데기)→사용자 / 파일시스템=`/`부터 트리, 모든 게 파일 / 함정: 커널↔셸 역할 바꿔치기

_관련 개념: linuxfeat · shelltypes · process_

## 리눅스 파일시스템 구조 — Linux File System (FHS)

`시스템 보안`  `/ 루트부터 트리` `FHS 표준` `/etc·/var·/tmp·/bin` `파일 종류(ls -l 첫 문자)` `ext4·저널링`

**한줄:** 최상위 /(루트)부터 하나의 트리(FHS) / 드라이브 문자 없이 마운트 / 주요 디렉터리 용도(/etc 설정·/var 로그·/tmp 임시) / 모든 게 파일

**정의**

리눅스는 최상위 `/`(루트) 하나에서 시작하는 **계층적 트리**다. 표준 배치를 **FHS(Filesystem Hierarchy Standard)**라 한다. 윈도우의 `C:`·`D:` 같은 **드라이브 문자가 없고**, 디스크·장치는 트리의 한 지점에 **마운트**해 붙인다.

**주요 디렉터리 (보안 핵심 굵게)**

- `/bin`·`/sbin` — 필수 명령(바이너리), `sbin`=관리자용
- **`/etc`** — **환경설정 파일**(`passwd`·`shadow`·`fstab` 등). 보안의 핵심
- `/home` 일반 사용자 홈 · `/root` root의 홈
- **`/var`** 가변 데이터, 특히 **`/var/log`(로그)**
- **`/tmp`** 임시파일, **누구나 쓰기 가능**(스티키 비트) → 경쟁조건·심링크 공격 표적
- `/dev` 장치파일 · `/proc` 프로세스·커널 정보(가상) · `/usr` 응용 · `/boot` 부팅 커널 · `/lib` 라이브러리

**파일 종류 (ls -l 첫 문자)**

리눅스는 **모든 것을 파일로** 취급한다. `ls -l` 맨 앞 한 글자로 구분: `-` 일반파일 · `d` 디렉터리 · `l` 심볼릭 링크 · `b` 블록장치 · `c` 문자장치 · `p` 파이프 · `s` 소켓.

**파일시스템 종류**

**ext2 → ext3 → ext4**(리눅스 표준), `xfs` 등. **ext3부터 저널링(journaling)**: 변경 내용을 먼저 기록해 **비정상 종료 시 빠른 복구·무결성**을 보장.

**보안 포인트**

`/etc`(설정)·`/var/log`(로그)·`/tmp`(공용 쓰기)가 보안 관점의 급소. 로그 **위·변조 방지**, `/tmp` **스티키 비트** 유지, 중요 영역은 별도 파티션으로 **분리 마운트**(`noexec`·`nosuid` 옵션).

> **시험 한줄정리:** 리눅스 FS = `/`부터 하나의 트리(**FHS**), 드라이브 문자 없이 **마운트** / 급소 디렉터리 `/etc`설정·`/var/log`로그·`/tmp`공용쓰기 / 파일종류 `ls -l` 첫 문자(`d`·`l`·`-`) / **ext4·저널링**

_관련 개념: linuxarch · symlink · race_

## 파일시스템 내부 구조 (부트·슈퍼·아이노드·데이터) — Boot / Super / Inode / Data Block

`시스템 보안`  `부트 블록` `슈퍼 블록` `아이노드 블록` `데이터 블록` `이름은 디렉터리에`

**한줄:** 유닉스 FS = 부트+슈퍼+아이노드+데이터 블록 / 아이노드=파일 메타데이터(이름은 없음, 디렉터리가 이름↔아이노드 매핑)

**정의**

하나의 유닉스 파일시스템(파티션)은 **4가지 블록 영역**으로 구성된다. 순서: **부트 → 슈퍼 → 아이노드 리스트 → 데이터**.

**4개 블록 (역할)**

- **부트 블록(Boot Block)** — 파일시스템 맨 앞. **부팅에 필요한 부트스트랩 코드** 영역.
- **슈퍼 블록(Super Block)** — **파일시스템 전체 정보**(크기, 총 블록·아이노드 수, 빈 블록·아이노드 목록, 마운트 상태). **손상되면 치명적**이라 백업본을 둔다.
- **아이노드 블록/리스트(Inode List)** — 파일마다 하나씩 **아이노드(inode)**. 파일의 **메타데이터**를 담는다.
- **데이터 블록(Data Block)** — **실제 파일 내용** 저장.

**아이노드 — 핵심 함정**

아이노드는 파일의 **주민등록** 같은 것. 담기는 것: 파일 **종류·권한(rwx)·소유자(UID/GID)·크기·시간(atime·mtime·ctime)·링크 수·데이터 블록 위치 포인터**.**[담기지 않는 것 = 파일 이름]** **이름↔아이노드 번호 매핑은 '디렉터리'**가 갖는다(디렉터리 = 이름·아이노드번호 목록). 그래서 **하드 링크**는 이름 여러 개가 한 아이노드를 공유하는 것. '아이노드에 파일 이름이 있다'는 **틀린 보기**로 자주 나온다.

**보안·복구 포인트**

슈퍼 블록·아이노드 손상은 파일시스템 붕괴로 이어져 `fsck`(File System Check)로 검사·복구한다. 파일을 삭제해도 아이노드·데이터 블록이 **즉시 덮이지 않아** 포렌식으로 **복구가 가능**한 경우가 있다(디스크 완전 삭제 필요).

> **시험 한줄정리:** 유닉스 FS 4영역 = **부트**(부팅코드)·**슈퍼**(FS 전체정보)·**아이노드**(파일 메타데이터, **이름 없음**)·**데이터**(실제 내용) / 이름↔아이노드는 **디렉터리**가 매핑 / 손상 복구=`fsck`

_관련 개념: linuxfs · symlink · uidgid_

## 디스크 파티션 — Disk Partition

`시스템 보안`  `물리 디스크 논리 분할` `마운트·/etc/fstab` `swap=가상메모리` `MBR vs GPT` `/dev/sda1`

**한줄:** 하나의 물리 디스크를 논리 영역으로 분할 / 마운트로 트리에 연결(/etc/fstab) / 중요 영역 분리로 보안·장애 격리

**정의**

하나의 물리 디스크를 **여러 논리 영역으로 나눈 것**. 각 파티션에 파일시스템을 만들어 **마운트**해 쓴다. 장치명은 `/dev/sda`(첫 디스크)·`/dev/sda1`(그 첫 파티션), `sdb`…

**왜 나누나 (보안·관리)**

- **장애 격리** — `/var`(로그) 폭주·`/home` 과다 사용이 나도 **루트(`/`) 시스템은 보호**.
- **보안 강화** — 분리 파티션에 **`nosuid`·`noexec`·`nodev`** 마운트 옵션 → SetUID·실행 차단.
- **백업·복구**가 쉽고 손상 범위가 좁아진다.

**주요 파티션 · swap**

`/`(루트, 필수) · `/boot`(부팅 커널) · `/home` · `/var` · `/tmp` · **`swap`(스왑)**=**가상 메모리**(물리 메모리가 부족할 때 디스크를 메모리처럼 사용).

**파티션 테이블 — MBR vs GPT**

- **MBR (구방식)**: 디스크 첫 섹터에 부트코드+파티션 테이블. 최대 **2TB**, **주 파티션 4개** 제한.

- **GPT (신방식)**: **대용량·많은 파티션** 지원, **UEFI**와 함께 사용. 요즘 표준.

**마운트 · /etc/fstab**

파티션을 디렉터리에 연결하는 것이 **마운트**(`mount` 명령). 부팅 시 **자동 마운트** 설정은 `/etc/fstab`에 적는다(마운트 옵션도 여기서).

> **시험 한줄정리:** 파티션 = 물리 디스크를 **논리 분할**(`/dev/sda1`) / **마운트**로 트리에 연결(`/etc/fstab`) / **swap**=가상메모리 / **MBR**(2TB·4개) vs **GPT**(대용량) / 중요영역 분리+`nosuid·noexec`로 보안

_관련 개념: linuxfs · fsinternal_

## 파일시스템 관리 (생성·검사·마운트) — mkfs · fsck · mount

`시스템 보안`  `mkfs=생성(포맷)` `fsck=무결성 검사·복구` `mount/umount` `언마운트 후 fsck` `/etc/fstab 자동`

**한줄:** 파티션 생애주기: mkfs로 생성(포맷) → mount로 연결 → fsck로 검사·복구 / fsck는 마운트 해제 후 실행

**흐름으로 기억**

파티션을 나눈 뒤 **①파일시스템 생성(`mkfs`) → ②마운트(`mount`)해서 사용 → ③문제 생기면 검사·복구(`fsck`)**. 세 명령이 한 세트다.

**① 생성 — mkfs**

**`mkfs`(Make File System)** — 파티션에 파일시스템을 **만든다(포맷)**. 이때 **슈퍼 블록·아이노드 리스트·데이터 블록** 구조가 잡힌다. 예: `mkfs -t ext4 /dev/sdb1` 또는 `mkfs.ext4 /dev/sdb1`.
**주의:** 기존 데이터가 **지워진다**.

**② 마운트 — mount · umount**

**`mount`**로 파일시스템을 디렉터리(마운트 포인트)에 **연결**, **`umount`**로 해제. 예: `mount /dev/sdb1 /data`. 부팅 시 **자동 마운트**는 `/etc/fstab`에 등록.**[보안 옵션]** `nosuid`(SetUID 무시)·`noexec`(실행 금지)·`nodev`(장치파일 무시)·`ro`(읽기 전용) — `/tmp`·`/home` 등에 적용해 공격 표면을 줄인다.

**③ 무결성 검사 — fsck (함정 주의)**

**`fsck`(File System Check)** — 슈퍼 블록·아이노드·연결 상태 등 **파일시스템 구조의 이상을 검사·복구**한다. 비정상 종료·전원 장애 후 사용.**[시험 함정]** 반드시 **마운트 해제(umount) 상태**에서 실행해야 한다 — 마운트된 채로 돌리면 **오히려 손상**될 수 있다. 복구된 소유자 불명 파일은 **`lost+found`** 디렉터리에 들어간다.

**헷갈리지 말 것 — 두 가지 '무결성'**

**`fsck`**=**파일시스템 구조**의 무결성(디스크가 깨졌나). **Tripwire** 같은 **무결성 점검 도구**=**파일 내용 변조** 여부(해시 비교로 침입자가 파일을 바꿨나). 이름은 비슷하지만 **목적이 다르다.**

> **시험 한줄정리:** **`mkfs`** 생성(포맷) → **`mount`** 연결(`/etc/fstab`, 옵션 `nosuid·noexec`) → **`fsck`** 구조 검사·복구(**반드시 언마운트 후**, 복구본은 `lost+found`) / fsck≠Tripwire(파일 변조 점검)

_관련 개념: partition · fsinternal · linuxfs_

## 파일시스템 종류 — ext2/3/4 · XFS · NFS · procfs

`시스템 보안`  `ext2=저널링 없음` `ext3부터 저널링` `ext4=리눅스 표준` `XFS=RHEL7+ 기본` `NFS=네트워크`

**한줄:** 리눅스 로컬=ext2→ext3(저널링)→ext4·XFS / 네트워크=NFS·CIFS / 가상=proc·tmpfs / 타 OS=FAT·NTFS

**정리하는 법 — 3그룹**

종류가 많아 보이지만 **①로컬(디스크) ②네트워크 ③가상(메모리)** 세 갈래로 묶으면 간단하다. 시험은 주로 **①의 계보(저널링 여부)**를 묻는다.

**① 로컬 — ext 계보 (핵심)**

- **ext2** — **저널링 없음**. 비정상 종료 시 `fsck` 전체 검사로 **복구가 느림**.

- **ext3** — **저널링 도입**. 빠른 복구·무결성.

- **ext4** — **리눅스 표준**. 대용량·성능 개선(extent 방식).

**[저널링(journaling)이란]** 변경 내용을 **먼저 저널(로그)에 기록**한 뒤 실제 반영 → 정전·비정상 종료 때 저널만 보고 **빠르게 복구**. **ext2만 저널링이 없다**(시험 단골).

**① 로컬 — 그 외**

- **XFS** — 대용량·고성능 저널링. **RHEL/CentOS 7 이후 기본**.
- **Btrfs** — 스냅샷·체크섬 등 최신 기능.
- **JFS**(IBM)·**ReiserFS** — 저널링 계열(구형).
- **swap** — 파일시스템은 아니지만 **가상 메모리**용 전용 영역.

**② 네트워크 · ③ 가상 · 타 OS**

- **네트워크**: **NFS**(Network File System, 유닉스 표준 원격 공유) · **CIFS/SMB**(윈도우 공유 마운트).
- **가상(메모리)**: **`/proc`**(procfs — 프로세스·커널 정보) · `sysfs` · **`tmpfs`**(메모리에 올리는 임시 저장, 재부팅 시 사라짐).
- **타 OS**: **FAT/FAT32·exFAT**(호환성 좋음, 권한 없음) · **NTFS**(윈도우) · **ISO9660**(CD/DVD).

**보안 포인트**

**FAT 계열은 파일 권한·소유자 개념이 없어** 보안이 약하다(USB 등). **NFS**는 잘못 설정하면(`/etc/exports`에 `no_root_squash`·전체 공개) **원격에서 파일 접근·권한 상승**으로 이어진다. 확인은 `df -T`·`mount`·`/etc/fstab`.

> **시험 한줄정리:** **ext2(저널링 X) → ext3(저널링 O) → ext4(표준)**, **XFS**(RHEL7+ 기본) / 네트워크 **NFS**·CIFS / 가상 `proc`·`tmpfs` / 타OS FAT(권한 없음·취약)·NTFS

_관련 개념: linuxfs · fsadmin · fsinternal_

## 리눅스 부팅 순서 · 부트로더 — Boot Sequence · GRUB / LILO

`시스템 보안`  `BIOS→MBR→부트로더→커널→init` `GRUB·LILO` `MBR=부트 마스터` `싱글유저 모드 위험` `GRUB 패스워드`

**한줄:** 전원→BIOS/UEFI→MBR의 부트로더(GRUB)→커널 로드→init/systemd→런레벨 서비스 / 부트로더는 물리 접근 시 root 탈취 통로

**부팅 순서 (외울 흐름)**

- **1 BIOS/UEFI** — 전원 ON → 하드웨어 점검(POST) → 부팅 장치 선택.

- **2 MBR** — 디스크 **첫 섹터**의 부트 코드 실행 = **부트 마스터** 영역.

- **3 부트로더** — **GRUB**이 커널을 골라 메모리에 **적재**.

- **4 커널** — 커널 초기화·장치 인식, 루트 파일시스템 마운트.

- **5 init/systemd** — **최초 프로세스(PID 1)**. 런레벨·서비스 실행 → 로그인 화면.

**부트로더 — GRUB vs LILO**

**부트로더**는 커널을 찾아 메모리에 올려 실행시키는 프로그램.
- **GRUB (GRand Unified Bootloader)**: **현재 표준**. 부팅 시 **메뉴로 커널 선택**, 설정 변경이 유연. 설정 `/boot/grub/grub.conf`(GRUB2는 `grub.cfg`).

- **LILO (LInux LOader)**: 구형. 설정을 바꾸면 **다시 설치해야** 반영됨(`/etc/lilo.conf`).

**보안 — 물리 접근 시 root 탈취**

부팅 메뉴에서 **싱글 유저 모드(런레벨 1)**로 들어가면 **패스워드 없이 root 셸**을 얻을 수 있다 → **물리적 접근만으로 시스템 장악**. 부트로더 설정을 고쳐 커널 옵션을 바꾸는 것도 가능.

**방어**

**GRUB 패스워드 설정**(부팅 메뉴·편집 잠금), **BIOS/UEFI 패스워드**와 **부팅 순서 고정**(USB·CD 부팅 차단), 서버실 **물리적 접근 통제**. 이 셋이 세트.

> **시험 한줄정리:** 부팅 = **BIOS/UEFI → MBR → 부트로더(GRUB) → 커널 → init/systemd(PID 1)** / GRUB=표준(메뉴 선택) vs LILO=구형(재설치 필요) / **싱글유저 모드로 root 탈취** → GRUB·BIOS 패스워드로 방어

_관련 개념: partition · runlevel · linuxarch_

## 런레벨 — Run Level · systemd target

`시스템 보안`  `0=종료 6=재부팅` `1=싱글유저` `3=텍스트 5=GUI` `/etc/inittab` `systemd target`

**한줄:** 시스템 동작 상태(0~6): 0종료·1싱글유저·3텍스트·5GUI·6재부팅 / 요즘은 systemd target으로 대체

**정의**

리눅스가 어떤 **동작 상태(모드)**로 실행될지 나타내는 번호. **init**이 런레벨에 맞는 서비스들을 시작한다. 예전 기본 설정은 `/etc/inittab`.

**런레벨 0~6 (시험 단골)**

- **0** — 시스템 **종료(halt)**
- **1** — **싱글 유저 모드**(단일 사용자, 관리·복구용. **패스워드 없이 root** → 보안 위험)
- **2** — 다중 사용자(**NFS 등 네트워크 서비스 제외**)
- **3** — **다중 사용자 + 네트워크**, **텍스트(CLI)** 모드 ← 서버 기본
- **4** — **사용하지 않음**(예약)
- **5** — 다중 사용자 + **X 윈도우(GUI)**
- **6** — **재부팅(reboot)**
**[함정]** **0(종료)과 6(재부팅)**을 기본 런레벨로 설정하면 **부팅이 끝나자마자 꺼지거나 무한 재부팅**. 4는 미사용.

**명령 · systemd 시대**

확인 `runlevel`·`who -r` / 변경 `init 3`·`telinit 3`.
요즘 배포판은 **systemd**가 init을 대체해 런레벨 대신 **target**을 쓴다: `poweroff`(0)·`rescue`(1)·`multi-user`(3)·`graphical`(5)·`reboot`(6). 기본값 확인·변경은 `systemctl get-default`·`set-default`.

**보안 포인트**

서버는 불필요한 GUI를 빼고 **런레벨 3(텍스트)**로 운영해 **공격 표면을 줄인다**. **싱글 유저 모드(1)**는 물리 접근자에게 root를 내주므로 **GRUB 패스워드**로 막는다.

> **시험 한줄정리:** 런레벨 **0=종료·1=싱글유저(root 위험)·2=NFS없는 다중·3=텍스트(서버)·4=미사용·5=GUI·6=재부팅** / systemd에선 `multi-user·graphical` target / 서버는 3으로 최소화

_관련 개념: boot · linuxarch_

## 셸 종류 (bash·sh·csh·ksh) — Shell Types

`시스템 보안`  `sh=본셸(원조)` `bash=리눅스 기본` `csh=C 문법` `ksh=콘셸` `로그인 셸=/etc/passwd`

**한줄:** sh(본셸 원조)→bash(리눅스 표준)·csh(C 문법)·ksh(콘셸)·zsh / 사용자 로그인 셸은 /etc/passwd 마지막 필드

**정의**

**셸(Shell)**은 사용자가 입력한 명령을 **해석해 커널에 전달**하고 그 결과를 돌려주는 **명령어 해석기(command interpreter)**다. 사용자와 운영체제(커널) 사이의 **대화 창구** — 프롬프트에 `ls`를 치면 셸이 해석 → 커널이 실행 → 결과를 화면에 표시. 명령을 모아 **셸 스크립트**로 자동화도 한다.**[왜 종류가 여럿?]** 이 명령 해석기가 여러 개 만들어졌고 문법·기능이 조금씩 다르다. 시험엔 **약자 풀네임**과 '리눅스 기본 셸이 무엇인가'가 잘 나온다.

**종류 (풀네임=곧 유래)**

- **sh** = **Bourne Shell**(본 셸) — 스티브 본이 만든 **최초의 표준** 유닉스 셸. 다른 셸의 뿌리.
- **bash** = **Bourne Again SHell** — sh를 확장·개선. **리눅스의 기본 셸**, 가장 널리 쓰임.
- **csh** = **C Shell** — **C 언어 문법** 스타일. 빌 조이 작.
- **ksh** = **Korn Shell**(콘 셸) — sh 호환 + csh 기능. 데이비드 콘 작.
- **tcsh**(csh 개선), **zsh**(강력한 기능, 요즘 macOS 기본).

**확인·설정 (실무/시험)**

현재 셸 확인 `echo $SHELL` · 사용 가능한 셸 목록 `/etc/shells` · 사용자별 **로그인 셸**은 `/etc/passwd`의 **마지막 필드**(예: `/bin/bash`).

**보안 포인트**

로그인이 필요 없는 **서비스·시스템 계정**은 로그인 셸을 `/sbin/nologin`이나 `/bin/false`로 지정해 **셸 접근을 차단**한다(계정 잠금·공격 표면 축소).

> **시험 한줄정리:** sh=원조 본셸 / **bash=리눅스 기본**(Bourne Again SHell) / csh=C 문법 / ksh=콘셸(sh+csh) / 로그인 셸=`/etc/passwd` 마지막 필드, 차단은 `nologin`

_관련 개념: linuxarch · uidgid_

## bash 환경 설정 파일 — .bash_profile · .bashrc · .bash_logout

`시스템 보안`  `로그인 시 .bash_profile` `셸마다 .bashrc` `로그아웃 .bash_logout` `전역 /etc/profile` `자동실행=지속성 표적`

**한줄:** .bash_profile=로그인 시 1회 / .bashrc=셸 열 때마다 / .bash_logout=로그아웃 시 / 자동 실행이라 백도어 지속성 표적

**정의**

사용자 홈 디렉터리(`~`)에 있는 **숨김 파일**(이름이 `.`으로 시작=닷파일). 셸이 **시작·종료할 때 자동으로 읽어** 환경(변수·alias·함수)을 설정한다.

**언제 실행되나 (핵심)**

- `~/.bash_profile` — **로그인 시 1회** 실행(login shell). 환경변수·`PATH` 설정. (없으면 `.bash_login`→`.profile` 순으로 대체)
- `~/.bashrc` — **셸을 열 때마다** 실행(새 터미널·서브셸 등 비로그인 인터랙티브). alias·함수·프롬프트. 보통 `.bash_profile`이 `.bashrc`를 불러 준다.
- `~/.bash_logout` — **로그아웃 시** 실행. 정리 작업(임시파일 삭제·`clear` 등).
- 전역: `/etc/profile`(시스템 전체 로그인), `/etc/bashrc`(전체 셸).

**시험 함정 — 로그인 vs 비로그인**

**로그인 셸**이 읽는 건 `.bash_profile`, **인터랙티브 비로그인 셸**(터미널 새 창 등)이 읽는 건 `.bashrc`. 이 둘을 뒤바꿔 내는 문제가 많다.

**보안 — 지속성(persistence) 표적**

로그인·셸 시작 때 **자동 실행**되므로, 공격자가 `.bashrc`·`.bash_profile`에 악성 명령을 심으면 **재접속·셸 실행 때마다 다시 실행**된다(백도어 **지속성** 확보). 그래서 이 파일들의 **무결성·이상 항목**이 점검 대상이다.

> **시험 한줄정리:** `.bash_profile`=**로그인 1회** / `.bashrc`=**셸 열 때마다** / `.bash_logout`=**로그아웃 시** / 전역=`/etc/profile` / 자동실행이라 백도어 **지속성** 표적

_관련 개념: shelltypes · uidgid_

## 셸 환경 변수 — Shell Environment Variables

`시스템 보안`  `환경변수 vs 셸변수` `PATH·HOME·SHELL` `export로 승격` `env·printenv·set` `PATH 조작 공격`

**한줄:** 셸·프로그램이 참조하는 설정값 / 환경변수=자식 프로세스로 상속(export) vs 셸변수=현재 셸만 / PATH 조작은 권한상승 공격

**정의**

셸과 프로그램이 동작에 참조하는 **이름=값** 형태의 설정값. `$이름`으로 참조한다(예: `echo $HOME`). 로그인·셸 시작 시 `.bash_profile`·`.bashrc`에서 설정된다.

**환경 변수 vs 셸 변수 (핵심 구분)**

- **셸 변수 (지역)**: `이름=값`으로 지정. **현재 셸에서만** 유효, **자식 프로세스엔 상속 안 됨.**

- **환경 변수 (전역)**: `export 이름`으로 **승격**하면 **자식 프로세스에도 상속**. 시스템 전반 동작에 영향.

**주요 변수 · 조회 명령**

- **PATH** — 실행 파일을 찾는 **검색 경로** 목록
- **HOME** 홈 디렉터리 · **SHELL** 로그인 셸 · **USER/LOGNAME** 사용자명 · **PWD** 현재 경로 · **LANG** 언어 · **PS1** 프롬프트 모양
조회: `env`·`printenv`(환경변수 목록) · `set`(셸변수+환경변수) · `echo $PATH`(값) · `export`(승격) · `unset`(삭제).

**보안 — PATH 조작 공격**

**PATH**에 현재 디렉터리(`.`)나 쓰기 가능한 경로가 **앞쪽**에 있으면, 공격자가 정상 명령 이름(예: `ls`)의 **악성 파일**을 심어 그게 대신 실행되게 만든다. **SetUID 프로그램**과 결합하면 **권한 상승**.**[방어]** PATH에 `.`을 넣지 말고, 중요한 명령은 **절대 경로**로 실행. (로더 변수 `LD_PRELOAD`·`LD_LIBRARY_PATH` 조작으로 악성 라이브러리를 주입하는 공격도 같은 맥락)

> **시험 한줄정리:** **환경변수**(`export`→자식 상속) vs **셸변수**(현재 셸만) / 주요=`PATH·HOME·SHELL` / 조회 `env·printenv·set` / **PATH에 `.` 넣으면 권한상승 공격**(절대경로·`.` 제거로 방어)

_관련 개념: bashfiles · shelltypes · uidgid_

## 셸쇼크 — Shellshock (CVE-2014-6271, Bashdoor)

`시스템 보안`  `bash 취약점` `환경변수로 명령 주입` `CGI 원격 실행(RCE)` `2014년 발견` `패치로 방어`

**한줄:** bash가 환경변수 속 함수 정의 뒤에 붙은 추가 명령까지 실행하는 취약점 / CGI 웹서버로 원격 명령 실행 / 패치로 방어

**정의**

2014년 발견된 **bash**의 치명적 취약점(별명 Bashdoor). bash가 **환경변수에 담긴 함수 정의**를 불러올 때, 함수 뒤에 붙은 **추가 명령까지 실행**해버린다 → 환경변수만 조작하면 **임의 명령 실행**. 20여 년간 잠복해 있었다.

**원리 · 테스트 페이로드**

환경변수 값이 `() { :;}; 악성명령` 형태면, bash가 앞부분을 함수로 해석하다 **뒤의 악성명령을 실행**한다.**[취약 여부 테스트]** `env x='() { :;}; echo vulnerable' bash -c "echo test"` → **vulnerable**이 출력되면 취약한 bash.

**왜 위험 — CGI 원격 실행**

HTTP 요청 헤더(User-Agent 등)가 **환경변수로 전달**되는 **CGI 웹서버**(Apache `mod_cgi`)에서, 원격 공격자가 헤더에 페이로드를 넣어 **서버에서 원격 명령 실행(RCE)**이 가능하다. DHCP 클라이언트·SSH ForceCommand 등도 벡터. **인증 없이 원격**이라 파급력이 컸다.

**방어**

근본 대책은 **bash를 최신으로 패치·업데이트**. WAF로 페이로드 차단은 임시방편이고, 불필요한 **CGI 비활성화**·서버 최소화가 함께 필요.

> **시험 한줄정리:** 셸쇼크 = bash가 **환경변수 속 함수 정의 뒤 추가 명령까지 실행**(2014, CVE-2014-6271) / **CGI 웹서버로 원격 명령 실행(RCE)** / 방어=**bash 패치**

_관련 개념: shellenv · shelltypes · bashfiles_

## 심볼릭 링크 · 하드 링크 — Symbolic / Hard Link

`시스템 보안`  `바로가기=경로` `ln -s` `inode` `하드=같은 실데이터` `심링크 공격(TOCTOU)`

**한줄:** 심볼릭 링크=경로를 가리키는 바로가기 파일(원본 삭제 시 깨짐) / 하드 링크=같은 inode(실데이터) 별칭 / 심링크는 TOCTOU 공격 도구

**정의**

하나의 파일을 다른 이름으로 가리키게 하는 **링크**에는 두 종류가 있다. 보안에서는 **심볼릭 링크**가 자주 문제된다(경쟁 조건 공격의 도구).

**심볼릭 vs 하드 (구분해서 암기)**

- **심볼릭 링크 (소프트 링크)**: **다른 파일의 경로(path)를 적어 둔 별도의 작은 파일** = 윈도우 '바로가기'. `ln -s 원본 링크`로 생성. 원본이 지워지면 **깨진 링크(dangling)**가 됨. 다른 디스크·디렉터리도 가리킬 수 있다.

- **하드 링크**: **같은 `inode`(실제 데이터)를 가리키는 또 다른 이름**. 원본을 지워도 데이터는 남는다(연결 수가 0이 될 때 실제 삭제). **같은 파일시스템 안**에서만 가능.

**[inode란]** 파일의 **메타데이터·데이터 위치**를 담은 관리 구조. 파일 '이름'(디렉터리 항목)과 '실체(inode)'는 별개 — 하드 링크는 여러 이름이 한 inode를 공유하는 것.

**보안 — 심볼릭 링크 공격**

**경쟁 조건(TOCTOU)**에서, 권한 있는 프로그램이 파일을 **검사한 뒤 사용하기 직전**에 공격자가 그 파일을 **심볼릭 링크로 바꿔치기**해 엉뚱한 파일(예: `/etc/passwd`)을 가리키게 만든다 → 권한 상승·파일 훼손. (경쟁 조건 카드와 연결)

> **시험 한줄정리:** 심볼릭 링크=경로를 가리키는 바로가기(`ln -s`, 원본 삭제 시 깨짐) / 하드 링크=같은 `inode` 별칭(같은 FS) / 심링크는 **TOCTOU 바꿔치기** 공격 도구

_관련 개념: race · uidgid_

## UID · GID (사용자·그룹 식별) — User ID / Group ID · RUID/EUID

`시스템 보안`  `root=UID 0` `RUID(실제)·EUID(유효)` `/etc/passwd` `SetUID로 EUID 변경` `권한 판정`

**한줄:** 유닉스는 사용자=UID·그룹=GID 숫자로 식별(root=0) / 권한 판정은 EUID(유효)로 / SetUID 실행 시 EUID가 소유자로 바뀜

**정의**

유닉스·리눅스는 사용자를 이름이 아니라 **숫자 ID**로 관리한다. **UID(User ID)**=사용자 번호, **GID(Group ID)**=그룹 번호. **root=UID 0**(슈퍼유저). 계정 정보는 `/etc/passwd`, 그룹은 `/etc/group`, 비밀번호 해시는 `/etc/shadow`.

**RUID vs EUID (시험 핵심)**

한 프로세스는 **신분증을 2개** 갖고 다닌다 — **RUID=신분, EUID=권한**.
- **RUID (Real UID, 실제)**: 이 프로세스를 **실제로 실행한 사용자**. '나 누구냐'.
🪪 **주민등록증** — 안 바뀐다.

- **EUID (Effective UID, 유효)**: **지금 권한 판정에 실제로 쓰이는** UID. '지금 뭘 할 수 있냐'.
🎫 **지금 찬 출입증** — 바뀔 수 있다.

**[왜 '유효(Effective)'인가]** 커널이 “이 파일 열게 해줄까?”를 판단할 때 **실제로 들여다보는 값이 EUID**라서 — **효력을 발휘하는** ID라는 뜻이다. 평소엔 RUID=EUID지만, **SetUID** 프로그램을 실행하면 **EUID만** 소유자(주로 root)로 바뀐다.
**user1(1000)이 `passwd` 실행할 때**
- 실행 전 — RUID 1000 / EUID 1000 → shadow 못 건드림
- **실행 중 — RUID 1000 / EUID 0(root)** → **shadow 수정 가능**
- 종료 후 — RUID 1000 / EUID 1000 → 원래대로
**RUID가 1000으로 남아 있는 게 핵심** — 프로그램이 '권한은 root지만 실행자는 user1'임을 알아서 **user1의 비밀번호만** 바꿔준다. 확인은 `id -u`(EUID)·`id -ru`(RUID). ※ **Saved UID**는 권한을 잠깐 내렸다 되돌리려고 원래 EUID를 **보관**해두는 자리.

**SetUID/SetGID와의 연결**

**SetUID(Set User ID)** 비트가 붙은 실행 파일은 실행되는 동안 **EUID = 파일 소유자**가 된다. 예: `passwd`는 일반 사용자가 실행해도 `/etc/shadow`를 고쳐야 하므로 **root 소유 SetUID**로 설정돼 있다. 이 '잠깐 올라간 권한'이 **권한 상승·경쟁 조건**의 무대다.

**방어**

**SetUID 프로그램을 최소화**(공격 표면 축소)하고, 권한이 필요한 작업이 끝나면 **EUID를 원래대로 낮춘다(drop privileges)**. 불필요한 SetUID 비트 제거, 권한은 **최소 권한 원칙**으로.

> **시험 한줄정리:** 유닉스는 사용자=**UID**·그룹=**GID** 숫자로 식별(root=0) / 권한 판정은 **EUID(유효)** / **SetUID 실행 → EUID=소유자**(잠깐 root) → 권한 상승·경쟁조건의 무대

_관련 개념: race · symlink_

## 파일 권한 (rwx · chmod · umask) — File Permission

`시스템 보안`  `r4·w2·x1` `소유자/그룹/기타` `chmod 755` `umask=뺄셈` `디렉터리 x=진입`

**한줄:** 권한 rwx(읽기4·쓰기2·실행1)를 소유자/그룹/기타 3자리로 / chmod로 변경 / umask는 기본권한에서 빼는 값(파일666·디렉터리777 기준)

**구조 — ls -l 읽는 법**

`-rwxr-xr-x` → 맨 앞 **1글자=파일 종류**(`-`일반, `d`디렉터리), 그다음 **3자리씩 3묶음**.
- **u**(user/소유자) **rwx** · **g**(group/그룹) **r-x** · **o**(other/기타) **r-x**
- 숫자 값: **r=4(read) · w=2(write) · x=1(execute)** → 더해서 표기. `rwx`=7, `r-x`=5, `rw-`=6

**chmod — 권한 변경 (두 방식)**

**`chmod`(change mode)**
- **8진수(숫자) 방식**: `chmod 755 file` → `rwxr-xr-x`. `644`=`rw-r--r--`(일반 파일 표준), `600`=소유자만.
- **기호 방식**: `chmod u+x file`(소유자에 실행 추가) · `chmod go-w file`(그룹·기타 쓰기 제거) · `a`=all.
소유자 변경 **`chown`**(change owner), 그룹 변경 **`chgrp`**.

**디렉터리 권한 — 함정**

디렉터리에서는 의미가 달라진다.
- **r** — 목록 보기(`ls`)
- **w** — 그 안에 **파일 생성·삭제**(파일 자체 권한과 무관하게 **삭제 가능**!)
- **x** — 그 디렉터리로 **진입**(`cd`)·통과
**x 없으면 들어갈 수 없다**, **디렉터리 w가 있으면 남의 파일도 지울 수 있다**(→ 스티키 비트가 필요한 이유).

**umask — 디폴트 권한 (계산법)**

**`umask`**는 새로 만드는 파일·디렉터리의 **기본 권한에서 빼는(마스킹) 값**.**[계산]** 기준값: **파일 666**(실행권한 없음)·**디렉터리 777**. 여기서 umask를 뺀다.
umask **022** → 파일 **644**(`rw-r--r--`), 디렉터리 **755**(`rwxr-xr-x`).
umask **077** → 파일 **600**, 디렉터리 **700** (가장 안전).
※ 파일은 처음부터 **실행권한이 안 붙는다**는 게 함정.
설정은 `umask 022`, 영구 적용은 `/etc/profile`·`~/.bashrc`.

**보안 포인트**

**최소 권한 원칙** — 불필요한 **쓰기·실행 권한 제거**. 특히 **기타(other)에 쓰기 권한**(`777`)은 매우 위험. 중요 설정 파일은 `600`·`644`, umask는 **022 이상(권장 027·077)**.

> **시험 한줄정리:** **r4·w2·x1**을 **소유자/그룹/기타** 3자리로(`755`=`rwxr-xr-x`) / `chmod` 변경·`chown` 소유자 / 디렉터리는 **x=진입·w=삭제** / **umask=뺄셈**(파일 666·디렉터리 777 기준, 022→644·755)

_관련 개념: specialperm · uidgid · linuxfs_

## 특수 권한 (SetUID · SetGID · 스티키 비트) — SetUID · SetGID · Sticky Bit

`시스템 보안`  `SetUID 4000` `SetGID 2000` `스티키 1000` `passwd=4755·/tmp=1777` `find -perm -4000`

**한줄:** SetUID(4000)=실행 중 소유자 권한 / SetGID(2000)=그룹 권한·디렉터리 그룹 상속 / 스티키(1000)=자기 파일만 삭제 / 점검=find -perm -4000

**정의 — 일반 rwx 앞에 붙는 네 번째 자리**

`chmod 4755`처럼 **맨 앞 한 자리**가 특수 권한이다. **SetUID=4 · SetGID=2 · 스티키 비트=1** (더해서 쓸 수 있음).

**SetUID가 왜 필요한가 — 딜레마로 이해하기**

비밀번호를 바꾸려면 `/etc/shadow`를 고쳐야 하는데, 그 파일은 **권한 400 — root만 읽기**다. 여기서 딜레마가 생긴다.
- 사용자에게 `/etc/shadow` **쓰기 권한을 주면** → **남의 비밀번호까지** 바꿀 수 있다 ❌
- **안 주면** → **자기 비밀번호도** 못 바꾼다 ❌
**[SetUID의 답]** **권한을 '사람'이 아니라 '프로그램'에 붙인다.** — “이 프로그램을 **실행하는 동안만** 너는 잠깐 소유자(root)가 된다.” 그래서 `passwd`는 root 권한으로 shadow를 고치되, **하는 일이 정해져 있어** 그 이상은 못 한다.
🏦 비유: 금고엔 내가 못 들어가지만, **창구 직원**(=SetUID 프로그램)이 금고 권한으로 **내 것만** 꺼내준다.

**오해 바로잡기 — 사용자가 root가 되는 게 아니다**

❌ “실행하면 **사용자에게** root 권한을 준다” → ⭕ “**프로그램(프로세스)이** root 권한으로 실행된다”. 사용자는 root가 되지 않고, **그 프로그램이 제공하는 기능**만 쓸 수 있다.**[🏧 ATM 비유]** ATM은 은행 금고 권한이 있고 **누구나** 쓸 수 있다. 하지만 내가 ATM을 쓴다고 **내가 금고 권한을 얻는 건 아니다** — 나는 '출금' 버튼만 누르고, ATM이 **내 잔액을 확인해 내 돈만** 내준다.

- **0755 (일반)**: `-rwxr-xr-x`
실행 시 EUID = **실행한 사람**

- **4755 (SetUID)**: `-rw**s**r-xr-x`
실행 시 EUID = **파일 소유자**

**차이는 `s` 한 글자뿐**이고 rwx는 동일하다. 주의: **root 소유라고 root 권한으로 실행되는 게 아니다**(`/bin/ls`도 root 소유지만 SetUID가 없어 실행자 권한으로 돈다). 또한 **권한이 부족할 때만 발동하는 조건부 장치가 아니라**, 실행하면 **항상** EUID가 소유자로 바뀐다(그래서 root가 일반 사용자 소유 SetUID를 실행하면 **권한이 오히려 내려간다**). 어떤 UID가 될지는 비트가 아니라 **`ls -l`의 소유자 칸**이 정한다.

**셋의 역할**

- **SetUID(4000)** — 실행하는 동안 **EUID가 파일 소유자**가 된다(주로 root). 예: `/usr/bin/passwd`가 일반 사용자도 `/etc/shadow`를 고칠 수 있는 이유. 표시: 소유자 x자리에 **`s`** → `-rw**s**r-xr-x`(4755)
- **SetGID(2000)** — 실행 중 **그룹 권한**을 얻음. **디렉터리**에 걸면 그 안에 만든 파일이 **디렉터리의 그룹을 상속**(공동 작업 디렉터리). 표시: 그룹 x자리에 **`s`**
- **스티키 비트(1000)** — **디렉터리**에 설정. 그 안에서 **자기 소유 파일만 삭제** 가능. 대표: `/tmp` → `drwxrwxrw**t**`(1777). 표시: 기타 x자리에 **`t`**
**[대문자 S·T의 의미]** 원래 **실행 권한(x)이 없는데** 특수 권한만 걸리면 **대문자 `S`·`T`**로 표시된다(설정은 됐지만 실행 불가 상태).

**설정 · 점검 명령 (시험 단골)**

설정: `chmod 4755 file`(SetUID) · `chmod u+s file` / `chmod 2755`·`g+s`(SetGID) / `chmod 1777 dir`·`o+t`(스티키)**[SetUID 파일 찾기]** `find / -perm -4000 -print` — **SetUID가 설정된 모든 파일**을 찾는다(정기 점검 필수). SetGID는 `-perm -2000`.
※ `-4000`(앞에 **붙임표**)은 '그 비트를 **포함**하는' 것, `4000`은 '권한이 **정확히** 4000'인 것. 실무·시험 모두 **`-4000`**을 주로 쓴다.

**보안 — 권한 상승의 온상**

SetUID 프로그램에 **버퍼 오버플로·경쟁 조건(TOCTOU)·PATH 조작** 취약점이 있으면 **root 권한 탈취**로 직결된다. 그래서 **불필요한 SetUID 파일 제거**(`chmod u-s`)와 **주기적 목록 점검**(위 find 명령)이 리눅스 보안의 기본이다.**[왜 뚫리면 끝인가]** 빌려주는 건 **제한 없는 소유자 열쇠(root면 전체 권한)**다. “김씨 칸만 여는 열쇠” 같은 건 없다. **'본인 것만'이라는 제한은 자물쇠가 아니라 프로그램 코드에만** 있어서, 프로그램이 속아 넘어가면 그 열쇠가 **통째로** 공격자에게 간다. 그래서 **SetUID 프로그램은 BOF 공격의 대표 표적**이다(일반 프로그램을 터뜨려봐야 원래 자기 권한밖에 안 나온다).

**관점 — SetUID는 '보안 기능'이 아니라 필요악**

SetUID를 **보안 기능으로 이해하면 계속 헷갈린다**. 정확히는 **보안을 희생해 기능을 가능하게 하는 장치**다.
- **보안만 생각하면** → SetUID는 **하나도 없는 게 최선**
- **없으면** → 사용자가 비밀번호조차 못 바꿈(기능이 성립 안 함)
- **그래서** → 꼭 필요한 것만 남기고 **최소화**
즉 실무·시험의 주제는 **“SetUID를 잘 거는 법”이 아니라 “SetUID를 줄이는 법”**이다. 시험에서도 늘 **위험 요소·점검 대상**으로 출제된다(방어 수단으로 나오지 않는다). 대안은 **sudo·Capabilities**(별도 카드).

> **시험 한줄정리:** **SetUID 4**(실행 중 소유자 권한, `passwd`=4755, 표시 `s`) · **SetGID 2**(그룹 권한·디렉터리 그룹 상속) · **스티키 1**(디렉터리, **자기 파일만 삭제**, `/tmp`=1777, 표시 `t`) / 점검 `find / -perm -4000 -print`

_관련 개념: fileperm · uidgid · race_

## 계정 파일 (/etc/passwd · /etc/shadow) — Password & Shadow File

`시스템 보안`  `passwd 7필드` `shadow 9필드` `x=shadow로 이동` `644 vs 400` `존 더 리퍼`

**한줄:** /etc/passwd=계정 정보 7필드(누구나 읽기 가능, 패스워드 자리는 x) / /etc/shadow=암호화된 패스워드 9필드(root만) / 크래킹 대상

**/etc/passwd — 7개 필드 (순서 그대로 출제)**

```
root:x:0:0:root:/root:/bin/bash
```

- ① **사용자명** ② **패스워드 자리**(**`x`**=실제 해시는 shadow에 있음) ③ **UID** ④ **GID** ⑤ **설명(코멘트)** ⑥ **홈 디렉터리** ⑦ **로그인 셸**
권한은 **644** — **누구나 읽을 수 있다**(프로그램들이 UID↔이름 변환에 필요해서).

**왜 shadow로 분리했나 (핵심)**

옛날엔 **암호화된 패스워드가 passwd 파일 안에** 있었다 → 파일이 **644라 누구나 읽을 수 있으니** 해시를 그대로 복사해 **오프라인 크래킹**이 가능했다. 그래서 해시만 **`/etc/shadow`로 분리**하고 권한을 **400(또는 600) — root만 읽기**로 잠갔다. passwd의 `x`는 '해시는 shadow에 있다'는 표시.

**/etc/shadow — 9개 필드**

① 사용자명 ② **암호화된 패스워드(해시)** ③ 마지막 변경일 ④ **최소** 사용일 ⑤ **최대** 사용일(만료 주기) ⑥ **경고** 일수 ⑦ **비활성** 유예일 ⑧ **계정 만료일** ⑨ 예약**[해시 자리 표시]** `*`·`!`=**로그인 잠금**, 빈 칸=**패스워드 없음(매우 위험)**. 최근 해시는 `$6$`(SHA-512)로 시작.

**패스워드 크래킹 · 존 더 리퍼**

해시를 얻으면 **오프라인 크래킹**을 시도한다.
- **사전 공격**(Dictionary) — 흔한 단어 목록 대입
- **무차별 대입**(Brute Force) — 모든 조합
- **레인보우 테이블** — 미리 계산한 해시표 (→ **솔트(salt)**로 무력화)
**존 더 리퍼(John the Ripper)** — 대표적인 패스워드 크래킹 도구. **공격 도구이자, 관리자가 자기 시스템의 취약한 암호를 점검하는 도구**로도 쓴다.

**방어**

**shadow 분리 유지**·권한 확인, **솔트+강한 해시(SHA-512)**, **복잡도·만료 주기 정책**, 로그인 실패 **계정 잠금**, 불필요 계정 삭제·`/sbin/nologin` 처리.

> **시험 한줄정리:** `/etc/passwd` **7필드**(이름:**x**:UID:GID:설명:홈:셸, **644 누구나 읽기**) / `/etc/shadow` **9필드**(해시+만료 정책, **root만**) / 분리 이유=**오프라인 크래킹 방지** / 크래킹 도구=**존 더 리퍼**, 방어=솔트·SHA-512

_관련 개념: uidgid · shelltypes · fileperm_

## 리눅스 로그 파일 — Linux Log Files (utmp·wtmp·btmp)

`시스템 보안`  `utmp=현재접속` `wtmp=접속이력` `btmp=실패기록` `바이너리→전용명령` `WORM 무결성`

**한줄:** /var/log에 기록 / utmp=현재 접속(who)·wtmp=접속 이력(last)·btmp=실패(lastb)·lastlog=마지막 로그인 / 바이너리라 전용 명령으로만 조회

**위치**

대부분 **`/var/log`** 아래에 쌓인다. 침해사고 분석의 1차 증거이자, **공격자가 가장 먼저 지우려는 대상**.

**3대 로그 (utmp·wtmp·btmp — 시험 핵심)**

- **utmp** — **현재 로그인 중**인 사용자. 조회: **`who`**·`w`·`users`
- **wtmp** — **로그인/로그아웃 이력**(누가 언제 접속했다 나갔나), 재부팅 기록도. 조회: **`last`**
- **btmp** — **실패한 로그인 시도**(**b**ad). **무차별 대입 공격 탐지**의 핵심. 조회: **`lastb`**
- **lastlog** — 사용자별 **마지막 로그인** 시각. 조회: `lastlog`
**[함정]** 이 넷은 **바이너리 파일**이라 `cat`·`vi`로 열면 깨진다 → **반드시 전용 명령**으로 봐야 한다. (텍스트 로그와 구분해서 출제)

**그 밖의 로그 (텍스트)**

- **`secure`**(데비안 계열은 `auth.log`) — **인증·su·sudo·SSH 접속** 기록. 침입 분석 1순위
- **`messages`**(`syslog`) — 시스템 전반 메시지
- `cron` — 예약 작업 실행 · `xferlog` — FTP 전송 · `sulog` — su 사용 · `dmesg` — 부팅·커널
- **acct/pacct** — 사용자가 실행한 **명령어** 기록(`lastcomm`)
수집·관리는 **`syslog`/`rsyslog`** 데몬이 담당(`/etc/rsyslog.conf`).

**로그 무결성 — WORM · 원격 로그**

공격자는 흔적을 지우려 로그를 **삭제·변조**한다. 그래서:
- **WORM(Write Once Read Many)** — **한 번 기록하면 수정·삭제할 수 없는** 저장 매체·방식. 로그를 여기 보관하면 **위·변조 자체가 불가능**해 증거 능력이 생긴다.
- **원격 로그 서버**로 실시간 전송(로컬을 지워도 사본이 남음)
- 로그 파일 **권한 최소화**, **정기 백업·보존 기간** 준수, 무결성 점검(해시)

> **시험 한줄정리:** `/var/log`: **utmp**=현재접속(`who`)·**wtmp**=접속이력(`last`)·**btmp**=**실패**(`lastb`)·**lastlog**=마지막로그인 → **바이너리라 전용 명령** / `secure`=인증 / 무결성=**WORM**·원격 로그 서버

_관련 개념: passwdfile · linuxfs · cron_

## cron · crontab (예약 작업) — cron · crontab · at

`시스템 보안`  `분 시 일 월 요일` `crontab -e/-l/-r` `at=1회성` `cron.allow/deny` `백도어 지속성`

**한줄:** 정해진 시각에 작업을 자동 실행하는 데몬 / crontab 5필드=분 시 일 월 요일 / at은 1회성 / 공격자의 백도어 지속성 수단

**정의 (어원)**

**cron**은 그리스어 **chronos(시간)**에서 온 이름. **주기적으로** 명령을 실행하는 데몬(`crond`)이고, 그 일정표가 **crontab**(cron table)이다. **`at`**은 **1회성** 예약(한 번만 실행) — 이 둘의 구분이 자주 나온다.

**crontab 형식 — 5개 필드 (순서 암기)**

```
분  시  일  월  요일   명령
 *   *   *   *    *
```

- **분** 0–59 · **시** 0–23 · **일** 1–31 · **월** 1–12 · **요일** 0–7(**0과 7 모두 일요일**)
- 예) `30 2 * * *` = 매일 **새벽 2시 30분** · `0 */6 * * *` = 6시간마다
※ **시·분 순서가 아니라 분·시 순서**인 게 함정.

**명령 · 파일 위치**

`crontab -e`(편집) · `crontab -l`(목록) · `crontab -r`(**전체 삭제 — 주의**) · `crontab -u 사용자`(관리자가 지정)
사용자별 파일 `/var/spool/cron/`, 시스템 전역 `/etc/crontab`·`/etc/cron.d/`·`cron.daily` 등.

**보안 — 지속성(persistence) 수단**

공격자는 침투 후 **cron에 악성 스크립트를 등록**해 **재부팅·시간이 지나도 반복 실행**되게 만든다(백도어 **지속성** 확보, 역방향 셸 주기적 접속 등). 그래서 침해사고 조사 때 **crontab 목록은 필수 점검 대상**이다.

**방어 — cron.allow / cron.deny**

**`/etc/cron.allow`**에 적힌 사용자만 cron 사용 허용, **`/etc/cron.deny`**는 차단 목록. **allow가 있으면 allow 우선**(거기 없는 사람은 전부 차단)이라 **allow 방식이 더 안전**하다. 그 외: crontab 정기 점검, cron 로그(`/var/log/cron`) 확인, 등록 스크립트 **권한·소유자 확인**.(`at`도 `at.allow`·`at.deny`로 동일하게 제어)

> **시험 한줄정리:** cron=**주기** 실행(chronos), **at=1회성** / crontab **분 시 일 월 요일**(요일 0·7=일요일) / `-e`편집·`-l`목록·`-r`전체삭제 / **백도어 지속성** 표적 → `cron.allow`로 통제·정기 점검

_관련 개념: linuxlog · bashfiles · apt_

## 리눅스 보안 도구 · 점검 명령 — Security Tools · Kali Linux

`시스템 보안`  `칼리 리눅스=모의해킹 배포판` `목적별 분류` `Tripwire 무결성` `chkrootkit 루트킷` `find로 이상 파일 탐지`

**한줄:** 목적별 분류가 핵심(스캔·취약점·패킷·크래킹·무결성·탐지) / 칼리 리눅스=도구 내장 모의해킹 배포판 / find로 SetUID·소유자 없는 파일 점검

**칼리 리눅스 (Kali Linux)**

**모의 해킹·취약점 점검용 도구를 미리 모아 놓은 리눅스 배포판**(데비안 기반, 옛 BackTrack의 후속). 수백 개 도구가 기본 탑재돼 **침투 테스트·보안 진단**에 쓰인다. **도구 자체는 중립**이고, **허가받은 대상에만** 사용해야 한다(무단 사용은 불법).

**도구 — 목적별 분류 (이렇게 외우기)**

- **포트·네트워크 스캔** — **Nmap**(Network Mapper)
- **취약점 점검** — **Nessus**·**OpenVAS**
- **패킷 캡처·분석** — **Wireshark**·**tcpdump**
- **패스워드 크래킹** — **John the Ripper**·**Hydra**
- **파일 무결성 점검** — **Tripwire**·**AIDE** (해시로 변조 탐지)
- **침입 탐지(IDS)** — **Snort**
- **루트킷 탐지** — **chkrootkit**·**rkhunter**
- **접근 통제** — **TCP Wrapper**(`hosts.allow`/`hosts.deny`)

**find로 이상 파일 탐지 (점검 실무)**

- `find / -perm -4000 -print` — **SetUID 파일**(권한 상승 통로) 점검
- `find / -nouser -o -nogroup` — **소유자·그룹이 없는 파일**(삭제된 계정의 잔존물, 침입 흔적)
- `find / -name "..." -o -name ".. "` — **은닉을 노린 수상한 이름**의 파일
- `find / -mtime -1` — **최근 변경된 파일**(침해 직후 변경 추적)
- `find / -size +100M` — 비정상적으로 큰 파일(수집된 데이터 은닉)

**정리 관점**

시험은 **'이 도구가 무슨 용도인가'**를 묻는다. **Nmap=스캔 · Nessus=취약점 · Wireshark=패킷 · John the Ripper=패스워드 · Tripwire=무결성 · Snort=침입탐지 · chkrootkit=루트킷** — 이 대응 관계만 확실히 하면 대부분 풀린다.

> **시험 한줄정리:** **칼리 리눅스**=모의해킹 도구 내장 배포판 / 용도 대응: **Nmap**스캔·**Nessus**취약점·**Wireshark**패킷·**John the Ripper**크래킹·**Tripwire**무결성·**Snort**IDS·**chkrootkit**루트킷 / 점검 `find / -perm -4000`·`-nouser`

_관련 개념: specialperm · passwdfile · linuxlog_

## 권한 위임의 대안 (sudo · Capabilities) — sudo · POSIX Capabilities · MAC

`시스템 보안`  `SetUID는 1970년대 유산` `sudo=정책+감사로그` `Capability=root 분할` `SELinux/AppArmor=MAC` `ping은 이제 SetUID 아님`

**한줄:** SetUID는 권한을 통째로 빌려줘 위험 / 현대는 sudo(정책·로그)·Capabilities(root를 40여 조각으로)·MAC으로 잘게 위임 / 강화 원칙=SetUID를 이들로 대체

**왜 대안이 나왔나**

SetUID는 **1970년대** 설계다. 당시 유닉스는 **서로 신뢰하는 소수**가 쓰던 환경이었고(인터넷도 원격 공격자도 없었다), 권한 모델이 **`UID/GID + rwx`뿐**이라 표현력이 낮았다. 그 안에서 짜낸 해법이라 **권한을 통째로(root면 전권) 빌려주는** 방식이 됐다.**[문제]** 필요한 건 “포트 하나 열기”뿐인데 **root 전체**를 줘야 한다 → 그 프로그램이 뚫리면 **시스템 전체**가 넘어간다. 그래서 이후 **“필요한 만큼만 쪼개서 위임”**하는 방식들이 개발됐다.

**① sudo — 정책으로 위임 + 감사 로그**

**sudo(superuser do)**: **누가 / 어느 호스트에서 / 무슨 명령을** 실행할 수 있는지 **`/etc/sudoers`** 정책으로 지정한다(편집은 문법 검사가 되는 `visudo`).
- **명령 단위로 좁게** 허용 가능 — root 셸을 통째로 주지 않는다
- **누가 언제 무엇을 실행했는지 로그가 남는다**(`/var/log/secure`) → **책임 추적성**
- 확인 `sudo -l`. **`su`와 비교**: `su`는 **root 비밀번호로 root가 되어 무엇이든** 가능하지만, `sudo`는 **자기 비밀번호로 허용된 명령만** + 로그가 남는다 → **sudo 권장**

**② Capabilities — root를 잘게 쪼갬**

리눅스는 root의 전능한 권한을 **40여 개의 능력(capability)**으로 분할했다. 필요한 **조각만** 프로그램에 부여한다.
- **CAP_NET_RAW** — 원시 소켓 사용 · **CAP_NET_BIND_SERVICE** — 1024 미만 포트 열기 · **CAP_DAC_OVERRIDE** — 파일 권한 검사 무시
- 부여·확인: `setcap` · `getcap`
**[대표 사례]** `ping`은 예전엔 **SetUID root**였다(원시 소켓이 필요해서). 지금은 대부분 **`cap_net_raw` 하나만** 갖는다 → **뚫려도 root가 나오지 않는다**.

**③ 더 강한 통제 — MAC · seccomp**

- **SELinux · AppArmor** — **강제 접근 통제(MAC)**. 관리자가 정한 정책이 우선이라 **root라도 정책 밖 행동은 불가**. (기존 rwx 방식은 소유자가 마음대로 바꿀 수 있는 **임의 접근 통제(DAC)**)
- **seccomp** — 프로세스가 쓸 수 있는 **시스템 콜 자체를 제한** → 뚫려도 할 수 있는 게 없다
- **PolicyKit** — 권한이 필요한 작업을 **별도 데몬에 요청**하고 정책으로 판단(프로그램이 권한을 직접 갖지 않음)

**그럼 SetUID는 왜 아직 남아 있나**

① **하위 호환성** — 수십 년 된 프로그램이 이를 전제로 동작 ② **단순함** — capabilities는 설정이 복잡하고 잘못 쓰면 오히려 위험. 다만 배포판들이 **SetUID 바이너리 수를 계속 줄이는 추세**다.
**시험 포인트:** 리눅스 보안 강화의 기본 원칙은 **“불필요한 SetUID 제거 → sudo·Capabilities로 대체”**.

> **시험 한줄정리:** SetUID=권한을 **통째로** 빌려주는 1970년대 방식 → 현대 대안: **sudo**(`/etc/sudoers` 정책+**감사 로그**, `su`보다 권장) · **Capabilities**(root를 40여 조각으로, `ping`=`cap_net_raw`) · **SELinux/AppArmor**(MAC, root도 정책 밖 불가) / 강화 원칙=**SetUID 제거 후 대체**

_관련 개념: specialperm · uidgid · passwdfile_
