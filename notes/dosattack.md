# 네트워크 기반 공격 — DoS·DDoS

> 자동 생성 — 원본은 `cards/dosattack.js`. 직접 수정 금지.

## DoS · DDoS 개요 — Denial of Service · Distributed DoS

`네트워크 보안`  `가용성 침해` `DDoS=봇넷·좀비PC` `DRDoS=반사·증폭` `대역폭·자원·애플리케이션` `출발지 위조`

**한줄:** 정상 서비스를 못 하게 만드는 가용성 공격 / DoS=단일, DDoS=다수 좀비PC(봇넷), DRDoS=출발지를 피해자로 위조해 제3자가 대신 때리게 함

**정의 — 보안 3요소 중 '가용성'**

**DoS(Denial of Service)** — 시스템 자원을 고갈시켜 **정상 사용자가 서비스를 받지 못하게** 만드는 공격. 정보를 훔치거나(기밀성) 바꾸는(무결성) 게 아니라 **가용성(Availability)**을 노린다.
- **DoS**: **한 대**에서 공격. 차단이 비교적 쉽다.

- **DDoS (Distributed)**: 악성코드에 감염된 **좀비 PC(봇넷)** 수천~수만 대를 **C&C 서버**로 조종해 동시에 공격. **출발지가 분산돼** 차단이 어렵다.

- **DRDoS (Distributed Reflection)**: 출발지 IP를 **피해자로 위조**해 아무 죄 없는 **제3의 서버들이 응답을 피해자에게** 보내게 함. **반사 + 증폭**으로 위력이 커지고 **진짜 공격자를 추적하기 어렵다**.

**공격 유형 3분류 (어디를 고갈시키나)**

- **① 대역폭 소진형(볼류메트릭)** — 회선 자체를 채워버림. **UDP·ICMP Flooding, 스머프, DRDoS 증폭**
- **② 자원 고갈형(프로토콜)** — 서버의 **연결 테이블·메모리**를 고갈. **SYN Flooding, Land Attack**
- **③ 애플리케이션 계층형** — 적은 트래픽으로 **웹 서버 처리 능력**을 고갈. **HTTP GET Flooding, Slowloris, Hash DoS** — **정상 요청과 구분이 어려워** 탐지가 가장 까다롭다

**공통 대응**

- **임계치 기반 차단**(초당 요청·연결 수 제한, Rate Limit)
- **출발지 IP 위조 차단** — **인그레스 필터링**·uRPF(들어온 경로가 맞는지 검증)
- **DDoS 대응 장비·클린존**, ISP·CDN 단에서 흡수
- **불필요한 서비스·포트 차단**, 패치, 이중화·확장성 확보
**핵심 한계**: 대역폭 자체가 가득 차면 **서버에서 막을 수 없다** → **상위(ISP·CDN)에서 걸러야** 한다.

> **시험 한줄정리:** DoS=**가용성** 침해 / **DDoS**=좀비PC(봇넷)+**C&C** 조종 / **DRDoS**=출발지를 피해자로 위조해 **제3자가 반사·증폭** / 유형 **①대역폭(UDP·ICMP·스머프) ②자원(SYN·Land) ③애플리케이션(HTTP GET·Slow·Hash)** / 대응=임계치·인그레스 필터링·상위 차단

_관련 개념: synflood · icmpattack · httpflood_

## TCP SYN Flooding · Land Attack — SYN Flooding · Land Attack

`네트워크 보안`  `3-way 마지막 ACK 안 보냄` `백로그 큐 고갈` `SYN 쿠키` `Land=출발지·목적지 동일` `netstat SYN_RECEIVED`

**한줄:** SYN Flooding=3-way의 마지막 ACK를 안 보내 연결 대기 큐(백로그)를 고갈 / Land Attack=출발지와 목적지를 같게 위조해 자기 자신에게 응답하게 만듦

**TCP SYN Flooding — 원리**

3-way handshake의 **빈틈**을 노린다.
- **1 SYN 폭주** — 공격자가 **출발지 IP를 위조**한 SYN을 대량 전송

- **2 서버 대기** — 서버는 SYN+ACK를 보내고 **백로그 큐**에 자리를 잡아 둠(**SYN_RECEIVED**)

- **3 ACK 안 옴** — 위조된 IP라 **마지막 ACK가 오지 않음** → 자리가 계속 점유됨

- **4 큐 고갈** — 큐가 가득 차 **정상 사용자의 연결이 거부**됨

**탐지**: `netstat -an`에 **SYN_RECEIVED가 대량**으로 보인다. 트래픽 양은 적어도 효과가 크다.

**SYN Flooding 대응 (시험 단골)**

- **SYN 쿠키(SYN Cookie)** — **큐에 저장하지 않고** 필요한 정보를 순서번호에 암호화해 담아 보냈다가, **ACK가 오면 검증**해 그때 연결을 만든다 → **큐가 고갈되지 않는다**(가장 대표적인 대응)
- **백로그 큐 크기 확대**
- **SYN_RECEIVED 타임아웃 단축** — 오래 붙잡지 않고 빨리 정리
- **First SYN Drop** — 첫 SYN을 일부러 버리고, **정상 클라이언트는 재전송**한다는 성질을 이용해 걸러낸다
- 방화벽·IPS의 **임계치 기반 차단**, 인그레스 필터링

**Land Attack**

**출발지 IP·포트를 목적지와 똑같이** 위조한 SYN 패킷을 보낸다. 받은 시스템은 **자기 자신에게 응답**을 보내며 무한히 맴돌아 **자원을 소모**한다(이름은 Local Area Network Denial).**[대응]** **출발지 IP = 목적지 IP인 패킷을 차단**(라우터·방화벽 필터링). 요즘 OS는 대부분 **패치**되어 있어 실제 위협은 낮지만 **개념 문제로는 자주** 나온다.

> **시험 한줄정리:** **SYN Flooding**=위조 SYN 폭주 → **백로그 큐 고갈**(netstat에 **SYN_RECEIVED** 대량) → 대응 **SYN 쿠키**·큐 확대·타임아웃 단축·First SYN Drop / **Land Attack**=**출발지=목적지**로 위조해 자기 자신에게 응답 → 동일 IP 패킷 차단

_관련 개념: dos · tcpstate · tcpudp_

## ICMP 공격 · 스머프 · UDP Flooding — Smurf · ICMP / UDP Flooding · Fraggle

`네트워크 보안`  `Echo Request/Reply 악용` `스머프=브로드캐스트 증폭` `Fraggle=UDP판` `디렉티드 브로드캐스트 차단` `임계치·인그레스 필터링`

**한줄:** 스머프=출발지를 피해자로 위조한 ICMP를 브로드캐스트로 뿌려 모든 응답이 피해자에게 몰리게 함 / Fraggle은 UDP판 / 대응=디렉티드 브로드캐스트 차단

**공격에 쓰이는 ICMP 메시지**

- **Echo Request(8) / Echo Reply(0)** — **ping**. **스캐닝(ping 스윕)·ICMP Flooding·스머프**에 사용되는 **대표 메시지**
- **Destination Unreachable(3)** — 위조해 보내면 **정상 연결을 끊게** 만들 수 있다
- **Redirect(5)** — 위조하면 **경로를 공격자 쪽으로 변조**(중간자 공격)
- **Time Exceeded(11)** — TTL 소진 통지. **traceroute**가 이용 → **내부 구조 정찰**에 악용
- **Source Quench(4)** — 속도를 늦추라는 메시지. 위조 시 **성능 저하** 유발(현재는 폐기)

**스머프 공격 (Smurf) — 반사·증폭의 원형**

- **1 위조** — 출발지 IP를 **피해자**로 위조한 **ICMP Echo Request** 생성

- **2 브로드캐스트** — 중계 네트워크의 **브로드캐스트 주소**로 전송

- **3 증폭** — 그 네트워크의 **모든 호스트가 Echo Reply**를 보냄

- **4 집중** — 응답이 전부 **피해자에게** 쏟아짐(수백 배 증폭)

중계로 이용당하는 네트워크를 **증폭 네트워크(Amplifier)**라 한다.
**Fraggle 공격** — **똑같은 원리를 UDP로** 수행(echo·chargen 서비스 이용). **스머프=ICMP, Fraggle=UDP**로 짝지어 외운다.

**대응 (ICMP · UDP Flooding 공통)**

- **디렉티드 브로드캐스트 차단** — 라우터에서 `no ip directed-broadcast`. **스머프의 근본 대응**
- **브로드캐스트로 온 ICMP에 응답하지 않도록** 호스트 설정
- **인그레스 필터링**(출발지 IP 위조 차단) — 반사 공격 자체를 막는 근본 대책
- **불필요한 ICMP·UDP 서비스 차단**(echo·chargen 등 비활성화)
- **임계치 기반 제한**(Rate Limit)과 **ISP·DDoS 대응 장비**에서의 상위 차단

> **시험 한줄정리:** ICMP 악용 메시지 = **Echo Request(8)/Reply(0)**·Unreachable(3)·**Redirect(5)**·Time Exceeded(11) / **스머프**=출발지를 피해자로 위조 + **브로드캐스트** → 모든 응답이 피해자에게(**Fraggle=UDP판**) / 대응=**디렉티드 브로드캐스트 차단**·인그레스 필터링·임계치

_관련 개념: dos · netproto · fragattack_

## IP 단편화 공격 (Ping of Death · Teardrop) — IP Fragmentation Attacks

`네트워크 보안`  `재조립 취약점` `PoD=규격 초과` `Teardrop=오프셋 조작` `Bonk·Boink 변종` `패치가 근본 대응`

**한줄:** IP 재조립 과정을 노림 / Ping of Death=규격(65535) 넘는 큰 패킷으로 오버플로 / Teardrop=단편 오프셋을 겹치거나 어긋나게 조작해 재조립 오류 유발

**공통 원리 — 재조립이 약점**

IP는 MTU보다 큰 패킷을 **단편(fragment)**으로 쪼개고, **최종 목적지에서 재조립**한다. 이때 **식별자·플래그·오프셋**을 믿고 합치는데, 이 값을 **비정상적으로 조작**하면 재조립 코드가 오작동해 **시스템이 다운**된다.

**Ping of Death (죽음의 핑)**

IP 패킷의 **최대 크기는 65,535바이트**인데, 이를 **초과하는 크기**의 ICMP 패킷을 **여러 단편으로 쪼개** 보낸다. 받는 쪽이 **재조립할 때 버퍼를 넘겨**(오버플로) 시스템이 다운된다.**[대응]** **OS 패치**(현대 OS는 대부분 방어됨) · 방화벽에서 **비정상적으로 크거나 단편화된 ICMP 차단** · 불필요한 ICMP 차단.

**Teardrop · 변종들**

**Teardrop** — 단편의 **오프셋 값을 겹치게(overlap)** 조작해 보낸다. 재조립 시 계산이 음수가 되거나 꼬여 **커널이 멈추거나 다운**된다.**[변종 (종류 문제로 출제)]** **Bonk** — 단편 **순서 번호(오프셋)를 모두 같게** 보내 혼란을 준다.
**Boink** — Bonk의 변형으로, 오프셋을 **일정하게 어긋나도록** 조작한다.
**NewTear·SynDrop** 등도 같은 계열의 변종이다.
**대응**: **OS 패치**가 근본 · 방화벽·IPS에서 **비정상 단편 차단** 및 **재조립 후 검사**.

> **시험 한줄정리:** 재조립 취약점 공격 / **Ping of Death**=**65,535바이트 초과** 패킷을 단편화 → 재조립 시 **오버플로** / **Teardrop**=**오프셋을 겹치게** 조작 → 재조립 오류(변종 **Bonk**=오프셋 동일, **Boink**=일정하게 어긋남) / 대응=**패치**·비정상 단편 차단

_관련 개념: ipheader · icmpattack · dos_

## HTTP GET Flooding · Cache Control · HULK — HTTP GET Flooding · CC Attack · HULK DoS

`네트워크 보안`  `애플리케이션 계층 DDoS` `3-way 완성 필요` `no-cache로 캐시 우회` `HULK=URL 랜덤화` `임계치·캡차`

**한줄:** 대량 HTTP GET으로 웹서버 자원 고갈 / Cache Control 공격=no-cache 헤더로 캐시를 우회해 원 서버 직접 타격 / HULK=URL을 매번 바꿔 캐시·탐지 회피

**HTTP GET Flooding**

대량의 **HTTP GET 요청**을 보내 웹 서버의 **처리 능력·DB 연결**을 고갈시킨다.**[특징 — 왜 막기 어려운가]** ① **3-way handshake를 정상적으로 완료**해야 요청이 가능하므로 **출발지 IP를 위조할 수 없다** → 대신 **실제 좀비 PC**가 필요하다.
② 요청 자체는 **문법적으로 정상**이라 패킷만 봐서는 **정상 사용자와 구분이 어렵다**.
③ DB 조회처럼 **무거운 페이지**를 노리면 적은 요청으로도 큰 효과.

**Cache Control 공격 (CC Attack)**

보통 반복 요청은 **웹 캐시·CDN**이 대신 응답해 원 서버 부하를 줄여 준다. 공격자는 요청 헤더에 **`Cache-Control: no-cache`**(또는 `no-store`)를 넣어 **캐시를 쓰지 말라고 지시**한다 → 모든 요청이 **원 서버까지 도달**해 부하가 그대로 걸린다.**[대응]** 중간 캐시·CDN이 **클라이언트의 Cache-Control 헤더를 무시**하고 캐시된 콘텐츠를 제공하도록 설정한다. 비정상적으로 **no-cache가 반복되는 요청**을 차단.

**HULK DoS**

**HULK(HTTP Unbearable Load King)** — 요청할 때마다 **URL 뒤 파라미터를 임의의 값으로 계속 바꾼다**(예: `/page?abc=랜덤값`).
- URL이 매번 달라 **캐시가 전혀 듣지 않고** 항상 원 서버가 처리
- **User-Agent·Referer도 랜덤화**해 패턴 기반 탐지를 회피
**대응**: **동일 IP·세션의 요청 수 임계치** 제한, 비정상적으로 다양한 **URL 파라미터 패턴 탐지**, 웹 방화벽(WAF).

**공통 대응**

- **임계치 기반 차단** — 같은 IP·세션의 **초당 요청 수** 제한
- **캡차(CAPTCHA)·자바스크립트 검증** — **실제 브라우저인지** 확인(봇 걸러내기)
- **웹 캐시·CDN 활용**과 클라이언트 캐시 헤더 무시 설정
- **WAF**로 비정상 패턴 차단, 서버 **이중화·오토스케일링**

> **시험 한줄정리:** **HTTP GET Flooding**=대량 GET으로 웹서버 고갈(**3-way 완성 필요 → IP 위조 불가·좀비PC**, 정상 요청과 구분 어려움) / **Cache Control 공격**=`no-cache`로 캐시 우회 → 캐시가 헤더를 **무시**하게 설정 / **HULK**=**URL 랜덤화**로 캐시·탐지 회피 → 임계치·캡차·WAF

_관련 개념: slowdos · dos · http_

## Slow HTTP 공격 · Hash DoS — Slowloris · RUDY · Slow Read · Hash DoS

`네트워크 보안`  `적은 트래픽·큰 효과` `Slow Header=Slowloris` `Slow POST=RUDY` `Slow Read` `Hash 충돌로 CPU 고갈`

**한줄:** 연결을 느리게 오래 붙잡아 동시 연결 수를 고갈(Slowloris·RUDY·Slow Read) / Hash DoS=해시 충돌을 유발하는 파라미터로 CPU를 고갈 / 둘 다 적은 트래픽으로 가능

**공통 특징 — 조용한 DoS**

대량 트래픽을 쏟아붓는 방식과 정반대다. **아주 적은 트래픽**으로 서버의 **동시 연결 수나 CPU**를 고갈시킨다.
- 트래픽이 적어 **대역폭 기반 탐지에 걸리지 않는다**
- 요청 형식이 **규격에 맞아** 비정상으로 보이지 않는다
- **공격자 한 대로도** 서버를 마비시킬 수 있다

**Slow HTTP 3종**

- **Slow HTTP Header DoS (Slowloris)** — HTTP **헤더를 완성하지 않는다**. 헤더의 끝을 알리는 **빈 줄(CRLF)을 보내지 않고** 조금씩 계속 이어 보내 **서버가 계속 기다리게** 만든다 → **동시 연결 수 고갈**
- **Slow HTTP POST DoS (RUDY, R-U-Dead-Yet)** — `Content-Length`를 **아주 크게 선언**해 놓고 본문을 **1바이트씩 아주 천천히** 보낸다 → 서버는 다 받을 때까지 **연결을 유지**
- **Slow Read** — 요청은 정상적으로 보내되, **응답을 아주 느리게 읽는다**(TCP 윈도우 크기를 매우 작게 광고) → 서버가 **다 보낼 때까지 연결 유지**

**Hash DoS**

웹 애플리케이션은 **POST 파라미터를 해시 테이블**에 저장한다. 해시 테이블은 보통 **O(1)**로 빠르지만, **같은 해시값이 나오도록 계산된 키**를 대량으로 보내면 **충돌이 몰려 O(n²)**로 느려진다.**[효과]** 단 **몇 개의 요청**만으로 **CPU 사용률 100%**를 만들 수 있다. 네트워크 부하가 거의 없어 **탐지가 매우 어렵다**.
**대응**: **POST 파라미터 개수·요청 본문 크기 제한**, **해시 함수에 난수(seed) 적용**(같은 충돌을 재현 못 하게), 언어·프레임워크 **패치**.

**Slow 계열 대응**

- **연결 타임아웃 설정** — 헤더·본문 수신에 **시간 제한**을 둔다(가장 직접적)
- **최소 전송 속도 요구** — 너무 느린 연결은 끊는다
- **IP당 동시 연결 수 제한**
- **Content-Length 상한** 설정, 웹서버 모듈 활용(예: `mod_reqtimeout`)

> **시험 한줄정리:** **적은 트래픽·큰 효과**형 / **Slowloris**=헤더를 끝내지 않음(**CRLF 미전송**) · **RUDY**=Content-Length 크게 잡고 **본문 찔끔찔끔** · **Slow Read**=응답을 **느리게 읽음**(윈도우 작게) → 대응 **타임아웃·최소속도·동시연결 제한** / **Hash DoS**=해시 **충돌** 유발로 **CPU 고갈** → 파라미터 수 제한·해시 난수화

_관련 개념: httpflood · dos · httpmsg_
