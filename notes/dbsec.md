## 데이터베이스 · DBMS 개요와 구성요소 — Database / Database Management System

`애플리케이션 보안`  `공용 데이터의 통합 집합` `DBMS=정의·조작·제어` `3단계 스키마(외부·개념·내부)` `논리적/물리적 독립성` `DBA`

**한줄:** DB=여러 사용자가 공용으로 쓰는 통합·저장된 운영 데이터 / DBMS의 3대 기능=정의·조작·제어 / 3단계 스키마(외부·개념·내부)로 데이터 독립성 확보

**데이터베이스 정의 (4가지 성질로 출제)**

**데이터베이스(Database)** — 여러 응용 시스템이 **공용**으로 쓰기 위해 **통합·저장**한 **운영 데이터**의 집합.
- **통합 데이터(Integrated)** — 같은 자료의 중복을 최소화
- **저장 데이터(Stored)** — 컴퓨터가 접근 가능한 매체에 저장
- **운영 데이터(Operational)** — 조직의 업무 수행에 반드시 필요한 자료(임시 자료가 아님)
- **공용 데이터(Shared)** — 여러 사용자가 동시에 함께 사용

**DBMS의 3대 기능 — 정의 · 조작 · 제어**

**DBMS(DataBase Management System)** = 사용자와 DB 사이에서 데이터를 관리해 주는 소프트웨어. 응용 프로그램이 파일을 직접 다루지 않게 해 준다.
- **정의 기능 (Definition)**: 데이터의 **구조·형식·제약조건**을 정한다 → **DDL**(CREATE·ALTER·DROP)

- **조작 기능 (Manipulation)**: 데이터를 **넣고·읽고·고치고·지운다** → **DML**(INSERT·SELECT·UPDATE·DELETE)

- **제어 기능 (Control)**: **무결성·보안(권한)·병행 제어·회복**을 담당 → **DCL**(GRANT·REVOKE·COMMIT·ROLLBACK)

**[보안 포인트]** **보안·권한 관리는 세 번째 '제어 기능'**에 속한다. "DBMS의 어느 기능이냐"로 자주 물어본다.

**구성요소 · 3단계 스키마**

**스키마(Schema)** = DB의 구조와 제약조건을 적어 둔 **설계도**. ANSI/SPARC는 이를 3단계로 나눈다.외부 스키마 (External)사용자·응용 프로그램이 보는 관점. 여러 개 존재. = 서브스키마·뷰
↓
개념 스키마 (Conceptual)조직 전체가 보는 통합 관점. **DB당 하나**. 그냥 "스키마"라 하면 이것
↓
내부 스키마 (Internal)실제 저장 구조·인덱스·접근 경로. 물리적 저장 관점

- **논리적 독립성** — 개념 스키마가 바뀌어도 외부 스키마(응용 프로그램)는 영향 없음
- **물리적 독립성** — 내부 스키마(저장 장치)가 바뀌어도 개념 스키마는 영향 없음
- **인스턴스(Instance)** — 스키마에 실제로 채워진 그 순간의 데이터 값
- **DBA(DataBase Administrator)** — 스키마 정의, **권한 부여·회수**, 백업·회복, 성능 관리를 맡는 사람

**DB를 쓰면 좋은 점 / 나쁜 점**

- **장점**: 중복 최소화 · 데이터 **일관성·무결성** 유지 · **공용 사용** · 보안(권한) 통제 · 데이터 독립성

- **단점**: 전문가(DBA) 필요 · 비용 큼 · **백업/회복이 어려움** · 시스템이 복잡 · **한 곳이 무너지면 전체가 마비**

> **시험 한줄정리:** DB=**통합·저장·운영·공용** 데이터 / DBMS 3대 기능=**정의(DDL)·조작(DML)·제어(DCL)**이고 **보안은 제어 기능** / 3단계 스키마=**외부(사용자·뷰)→개념(DB당 1개)→내부(저장 구조)**, 여기서 **논리적·물리적 데이터 독립성**이 나온다

## 데이터 모델 · 관계형 모델 · ERD — Data Model / Entity-Relationship Diagram

`애플리케이션 보안`  `계층·망·관계형` `릴레이션=행(튜플)+열(속성)` `기본키·외래키` `ERD=개체·속성·관계` `무결성 제약`

**한줄:** 데이터 모델=계층형·망형·관계형(현재 주류) / 관계형은 릴레이션(표)로, 행=튜플·열=속성, 기본키·외래키로 연결 / ERD는 개체(□)·속성(○)·관계(◇)로 그린 설계도

**데이터 모델의 종류**

**데이터 모델** = 현실 세계의 자료를 DB에 어떤 **구조**로 담을지 정한 틀.계층형 (Hierarchical)트리 구조. 부모-자식 **1:N**만 가능. 검색은 빠르나 구조 변경이 어렵다
→
망형 (Network)그래프 구조. **N:M** 표현 가능하나 구조가 복잡
→
관계형 (Relational)**표(테이블)**로 표현. 구조가 단순하고 SQL로 다룬다. **현재 대부분**
→
객체지향 / NoSQL객체·문서·키값 형태로 저장. 대용량·비정형에 사용

**관계형 모델 용어 (표 기준으로 외우기)**

관계형 DB의 표 하나 = **릴레이션(Relation)**.
- **튜플(Tuple)** = **행(Row)·레코드**. 튜플의 개수 = **카디널리티(Cardinality)**
- **속성(Attribute)** = **열(Column)·필드**. 속성의 개수 = **차수(Degree)**
- **도메인(Domain)** = 한 속성이 가질 수 있는 값의 범위(예: 성별 = 남/여)

- **기본키 (Primary Key)**: 튜플을 **유일하게 구분**하는 속성. **중복 불가 · NULL 불가**

- **후보키 / 대체키**: 기본키가 될 자격이 있는 키가 **후보키**, 그중 안 뽑힌 나머지가 **대체키**

- **외래키 (Foreign Key)**: 다른 릴레이션의 기본키를 참조하는 속성. **테이블끼리 연결하는 고리**

**무결성 제약조건 (3가지)**

- **개체 무결성(Entity Integrity)** — 기본키는 **NULL이 될 수 없고 중복될 수 없다**
- **참조 무결성(Referential Integrity)** — 외래키 값은 **참조하는 릴레이션의 기본키에 실제로 있는 값**이거나 NULL이어야 한다
- **도메인 무결성(Domain Integrity)** — 속성 값은 **정해진 도메인(자료형·범위)** 안에 있어야 한다
**[보안 연결]** 무결성 제약은 **DB 보안 3요소 중 무결성**을 DBMS가 스스로 지켜 주는 장치다.

**ERD (개체-관계 다이어그램)**

**ERD(Entity-Relationship Diagram)** — 현실의 대상과 그 사이의 관계를 그림으로 그린 **DB 설계도**. 피터 첸(Peter Chen) 표기법 기준.
- **□ 사각형 = 개체(Entity)** — 관리 대상(학생·상품)
- **○ 타원 = 속성(Attribute)** — 개체가 가진 정보(이름·가격). 기본키 속성은 **밑줄**
- **◇ 마름모 = 관계(Relationship)** — 개체 사이의 연관(수강·주문)
- **― 선** — 개체와 속성·관계를 연결. 선 위에 **1:1 · 1:N · N:M**(관계 차수, 카디널리티)를 적는다
**[정규화]** 중복·이상현상(삽입·삭제·갱신 이상)을 없애려고 테이블을 쪼개는 작업. **1NF(원자값) → 2NF(부분 함수 종속 제거) → 3NF(이행 함수 종속 제거) → BCNF** 순서로만 기억해도 충분하다.

> **시험 한줄정리:** 모델=**계층형(1:N 트리) → 망형(N:M) → 관계형(표, 현재 주류)** / 릴레이션: **행=튜플(카디널리티)·열=속성(차수)**, **기본키=중복·NULL 불가**, **외래키=다른 테이블 기본키 참조** / 무결성=**개체·참조·도메인** / ERD=**□개체 ○속성 ◇관계** / 정규화 **1NF→2NF→3NF→BCNF**

_관련 개념: db · sqlcmd · dbthreat_

## MySQL · Oracle과 SQL 명령 (권한 부여) — SQL / GRANT / REVOKE

`애플리케이션 보안`  `DDL·DML·DCL` `GRANT ... TO ...` `REVOKE ... FROM ...` `WITH GRANT OPTION` `CASCADE`

**한줄:** SQL은 DDL(구조)·DML(데이터)·DCL(권한·트랜잭션)로 나뉘며, 보안에서 핵심은 DCL의 GRANT(부여)·REVOKE(회수) / MySQL=오픈소스·웹, Oracle=상용·대규모

**MySQL vs Oracle**

- **MySQL (현 MariaDB 계열)**: 오픈소스·경량. **웹 서비스(LAMP)**에서 널리 사용. 기본 포트 **3306**. 관리 정보는 **`mysql` 데이터베이스**(user 테이블 등)에 저장

- **Oracle**: 상용·대규모 기업용. 안정성·기능이 강함. 기본 포트 **1521**(리스너). 관리 뷰는 **`DBA_USERS`·`DBA_ROLES`** 등

**[DB별 기본 계정]** 설치 직후 남는 **기본 계정·기본 패스워드**(Oracle의 `scott/tiger`, `system` 등)를 그대로 두는 것이 대표적 취약점이다. **불필요 계정 삭제·패스워드 변경**이 첫 조치.

**SQL 3분류 — DDL · DML · DCL**

- **DDL — 정의어 (Data Definition Language)**: **CREATE**(생성) · **ALTER**(변경) · **DROP**(삭제) · TRUNCATE. 테이블·뷰·인덱스 등 **구조**를 다룬다

- **DML — 조작어 (Data Manipulation Language)**: **SELECT**(조회) · **INSERT**(삽입) · **UPDATE**(수정) · **DELETE**(삭제). 안에 든 **데이터**를 다룬다

- **DCL — 제어어 (Data Control Language)**: **GRANT**(권한 부여) · **REVOKE**(권한 회수) · **COMMIT**(확정) · **ROLLBACK**(취소). **보안과 트랜잭션**을 다룬다

**[함정]** **DELETE는 DML, DROP·TRUNCATE는 DDL**이다. DELETE는 행을 지우고 롤백 가능, DROP은 테이블 자체를 없앤다.

**권한 부여 · 회수 (GRANT / REVOKE)**

```
-- 권한 부여: GRANT 권한 ON 대상 TO 사용자
GRANT SELECT, INSERT ON student TO user1;

-- 받은 권한을 남에게 또 줄 수 있게 하려면
GRANT SELECT ON student TO user1 WITH GRANT OPTION;

-- 권한 회수: REVOKE 권한 ON 대상 FROM 사용자
REVOKE INSERT ON student FROM user1;

-- 그 사용자가 남에게 넘긴 권한까지 연쇄 회수
REVOKE SELECT ON student FROM user1 CASCADE;
```

- **GRANT … TO** / **REVOKE … FROM** — 전치사를 바꿔 내는 함정 문제가 흔하다
- **WITH GRANT OPTION** — 권한을 **재부여**할 수 있는 옵션. 남발하면 권한이 퍼져 통제 불가
- **CASCADE** — 그 사람이 뿌린 권한까지 **연쇄 회수**. **RESTRICT**는 남에게 준 게 있으면 회수를 **거부**
- **ROLE(역할)** — 권한을 묶어 이름을 붙인 것. 사람마다 권한을 주는 대신 역할을 부여 → **RBAC**

**권한 관리에서 지켜야 할 원칙**

- **최소 권한(Least Privilege)** — 업무에 꼭 필요한 권한만. 응용 프로그램 계정에 **DBA/root 권한을 주지 않는다**
- **PUBLIC 권한 회수** — 모든 사용자에게 열린 권한(`PUBLIC`)은 위험하니 제거
- **계정 분리** — 관리자용 · 응용 프로그램용 · 조회 전용을 나눈다
- **불필요한 저장 프로시저·기본 계정 제거** — SQL 인젝션이 성공했을 때 피해 범위를 줄인다

> **시험 한줄정리:** **DDL=CREATE·ALTER·DROP(구조)** / **DML=SELECT·INSERT·UPDATE·DELETE(데이터)** / **DCL=GRANT·REVOKE·COMMIT·ROLLBACK(권한·트랜잭션)** / **GRANT 권한 ON 대상 TO 사용자**, **REVOKE … FROM 사용자**, 재부여는 **WITH GRANT OPTION**, 연쇄 회수는 **CASCADE** / 원칙은 **최소 권한**

## DB 보안 위협 요소와 보안 요구사항 — Database Security Threats & Requirements

`애플리케이션 보안`  `집성(Aggregation)` `추론(Inference)` `부적절한 접근 방지` `SQL 인젝션` `내부자 위협`

**한줄:** DB 고유 위협의 핵심은 집성(조각을 모아 민감 정보 완성)과 추론(허용된 값에서 금지된 값을 유도) / 요구사항은 기밀성·무결성·가용성에 부적절 접근 방지·추론 방지·사용자 인증·감사가 더해진다

**DB만의 위협 — 집성 vs 추론 (최다 출제)**

- **집성 (Aggregation)**: 낱개로는 **등급이 낮은 정보들을 모아** 더 **높은 등급의 정보**를 만들어 내는 것.
예) 직원 개개인의 이름·부서·전화번호는 공개지만, **전부 모으면 조직 전체 인력 구조**가 드러남

- **추론 (Inference)**: 접근이 **허용된 데이터로부터 논리적으로 유추**해 **허용되지 않은 데이터**를 알아내는 것.
예) "부서 평균 연봉"과 "부서원 수 1명"을 알면 **그 사람의 연봉**이 그대로 나옴

**[구분 요령]** **집성=조각을 모아 큰 그림**(더하기), **추론=아는 값에서 모르는 값을 논리로 끌어냄**(빼기·나누기). 대응은 **다중 인스턴스화(Polyinstantiation)·분할(Partitioning)·잡음 삽입·질의 제한**.

**일반적인 DB 보안 위협**

- **SQL 인젝션** — 입력값에 SQL을 섞어 인증 우회·데이터 유출. **가장 대표적인 공격**
- **권한 오·남용** — 과도한 권한을 받은 계정, 퇴사자 계정 미삭제, **내부자에 의한 대량 유출**
- **기본 계정·약한 패스워드** — 설치 시 기본값 방치, 리스너 패스워드 미설정
- **미패치 취약점** — DBMS 자체 버그를 노린 원격 공격
- **백업 매체 유출** — 백업본은 **대개 평문**이라 통째로 유출되면 DB를 여는 것과 같다
- **감사 기록 부재·삭제** — 누가 무엇을 봤는지 추적 불가
- **가용성 위협** — 삭제·랜섬웨어 암호화·과부하 질의

**DB 보안 요구사항**

- **기밀성(Confidentiality)** — 인가된 사람만 볼 수 있어야 한다 → 접근통제·암호화
- **무결성(Integrity)** — 데이터가 **정확·일관**해야 한다 → 무결성 제약, 트랜잭션, 병행 제어
- **가용성(Availability)** — 필요할 때 쓸 수 있어야 한다 → 백업·이중화
- **부적절한 접근 방지** — 인가된 사용자에게도 **인가된 데이터만** 열어야 한다(뷰·컬럼 단위)
- **추론 방지** — 허용된 질의로 **금지된 값이 유도되지 않게** 한다
- **사용자 인증** — OS 인증과 **별도로** DBMS가 다시 확인해야 한다
- **감사 기능(Audit)** — 누가·언제·무엇을 했는지 기록하고 그 기록을 보호
- **다단계 보호** — 데이터마다 **등급(민감도)**을 매겨 등급별로 통제

> **시험 한줄정리:** **집성=낮은 등급 조각을 모아 높은 등급 정보 완성** / **추론=허용된 값에서 금지된 값을 논리로 유도**, 대응은 **다중 인스턴스화·분할·잡음·질의 제한** / 요구사항=**기밀·무결·가용 + 부적절한 접근 방지 · 추론 방지 · 사용자 인증 · 감사 · 다단계 보호**

_관련 개념: dbsecway · db · dbmodel_

## 데이터베이스 보안 기법 (접근통제·암호화·감사) — Database Security Controls

`애플리케이션 보안`  `DAC·MAC·RBAC` `뷰(View) 기반 통제` `TDE·컬럼 암호화` `마스킹·비식별화` `DB 감사·DAM`

**한줄:** DB 보안은 접근통제(DAC·MAC·RBAC)+뷰로 볼 범위를 자르고, 암호화(TDE·컬럼·API)로 저장 데이터를 지키며, 감사 로그로 누가 무엇을 봤는지 남기는 3층 구조

**① 접근통제 — 누가 어디까지**

- **DAC (임의적 접근통제)**: **소유자**가 자기 데이터의 권한을 직접 준다. SQL의 **GRANT·REVOKE**가 바로 DAC. 유연하지만 권한이 퍼지기 쉬움

- **MAC (강제적 접근통제)**: 데이터에 **보안 등급**, 사용자에게 **인가 등급**을 매겨 **시스템이 강제**. 소유자도 못 바꾼다. 군·정부용

- **RBAC (역할 기반 접근통제)**: 권한을 **역할(ROLE)**에 주고 사람에게 역할을 부여. 인사이동에 강해 **기업에서 가장 현실적**

**② 뷰(View) · 다중 인스턴스화**

- **뷰(View)** — 원본 테이블에서 **필요한 행·열만 보이게 만든 가상 테이블**. 사용자에게 테이블 대신 뷰만 주면 **주민번호 컬럼은 아예 안 보인다** → 부적절한 접근 방지의 대표 수단
- **다중 인스턴스화(Polyinstantiation)** — 같은 키에 대해 **등급별로 서로 다른 내용**의 행을 여러 개 둔다. 낮은 등급 사용자는 위장된 값을 보게 되어 **추론·존재 자체의 노출을 차단**
- **분할(Partitioning)** — 민감한 데이터를 별도 테이블·DB로 떼어 놓아 집성을 어렵게 한다

**③ 암호화 방식 (적용 지점으로 구분)**

- **TDE (Transparent Data Encryption) — DBMS 내장**: DBMS가 저장 파일 단위로 **알아서** 암·복호화. **응용 프로그램 수정이 거의 없다**(투명). 단, 정상 권한으로 접속한 사람에게는 평문으로 보임

- **API(플러그인) 방식 — 응용 프로그램에서**: 애플리케이션이 암호화 모듈을 호출해 넣고 뺀다. **보안은 강하나 소스 수정이 필요**

- **게이트웨이(어플라이언스) 방식**: DB 앞단 장비가 대신 암·복호화. DB 부하가 적음

- **일방향 해시** — **패스워드**는 복호화할 필요가 없으므로 **해시+솔트**로 저장(암호화 아님)
- **마스킹·비식별화** — 화면·개발/테스트용 데이터에서 `010-****-1234`처럼 가린다. 가명처리·총계처리·범주화
- **키 관리**가 실질적 관건 — 키를 DB 안에 같이 두면 암호화 의미가 사라진다

**④ 감사(Audit) · DB 접근제어 솔루션**

- **DB 감사 로그** — 접속 계정·시각·실행 SQL·결과 건수를 기록. **대량 SELECT·업무 외 시간 접속**이 유출 탐지의 핵심 지표
- **DAM(DB Activity Monitoring)** — 네트워크·에이전트로 DB 질의를 실시간 감시·차단
- **로그 보호** — 감사 로그를 **DBA도 못 지우게** 별도 서버로 분리 저장해야 의미가 있다
- **DB 방화벽** — 허용된 응용 서버·계정·SQL 패턴만 통과시켜 **SQL 인젝션·비인가 도구 접속** 차단
**[기본 대책]** 기본 계정·기본 포트 변경, 최소 권한, **주기적 패치**, 개발·운영 DB 분리, 백업본 암호화.

> **시험 한줄정리:** 접근통제 **DAC(GRANT·소유자)·MAC(등급·시스템 강제)·RBAC(역할)** / **뷰=볼 범위를 잘라 보여주는 가상 테이블**, **다중 인스턴스화=등급별 다른 행으로 추론 차단** / 암호화 **TDE(투명·앱 수정 최소)·API(강하나 소스 수정)·게이트웨이**, 패스워드는 **해시+솔트** / **감사 로그는 DBA도 못 지우게 분리 보관**

_관련 개념: dbthreat · sqlcmd · dbbackup_

## 데이터베이스 백업과 회복 — Database Backup & Recovery

`애플리케이션 보안`  `전체·차등·증분` `핫 백업 vs 콜드 백업` `REDO·UNDO` `RTO·RPO` `3-2-1 규칙`

**한줄:** 백업은 범위로 전체·차등·증분, 서비스 중단 여부로 핫·콜드로 나뉜다 / 회복은 로그를 이용해 완료된 트랜잭션은 REDO, 미완료는 UNDO / 목표치는 RTO(얼마나 빨리)·RPO(얼마나 최근까지)

**범위에 따른 백업 3종 (비교 문제 단골)**

- **전체 백업 (Full)**: 매번 **전부** 복사. 백업은 가장 느리고 용량이 크지만 **복구가 가장 단순·빠름**(전체본 1개만 필요)

- **차등 백업 (Differential)**: **마지막 전체 백업 이후** 변경분을 매번 누적해 복사. 복구 = **전체 1개 + 최신 차등 1개**

- **증분 백업 (Incremental)**: **마지막 백업(어떤 것이든) 이후** 변경분만. **백업이 가장 빠르고 작지만**, 복구 = **전체 1개 + 그 뒤 증분 전부**라 가장 느리고 하나만 손상돼도 위험

**[한 줄 정리]** **증분=백업이 편하고 복구가 고생**, **차등=백업이 무겁고 복구가 편함**. 기준점이 **전체 백업(차등)**이냐 **직전 백업(증분)**이냐가 갈림길.

**운영 방식·대상에 따른 구분**

- **콜드 백업 (Cold / 오프라인)**: DB를 **정지**시키고 복사. 일관성이 완벽하나 **서비스 중단** 필요

- **핫 백업 (Hot / 온라인)**: DB를 **가동한 채** 백업. 중단이 없어 실무 표준이지만 **로그(아카이브)와 함께**해야 일관성이 맞는다

- **물리 백업** — 데이터 파일·로그 파일을 통째로 복사. 빠르고 대용량에 적합
- **논리 백업** — `mysqldump`·Oracle `expdp`처럼 **SQL 문/논리 단위**로 추출. 이식성이 좋으나 느림
- **3-2-1 규칙** — 사본 **3**개, 서로 다른 매체 **2**종, **1**개는 **물리적으로 떨어진 곳**(랜섬웨어 대비 오프라인 사본 필수)
- **복구 훈련** — 백업은 **복원 테스트를 해봐야** 백업이다. 무결성 검증·주기적 리허설

**회복(Recovery) 기법 — REDO · UNDO**

DBMS는 모든 변경을 **로그(저널)**에 먼저 적고 데이터에 반영한다.
- **REDO(재실행)** — **COMMIT까지 끝난** 트랜잭션인데 디스크에 반영이 안 됐으면 **다시 실행**해 반영 → 지속성 보장
- **UNDO(취소)** — **COMMIT 못 하고 중단된** 트랜잭션은 **되돌려** 없던 일로 → 원자성 보장
- **체크포인트(Checkpoint)** — 특정 시점 상태를 저장해 두어 회복 시 **거기서부터만** 검사 → 복구 시간 단축
- **그림자 페이징(Shadow Paging)** — 원본 페이지를 남겨 두고 사본에 작업, 실패 시 원본으로 되돌림
- **미디어 회복** — 디스크 자체가 깨지면 **백업본 복원 + 이후 로그 REDO**

**가용성 지표와 이중화**

- **RTO(Recovery Time Objective)** — **얼마나 빨리** 복구할 것인가(목표 복구 **시간**)
- **RPO(Recovery Point Objective)** — **얼마나 최근 시점까지** 살릴 것인가(허용 가능한 **데이터 손실량**). RPO 0에 가까우려면 실시간 이중화가 필요
- **RAID** — 디스크 장애 대비(1=미러링, 5=패리티 분산). **RAID는 백업이 아니다** — 실수로 지운 데이터는 그대로 지워진다
- **이중화** — 스탠바이 DB·클러스터·원격지 **DRS(재해복구시스템, Mirror·Hot·Warm·Cold Site)**

> **시험 한줄정리:** **전체·차등(전체 이후 누적)·증분(직전 이후만)** — **증분=백업 빠르고 복구 느림** / **콜드=정지 후, 핫=가동 중**, 논리(`mysqldump`)·물리 / 회복=로그로 **완료 트랜잭션 REDO · 미완료 UNDO** + **체크포인트** / **RTO=복구 시간 · RPO=손실 허용 시점**, **RAID는 백업이 아니다**

_관련 개념: dbsecway · db · netsep_
