## FTP 개요 · 종류 · 액티브/패시브 모드 — File Transfer Protocol

`애플리케이션 보안`  `21=제어·20=데이터` `제어·데이터 채널 분리` `액티브=서버가 연결` `패시브=클라이언트가 연결` `ftpusers=접속 금지 목록`

**한줄:** 파일 전송 프로토콜(제어 21·데이터 20, 채널 분리) / 액티브=서버가 데이터 연결을 걺, 패시브=클라이언트가 걺 / 접근통제는 /etc/ftpusers

**정의 · 채널 분리**

**FTP(File Transfer Protocol)** — 파일을 주고받는 프로토콜. **제어 채널과 데이터 채널을 따로** 쓰는 것이 가장 큰 특징이다.
- **21번 — 제어(명령) 채널**: 로그인·명령을 주고받으며 세션 내내 유지
- **20번 — 데이터 채널**: 실제 파일 전송용(액티브 모드에서 사용)

**액티브 vs 패시브 모드 (최다 출제)**

- **액티브 모드 (Active)**: 데이터 연결을 **서버가 클라이언트에게** 건다(서버 **20번** → 클라이언트).
➖ 클라이언트 **방화벽이 들어오는 연결을 막으면 전송 실패**. 요즘 환경에서 잘 안 되는 이유.

- **패시브 모드 (Passive)**: 서버가 **열어둔 포트 번호를 알려주면** 데이터 연결도 **클라이언트가 서버에게** 건다.
➕ 클라이언트 방화벽 문제가 없다
➖ 서버가 **여러 포트를 열어둬야** 해 서버 쪽 부담·노출이 커진다.

**[구분 요령]** “**누가 데이터 연결을 먼저 거는가**” — **액티브=서버가 능동적(Active)**으로 건다, **패시브=서버가 가만히(Passive) 기다리고 클라이언트가** 건다.

**FTP 종류**

- **일반 FTP** — 계정·비밀번호로 인증(단, **평문**)
- **익명 FTP(Anonymous FTP)** — 계정 `anonymous`로 **누구나 접속**, 비밀번호는 관례상 이메일. 공개 자료 배포용이지만 **설정을 잘못하면 매우 위험**
- **TFTP(Trivial FTP)** — **UDP 69**, 매우 단순. **인증 자체가 없다** → 네트워크 장비 부팅용 등 제한적으로만
- **SFTP**(SSH 기반, 22) · **FTPS**(SSL/TLS) — **암호화되는 안전한 대체재**

**접근 통제 파일**

- **`/etc/ftpusers`** — **여기 적힌 사용자는 FTP 접속이 '금지'**된다. 이름만 보면 허용 목록 같아서 **반대로 아는 함정**이 자주 나온다. **root를 반드시 등록**해 원격 FTP 로그인을 막는다
- `/etc/ftpaccess` — 접속 수·전송·디렉터리 등 **상세 접근 제어**
- `/etc/ftphosts` — **호스트(IP) 기반** 허용·거부

> **시험 한줄정리:** FTP=**제어 21 · 데이터 20**(채널 분리) / **액티브=서버가 데이터 연결을 걺(클라 방화벽에 막힘)** vs **패시브=클라이언트가 걺(서버 포트 많이 열림)** / 종류 일반·**익명**·**TFTP(UDP 69·인증 없음)**·SFTP·FTPS / **`/etc/ftpusers`=접속 금지 목록(root 등록)**

_관련 개념: ftpsec · translayer · remoteattack_

## FTP 보안 취약점 · 로그 · 대책 — FTP Security

`애플리케이션 보안`  `평문 전송` `익명 FTP 오설정` `FTP 바운스 공격` `xferlog` `SFTP·FTPS·chroot`

**한줄:** 평문이라 ID·비밀번호가 그대로 노출 / 익명 FTP 오설정과 FTP 바운스 공격이 대표 취약점 / 전송 기록은 xferlog / 대책=SFTP·FTPS·익명 차단·chroot

**취약점**

- **평문 전송** — **ID·비밀번호와 파일 내용이 모두 평문**이라 스니핑 한 번이면 계정이 넘어간다(가장 근본적인 문제)
- **익명 FTP 오설정** — 익명 계정에 **쓰기 권한**이 있으면 공격자가 **웹셸·악성코드를 업로드**하고, 홈 디렉터리 제한이 없으면 **상위 디렉터리로 이동**해 시스템 파일에 접근한다
- **무차별 대입** — 인터넷에 열린 FTP는 자동화 봇의 표적

**FTP 바운스 공격 (Bounce Attack)**

FTP가 **데이터를 보낼 주소를 클라이언트가 지정**할 수 있다는 점(**PORT 명령**)을 악용한다. 공격자가 **제3의 시스템 주소**를 지정하면, **FTP 서버가 대신 그쪽으로 접속**하게 된다.**[왜 위험한가]** 공격의 **출발지가 FTP 서버**가 되므로 **추적을 회피**할 수 있고, 그 서버를 **포트 스캔의 경유지**로 쓰거나 **방화벽 내부**를 스캔할 수 있다.
**대응**: FTP 서버에서 **PORT 명령의 목적지를 접속한 클라이언트로 제한**(요즘 서버는 기본 차단).

**로그 기록**

**`xferlog`**(보통 `/var/log/xferlog`) — FTP의 **파일 전송 기록**이다. **언제·누가·어떤 파일을·어느 방향으로(업로드/다운로드)·성공했는지**가 남아 침해 조사의 핵심 증거가 된다.
접속·인증 실패 기록은 `/var/log/secure`(또는 `messages`)에서 함께 본다.

**보안 대책**

- **SFTP(SSH·22) 또는 FTPS(SSL/TLS)로 대체** — 평문 문제를 근본적으로 해결(1순위)
- **익명 FTP 비활성화**. 꼭 필요하면 **읽기 전용**으로만
- **`/etc/ftpusers`에 root·시스템 계정 등록**해 접속 차단
- **chroot로 홈 디렉터리에 가둬** 상위 이동 차단
- 업로드 디렉터리는 **실행 권한 제거**, 쓰기와 읽기 분리
- 접속 IP 제한, 시도 횟수 제한, **`xferlog` 정기 점검**

> **시험 한줄정리:** FTP 취약점=**평문**·**익명 FTP 오설정(업로드·상위이동)**·무차별 대입·**바운스 공격(PORT 명령으로 제3자 경유 → 추적 회피·스캔)** / 전송 로그=**`xferlog`** / 대책=**SFTP·FTPS**·익명 차단·**ftpusers**·**chroot**

_관련 개념: ftp · sniffing · portscan_

## 메일 보안 프로토콜 (PGP · PEM · S/MIME) — PGP · PEM · S/MIME

`애플리케이션 보안`  `PGP=분산·신뢰의 웹` `PEM=중앙집중·복잡` `S/MIME=X.509·상용 표준` `기밀성·무결성·인증·부인방지` `MIME 확장`

**한줄:** 메일 본문 자체를 암호화·서명하는 기술 / PGP=분산(신뢰의 웹)·쉬움, PEM=중앙집중·이론상 최강이나 복잡, S/MIME=X.509 인증서 기반 상용 표준

**왜 필요한가**

SMTP는 **평문**이고 **발신자를 검증하지 않는다**. 전송 구간 암호화(STARTTLS)만으로는 **메일 서버에 저장된 내용**이나 **중간 서버**를 신뢰해야 한다. 그래서 **메일 내용 자체를 종단 간(End-to-End)으로 보호**하는 기술이 필요하다.
제공 기능: **기밀성(암호화) · 무결성 · 인증(전자서명) · 부인방지**.

**세 가지 비교 (표째로 출제)**

- **PGP (Pretty Good Privacy)**: 필 짐머만 제작. **분산형 신뢰 모델** — 중앙 CA 없이 **사용자끼리 서로의 공개키에 서명**해 신뢰를 쌓는다(**신뢰의 웹, Web of Trust**).
➕ **구현·사용이 쉽고** 무료라 널리 퍼졌다

- **PEM (Privacy Enhanced Mail)**: IETF 표준. **계층적 CA에 의존하는 중앙집중식** 구조.
➕ **보안성은 가장 높다**고 평가
➖ **구현이 복잡**해 실제로는 거의 쓰이지 않는다

- **S/MIME (Secure/MIME)**: MIME에 보안 기능을 더한 것. **X.509 인증서**와 **CA**를 사용한다.
➕ **아웃룩 등 상용 메일 프로그램에 기본 내장**돼 기업에서 널리 사용

**구분 포인트**

- **신뢰 모델**이 갈림점이다 — **PGP=분산(신뢰의 웹)** vs **PEM·S/MIME=중앙 CA**
- **PEM은 '가장 안전하지만 복잡해 안 쓰인다'**가 정답 포인트
- **S/MIME은 X.509 인증서**를 쓴다는 점이 자주 나온다
- 이들은 **본문 보호**이고, **SPF·DKIM·DMARC는 발신 도메인 위조 차단**으로 역할이 다르다(혼동 주의)

> **시험 한줄정리:** 메일 본문 종단 간 보호(기밀성·무결성·인증·부인방지) / **PGP=분산·신뢰의 웹·쉬움** · **PEM=중앙집중 CA·최고 보안이나 복잡해 미사용** · **S/MIME=X.509 인증서·상용 표준** / 발신자 위조 차단은 **SPF·DKIM·DMARC**로 역할이 다름

_관련 개념: sendmail · smtp · mailattack_

## sendmail · 스팸 차단 · SpamAssassin — sendmail · Anti-Spam · SpamAssassin

`애플리케이션 보안`  `대표 MTA` `sendmail.cf 설정` `access=릴레이 제어` `aliases·newaliases` `SpamAssassin=점수 합산`

**한줄:** sendmail=대표적인 유닉스 MTA / 릴레이 제어는 /etc/mail/access, 별칭은 /etc/aliases / 스팸 차단=RBL·베이지안·그레이리스팅·SpamAssassin(점수 합산)

**sendmail — 정의 · 운영 모드**

유닉스의 대표적인 **MTA(Mail Transfer Agent, 메일 전송 서버)**. 오래된 만큼 기능이 많지만 **설정이 복잡하고 과거 취약점이 많았다**.** 주요 실행 모드**
- **`-bd`** — **데몬 모드**. 백그라운드에서 메일 **수신 대기**(가장 기본)
- **`-q`** — **큐 처리**. 전송 대기 중인 메일을 주기적으로 재시도(예: `-q30m`)
- **`-bp`** — **메일 큐 확인**(`mailq`와 동일)
- **`-bt`** — 주소 재작성 규칙 **테스트 모드**
보통 `sendmail -bd -q30m` 형태로 **수신 대기 + 30분마다 큐 처리**를 함께 띄운다.

**주요 설정·접근 파일**

- **`/etc/mail/sendmail.cf`** — 핵심 설정 파일(직접 편집이 어려워 `.mc`로 생성)
- **`/etc/mail/access`** — **접근·릴레이 제어의 핵심**. 도메인·IP별로 **`RELAY`(중계 허용) · `OK`(수신 허용) · `REJECT`(거부) · `DISCARD`(조용히 폐기)**를 지정한다 → **오픈 릴레이를 막는 파일**. 수정 후 `makemap`으로 DB 갱신
- **`/etc/aliases`** — 메일 **별칭**(예: `admin` → 실제 담당자들). 수정 후 반드시 **`newaliases`** 실행
- `/etc/mail/local-host-names` — 이 서버가 받아줄 도메인 목록

**스팸 차단 방법**

- **릴레이 제한** — `access`로 **오픈 릴레이 차단**(가장 기본)
- **RBL/DNSBL** — 스팸 발송으로 등록된 **IP 블랙리스트를 실시간 조회**해 거부
- **발신자 인증** — **SPF·DKIM·DMARC**로 도메인 위조 메일 차단
- **내용 필터링** — **베이지안 필터** 등 통계 학습으로 스팸 문구 판별
- **그레이리스팅(Greylisting)** — 처음 보는 발신자의 메일을 **일단 임시 거부**하고, **정상 서버라면 재시도**하므로 그때 받아준다. **스팸 봇은 재시도하지 않는** 성질을 이용

**SpamAssassin**

대표적인 **오픈소스 스팸 필터**. 동작 방식이 특징적이다.**[점수 합산 방식]** 하나의 규칙으로 판단하지 않고, **헤더·본문 규칙 · 베이지안 학습 · RBL 조회** 등 **수많은 검사에 각각 점수를 매겨 합산**한다. 그 **총점이 임계치를 넘으면 스팸**으로 판정 → 단일 조건보다 **오탐이 적고 유연**하다.

> **시험 한줄정리:** sendmail=대표 **MTA**, 모드 **`-bd`(데몬)·`-q`(큐)·`-bp`(큐확인)·`-bt`(테스트)** / **`/etc/mail/access`=릴레이 제어(RELAY·OK·REJECT·DISCARD)** · **`/etc/aliases`+`newaliases`** / 스팸=릴레이제한·**RBL**·SPF/DKIM/DMARC·베이지안·**그레이리스팅** / **SpamAssassin=규칙별 점수 합산**

_관련 개념: mailsec · smtp · mailattack_

## 웹 서버 보안 (아파치 · 웹 로그 · WAF) — Apache Hardening · Web Log · WAF

`애플리케이션 보안`  `Options -Indexes` `ServerTokens Prod` `access_log·error_log` `CLF 형식` `WAF=7계층`

**한줄:** 아파치 보안설정=디렉터리 리스팅 차단·버전 숨김·전용계정 실행 / 로그는 access_log·error_log(CLF) / 일반 방화벽은 80·443을 못 막으므로 WAF가 필요

**아파치 주요 보안 설정 (httpd.conf)**

- **`Options -Indexes`** — **디렉터리 리스팅 차단**. 인덱스 파일이 없을 때 **파일 목록이 그대로 노출**되는 것을 막는다(가장 대표적인 설정)
- **`ServerTokens Prod` · `ServerSignature Off`** — 응답 헤더·오류 페이지의 **웹서버 종류·버전 노출 차단**(정찰 방지)
- **`Options -FollowSymLinks`** — **심볼릭 링크를 따라가지 못하게** 해 외부 파일 접근 차단
- **`AllowOverride None`** — `.htaccess` 비활성화(성능·설정 우회 방지)
- **전용 계정으로 실행** — `User/Group`을 **nobody·apache 등 비특권 계정**으로. **root로 실행 금지**
- **불필요한 모듈 제거**, **`LimitRequestBody`**로 업로드 크기 제한, 디렉터리별 접근 제어

**웹 로그**

- **`access_log`** — **모든 접근 기록**(누가 무엇을 요청했고 결과가 무엇인지)
- **`error_log`** — 오류·경고 기록
**CLF(Common Log Format)** 구조:

```
호스트(IP)  identd  사용자  [시간]  "요청줄"  상태코드  전송크기
```

**[로그로 공격 찾기]** **404가 대량**이면 **스캐닝**, 요청줄에 `' OR 1=1`·`<script>`·`../`가 보이면 **SQL 인젝션·XSS·디렉터리 트래버설** 시도다. **상태코드와 요청줄**을 함께 보는 것이 핵심.

**웹 방화벽 (WAF)**

**왜 필요한가** — 일반 방화벽은 **3·4계층**이라 웹 서비스를 하려면 **80·443을 열어둘 수밖에 없다**. 그 열린 문으로 들어오는 **정상적인 HTTP 요청 안에** 공격이 숨어 있으면 못 막는다.
- **7계층에서 HTTP 요청·응답의 내용을 검사**해 **SQL 인젝션·XSS·파일 업로드·디렉터리 트래버설** 등 웹 공격을 차단
- 탐지 방식: **블랙리스트(시그니처 기반)** — 알려진 공격 패턴 차단 / **화이트리스트(포지티브)** — 허용된 형식만 통과(더 안전하나 설정 부담)
- 응답 검사로 **개인정보·오류 메시지 노출 차단**도 가능

> **시험 한줄정리:** 아파치=**`Options -Indexes`(리스팅 차단)**·**`ServerTokens Prod`(버전 숨김)**·`-FollowSymLinks`·**비특권 계정 실행** / 로그 **`access_log`·`error_log`**, **CLF**(IP·시간·요청·상태코드·크기), **404 대량=스캐닝** / **WAF=7계층에서 HTTP 내용 검사**(방화벽은 80·443을 못 막음)

_관련 개념: dns · httpheader · firewall_

## DNS 구조 · 보안 · DNSSEC — DNS · DNSSEC

`애플리케이션 보안`  `UDP 53 질의·TCP 53 존전송` `재귀 vs 반복 질의` `A·MX·CNAME·NS·PTR` `캐시 포이즈닝` `DNSSEC=서명(암호화 아님)`

**한줄:** 도메인↔IP 변환(UDP 53 질의·TCP 53 존 전송) / 재귀 질의 vs 반복 질의 / 위협=캐시 포이즈닝·존 전송 유출·증폭 DDoS / DNSSEC=전자서명으로 위조 방지(암호화 아님)

**정의 · 계층 구조**

**DNS(Domain Name System)** — 사람이 쓰는 **도메인 이름을 IP 주소로 변환**하는 분산 데이터베이스.
- 구조: **루트(.) → TLD(.com·.kr) → 2차 도메인 → 호스트**의 **계층(트리)**
- 구성 요소: **리졸버**(질의하는 클라이언트 측) · **네임서버**(권한 있는 서버 / 캐싱 서버)
- 포트: **UDP 53 = 일반 질의**(빠르게), **TCP 53 = 존 전송·응답이 클 때**

**서비스 방식 · 주요 레코드**

- **재귀 질의 (Recursive)**: 클라이언트가 로컬 DNS에게 “**끝까지 알아봐서 답만 줘**”라고 맡기는 방식.

- **반복 질의 (Iterative)**: 로컬 DNS가 **루트 → TLD → 권한 서버**로 **차례차례 직접 물어보는** 방식.

**주요 레코드**: **A**(도메인→IPv4) · **AAAA**(IPv6) · **MX**(메일 서버) · **CNAME**(별칭) · **NS**(네임서버) · **PTR**(IP→도메인, 역방향) · SOA(존 정보)

**DNS 보안 위협**

- **DNS 스푸핑 · 캐시 포이즈닝** — **위조 응답을 진짜보다 먼저** 보내 캐시를 오염시킨다 → 사용자가 **정상 주소를 입력해도 피싱 사이트로** 간다. UDP라 응답 위조가 쉽다(**가장 대표적인 DNS 공격**)
- **존 전송(Zone Transfer) 취약** — 아무나 **AXFR**로 요청하면 **도메인 전체 목록**이 넘어가 **내부 서버 구조가 통째로 노출**된다 → 정찰의 노다지
- **DNS 증폭 DDoS** — 작은 질의에 **큰 응답**이 오는 성질 + 출발지 위조로 피해자를 폭격
- **DNS 터널링** — DNS 질의·응답에 **데이터를 숨겨** 방화벽을 우회해 유출·C2 통신

**DNSSEC · 대응**

**DNSSEC(DNS Security Extensions)** — DNS 응답에 **전자서명**을 붙여, 받은 쪽이 **진짜 권한 서버가 보낸 것이고 변조되지 않았음을 검증**한다(루트부터 이어지는 **신뢰 체인**).**[시험 함정]** **DNSSEC은 암호화가 아니다** — **무결성·출처 인증**만 제공하고 **기밀성은 제공하지 않는다**(내용은 그대로 보인다). 목적은 **캐시 포이즈닝 방지**.
**그 밖의 대응**: **존 전송을 허용된 세컨더리 서버로만** 제한 · 재귀 질의를 **내부 사용자에게만** 허용(외부 개방 금지 → 증폭 DDoS 차단) · 최신 패치 · 질의 ID·포트 랜덤화.

> **시험 한줄정리:** DNS=도메인↔IP(**UDP 53 질의 · TCP 53 존전송**), 계층 루트→TLD→도메인 / **재귀=대신 끝까지** vs **반복=차례로 직접** / 레코드 **A·AAAA·MX·CNAME·NS·PTR** / 위협 **캐시 포이즈닝·존 전송 유출·증폭 DDoS·터널링** / **DNSSEC=전자서명으로 위조 방지, 암호화는 아님**

_관련 개념: websec · netproto · dos_
