# 애플리케이션·웹 보안

> 자동 생성 — 원본은 `cards/webapp.js`. 직접 수정 금지.

## OAuth 2.0 — Open Authorization

`애플리케이션 보안`  `인가(위임)≠인증` `Access·Refresh 토큰` `Authorization Code` `4주체` `OIDC=인증`

**한줄:** 비밀번호를 주지 않고 제3자 앱에 제한된 권한만 위임하는 인가 프로토콜 / 인증(OIDC)과 구분 / Access·Refresh 토큰

**정의**

**OAuth = Open Authorization(개방형 인가)**. 사용자가 자신의 **비밀번호를 제3자 앱에 넘기지 않고**, 특정 자원에 대한 **제한된 권한만 위임**하도록 해 주는 표준이다. 예를 들어 어떤 앱이 내 구글 사진에 접근할 때, 그 앱은 내 구글 **비밀번호를 전혀 모른 채** 발급받은 **토큰**으로만 접근한다.

**인가 ≠ 인증 (최대 함정)**

OAuth는 **'무엇을 할 수 있는지(권한)'를 넘겨주는 인가(Authorization)** 프로토콜이지, **'네가 누구인지 확인하는 인증(Authentication)'이 아니다.** 로그인처럼 **신원 확인**까지 하려면 OAuth 위에 얹은 **OpenID Connect(OIDC)**를 쓴다.**[단골 함정]** 'OAuth는 인증 프로토콜이다' → **❌ 인가**. 인증이 필요하면 **OIDC**. OIDC는 인가서버가 **ID 토큰**을 추가로 발급해 신원을 증명한다.

**4주체 (역할 구분)**

누가 무엇을 하는지 넷으로 나눈다.
- **자원 소유자 (Resource Owner)**: 권한을 가진 **사용자 본인**.

- **클라이언트 (Client)**: 권한을 **위임받으려는 제3자 앱**.

- **인가 서버 (Authorization Server)**: 사용자를 확인하고 **토큰을 발급**(예: 구글 계정 서버).

- **자원 서버 (Resource Server)**: 실제 자원을 가진 서버. **토큰을 검증**하고 자원을 내준다(예: 구글 사진 API).

**권한 부여 흐름 — Authorization Code (대표·가장 안전)**

- **① 인가 요청** — 앱이 사용자를 인가 서버로 보내 로그인·동의를 받음.

- **② 인가 코드** — 동의하면 인가 서버가 임시 Authorization Code 발급.

- **③ 토큰 교환** — 앱이 뒤에서 그 코드를 Access Token으로 교환.

- **④ 자원 접근** — Access Token으로 자원 서버에 접근.

**[참고]** 코드를 한 번 거치므로 토큰이 브라우저에 노출되지 않는다. 구식 **Implicit** 방식은 토큰을 곧바로 노출해 취약 → 폐기 추세. 그 외 Client Credentials(서버 간)·Resource Owner Password(비권장)도 있다.

**토큰 2종**

- **Access Token(액세스 토큰)** — 자원 접근용 열쇠. **수명이 짧다**(탈취돼도 피해 최소화).
- **Refresh Token(리프레시 토큰)** — Access Token이 만료되면 **다시 발급받는** 재발급용. 수명이 길어 **안전하게 보관**해야 한다.

**보안 주의점**

**redirect_uri**(응답 받을 주소)를 정확히 **검증**해 열린 리다이렉트로 코드·토큰이 새는 것을 막는다. **state 파라미터**로 **CSRF**를 방지하고, 요청 권한은 꼭 필요한 **scope**만 최소로. 최신 권장은 **Authorization Code + PKCE** 조합, 모든 통신은 **HTTPS**.

> **시험 한줄정리:** OAuth 2.0 = 비밀번호 없이 **제한된 권한만 위임하는 인가**(≠인증, 인증은 **OIDC**) / 4주체(소유자·클라이언트·인가서버·자원서버) / **Authorization Code**로 Access·Refresh 토큰

_관련 개념: kerberos · winauth_
