# 네트워크 활용(TCP/IP) — 전송 계층

> 자동 생성 — 원본은 `cards/translayer.js`. 직접 수정 금지.

## 전송 계층 · 세그먼트 · 포트 — Transport Layer · Segment · Port

`네트워크 보안`  `PDU=세그먼트` `포트로 프로세스 구분` `well-known 0~1023` `흐름·혼잡 제어` `주요 포트 암기`

**한줄:** 종단 간(end-to-end) 전달을 책임지는 4계층 / PDU=세그먼트 / 포트 번호로 프로세스를 구분(0~1023 well-known)

**역할 · 세그먼트**

3계층(IP)이 **호스트까지** 데이터를 보내준다면, 전송 계층은 **그 안의 어느 프로그램에게** 줄지까지 책임진다(**종단 간·end-to-end**).
- **세그먼트(Segment)** — 전송 계층의 **PDU**. 상위 데이터를 **전송 가능한 크기로 쪼개고** TCP 헤더를 붙인 단위(UDP는 **데이터그램**이라 부른다)
- **포트 번호** — 같은 컴퓨터 안의 **프로세스를 구분**하는 번호. IP=집 주소, **포트=몇 호**
- **신뢰성·흐름 제어·혼잡 제어**(TCP만) — 순서 보장, 재전송, 속도 조절

**포트 번호 범위 (시험 단골)**

- **0 ~ 1023 — 잘 알려진 포트(Well-known)**: 표준 서비스용. 서버가 사용
- **1024 ~ 49151 — 등록 포트(Registered)**: 특정 업체·응용에 등록
- **49152 ~ 65535 — 동적/사설 포트(Dynamic)**: 클라이언트가 접속할 때마다 **임시로** 받는 번호
포트는 **16비트**라 **0~65535**까지 존재한다.

**주요 포트 (그대로 출제)**

- **20/21 FTP**(20=데이터, 21=제어) · **22 SSH** · **23 Telnet** · **25 SMTP**
- **53 DNS**(질의 UDP·존 전송 TCP) · **67/68 DHCP** · **69 TFTP**(UDP)
- **80 HTTP** · **110 POP3** · **143 IMAP** · **161/162 SNMP** · **389 LDAP**
- **443 HTTPS** · **445 SMB** · **514 syslog** · **3306 MySQL** · **3389 RDP**
**UDP를 쓰는 대표**: DNS(질의)·DHCP·TFTP·SNMP·syslog. **암기 짝**: 22 SSH ↔ 23 Telnet(평문), 80 HTTP ↔ 443 HTTPS.

**보안 관점**

열린 포트는 곧 **공격 표면**이다. **포트 스캔**(nmap)으로 어떤 서비스가 도는지 파악하는 것이 침투의 첫 단계이므로, **불필요한 포트·서비스를 닫고** 방화벽에서 **필요한 것만 허용**한다. 확인은 `netstat -an`·`ss -tuln`.

> **시험 한줄정리:** 전송 계층=**종단 간** 전달, PDU=**세그먼트**, **포트로 프로세스 구분**(16비트, 0~65535) / **0~1023 well-known · 1024~49151 등록 · 49152~ 동적** / 22 SSH·23 Telnet·25 SMTP·53 DNS·80 HTTP·443 HTTPS·161 SNMP

_관련 개념: tcpheader · udpheader · tcpudp_

## TCP 헤더 구조 — TCP Header

`네트워크 보안`  `기본 20바이트` `순서번호·확인응답번호` `플래그 6종` `윈도우=흐름제어` `옵션 가변`

**한줄:** 기본 20바이트 / 포트(각16bit)·순서번호(32)·확인응답번호(32)·헤더길이·플래그6·윈도우크기·체크섬·긴급포인터·옵션

**필드 (순서대로)**

- **출발지 포트 / 목적지 포트** — 각 **16비트**
- **순서 번호(Sequence Number, 32비트)** — 이 세그먼트 데이터의 **첫 바이트 번호**. **순서 보장·재조립**에 사용
- **확인 응답 번호(Acknowledgment Number, 32비트)** — **다음에 받기를 기대하는** 바이트 번호(여기까지 잘 받았다는 뜻)
- **데이터 오프셋(헤더 길이, 4비트)** — 헤더가 몇 워드인지(옵션 때문에 가변)
- **예약(Reserved)** — 미사용
- **제어 플래그(6비트)** — **URG·ACK·PSH·RST·SYN·FIN**
- **윈도우 크기(16비트)** — 한 번에 받을 수 있는 양 → **흐름 제어**
- **체크섬(16비트)** — 오류 검출 · **긴급 포인터** — URG와 함께 사용
- **옵션(가변)** — MSS·윈도우 스케일 등
**기본 크기 20바이트**(옵션 없을 때). UDP(8바이트)와의 대비가 자주 나온다.

**순서번호 · 확인응답번호가 하는 일**

TCP가 **신뢰성**을 갖는 근거다. 보낸 쪽은 **순서 번호**로 조각에 번호를 매기고, 받은 쪽은 **확인 응답 번호**로 '여기까지 받았다'를 알린다. **ACK가 안 오면 재전송**하고, 도착 순서가 뒤바뀌어도 **번호로 재조립**한다.

**보안 — 헤더를 노리는 공격**

- **세션 하이재킹** — **순서 번호를 예측**해 정상 연결에 끼어든다 → 대응은 **초기 순서번호(ISN) 난수화**
- **플래그 조작 스캔** — SYN·FIN·NULL·XMAS 스캔으로 **방화벽·IDS 우회**를 시도
- **RST 공격** — 위조한 RST로 **연결을 강제 종료**시킨다

> **시험 한줄정리:** TCP 헤더 **기본 20바이트** — 포트(16×2)·**순서번호(32)**·**확인응답번호(32)**·헤더길이·**플래그 6(URG·ACK·PSH·RST·SYN·FIN)**·**윈도우(흐름제어)**·체크섬·긴급포인터·옵션 / 순서번호 예측=**세션 하이재킹**

_관련 개념: tcpstate · udpheader · tcpudp_

## 3-way Handshake · TCP 연결 상태 — 3-way Handshake · TCP States

`네트워크 보안`  `SYN→SYN+ACK→ACK` `4-way 종료` `LISTEN·ESTABLISHED` `TIME_WAIT·CLOSE_WAIT` `netstat -an`

**한줄:** 연결 수립=3-way(SYN→SYN+ACK→ACK), 종료=4-way(FIN→ACK→FIN→ACK) / 상태는 netstat으로 확인(SYN_RECEIVED 폭증=SYN 플러딩)

**3-way handshake — 왜 3번인가**

- **1 SYN** — 클라이언트: '연결하자' + **내 순서번호** 알림

- **2 SYN+ACK** — 서버: '알겠다'(ACK) + **내 순서번호도** 알림(SYN)

- **3 ACK** — 클라이언트: '확인' → **양쪽 모두** 준비 완료

**양방향** 통신이라 **서로의 순서번호를 교환·확인**해야 해서 3번이 필요하다. 종료가 **4-way**인 이유는, 한쪽이 끝나도 **반대 방향은 남아 있을 수 있어** 각자 따로 닫기 때문이다(FIN → ACK → FIN → ACK).

**주요 연결 상태 (netstat으로 확인)**

- **LISTEN** — 서버가 **연결을 기다리는** 중(포트 열림)
- **SYN_SENT** — 클라이언트가 SYN을 보내고 응답 대기
- **SYN_RECEIVED** — SYN을 받고 **마지막 ACK를 기다리는** 중
- **ESTABLISHED** — **연결 완료**, 데이터 송수신 중
- **FIN_WAIT_1 / FIN_WAIT_2** — 내가 먼저 종료 요청한 뒤
- **CLOSE_WAIT** — **상대가 끊자고 했고 내가 닫기를 기다리는** 상태
- **TIME_WAIT** — 마지막 ACK를 보낸 뒤 **일정 시간 대기**(지연 패킷 정리·ACK 유실 대비)
- **CLOSED** — 연결 없음
확인 명령: `netstat -an` · `netstat -ant`(TCP만) · `ss -tan`

**상태로 읽는 이상 징후 (실무·시험)**

- **SYN_RECEIVED가 대량** → **SYN 플러딩** 공격 징후(3-way의 마지막 ACK를 안 보내 **백로그 큐 고갈**)
- **CLOSE_WAIT가 계속 쌓임** → **애플리케이션이 소켓을 닫지 않는 버그**(자원 누수)
- **ESTABLISHED가 비정상적으로 많음** → 과부하 또는 **백도어·비인가 연결** 의심
**대응**: SYN 쿠키, 백로그 큐 확대, 타임아웃 단축, 방화벽·IPS.

> **시험 한줄정리:** 수립 **3-way(SYN→SYN+ACK→ACK)** — 양방향이라 순서번호를 서로 확인 / 종료 **4-way(FIN→ACK→FIN→ACK)** / 상태 **LISTEN·ESTABLISHED·TIME_WAIT·CLOSE_WAIT**, 확인은 `netstat -an` / **SYN_RECEIVED 폭증=SYN 플러딩**

_관련 개념: tcpheader · tcpudp · translayer_

## UDP 헤더 구조 — UDP Header

`네트워크 보안`  `8바이트 고정` `필드 4개뿐` `포트·길이·체크섬` `비연결·무보장` `출발지 위조 쉬움`

**한줄:** 8바이트 고정, 필드는 출발지 포트·목적지 포트·길이·체크섬 4개뿐 / 순서번호·확인응답·윈도우가 없어 신뢰성·제어 기능이 없음

**필드 4개가 전부**

- **출발지 포트(16비트)** · **목적지 포트(16비트)**
- **길이(16비트)** — 헤더+데이터 전체 길이
- **체크섬(16비트)** — 오류 검출(선택적)
**총 8바이트 고정.** TCP의 20바이트와 비교해 **훨씬 가볍다**.

**TCP 헤더에 있고 UDP엔 없는 것 (이게 곧 특징)**

**순서 번호 · 확인 응답 번호 · 제어 플래그 · 윈도우 크기**가 **전부 없다**.**[그래서]** 순서 보장·재전송·흐름 제어·혼잡 제어가 **불가능**하다 = **비신뢰성**. 대신 **헤더가 작고 연결 절차가 없어 빠르다** → **DNS·DHCP·SNMP·TFTP·실시간 스트리밍·VoIP**에 적합.

**보안 — 위조와 증폭**

연결 과정(핸드셰이크)이 없어 **출발지 IP를 위조하기 쉽다**. 이 성질 때문에 **UDP 기반 증폭 DDoS**(DNS·NTP·SNMP·memcached 증폭)에 악용된다 — 작은 요청에 **큰 응답**이 피해자에게 쏟아지게 만든다. 대응은 **출발지 검증(uRPF)**·불필요 UDP 서비스 차단·응답 속도 제한.

> **시험 한줄정리:** UDP 헤더 **8바이트 고정** — **출발지 포트·목적지 포트·길이·체크섬** 4개뿐 / 순서번호·ACK·윈도우가 **없어** 신뢰성·제어 불가(대신 빠름) / 핸드셰이크가 없어 **출발지 위조·증폭 DDoS**에 악용

_관련 개념: tcpheader · tcpudp · translayer_
