## OWASP Top 10 — Open Worldwide Application Security Project

`애플리케이션 보안`  `웹 취약점 10대 목록` `2021 1위=접근통제 취약` `인젝션은 3위로 하락` `설계 결함 신설` `SSRF`

**한줄:** OWASP=웹 애플리케이션 보안을 연구하는 비영리 단체 / Top 10은 3~4년마다 갱신되는 대표 취약점 목록으로, 2021년판 1위는 취약한 접근통제, 인젝션은 3위로 내려왔다

**OWASP과 Top 10**

**OWASP(Open Worldwide Application Security Project)** — 웹 애플리케이션 보안을 연구·공개하는 **비영리 오픈 커뮤니티**. 무료로 문서·도구를 배포한다(ZAP, ESAPI 등).
- **OWASP Top 10** — 실제 데이터를 모아 뽑은 **가장 위험한 웹 취약점 10가지**. **3~4년마다 갱신**(2013 · 2017 · **2021**)
- 표준이라기보다 **인식 제고용 문서**지만, 시험·실무 모두에서 사실상 기준으로 쓰인다

**OWASP Top 10 (2021) — 순위째로 출제**

- **A01 취약한 접근통제(Broken Access Control)** — **1위로 상승**. 권한 없이 남의 자원에 접근
- **A02 암호화 실패(Cryptographic Failures)** — 옛 "민감 데이터 노출". 평문 전송·약한 알고리즘
- **A03 인젝션(Injection)** — SQL·OS 명령·**XSS가 여기로 통합**. 1위→**3위로 하락**
- **A04 안전하지 않은 설계(Insecure Design)** — **2021 신설**. 구현이 아니라 **설계 자체의 결함**
- **A05 보안 설정 오류(Security Misconfiguration)** — 기본 계정·디렉터리 리스팅·불필요 기능
- **A06 취약하고 오래된 요소(Vulnerable and Outdated Components)** — 미패치 라이브러리
- **A07 식별 및 인증 실패** — 약한 패스워드, 세션 관리 미흡
- **A08 소프트웨어·데이터 무결성 실패** — **신설**. 안전하지 않은 역직렬화, **공급망 공격**
- **A09 보안 로깅·모니터링 실패** — 기록이 없어 침해를 못 알아챔
- **A10 SSRF(Server-Side Request Forgery)** — **신설**. 서버가 공격자가 지정한 곳으로 요청을 대신 보냄
**[변화 포인트]** **1위가 인젝션 → 접근통제**로 바뀌었고, **XSS는 인젝션(A03)에 흡수**됐으며, **설계 결함·무결성 실패·SSRF가 신설**됐다는 세 가지가 핵심.

> **시험 한줄정리:** OWASP=웹 보안 비영리 단체, Top 10은 **3~4년마다** 갱신 / 2021판 **1위=취약한 접근통제**, **2위 암호화 실패**, **3위 인젝션(XSS 흡수)**, 신설 **A04 안전하지 않은 설계 · A08 무결성 실패(공급망) · A10 SSRF**

_관련 개념: sdlc · sqli · xss_

## 소프트웨어 개발 보안 · SDLC · 시큐어 코딩 7대 유형 — Secure SDLC / Secure Coding

`애플리케이션 보안`  `요구분석→설계→구현→시험→유지보수` `앞단계일수록 비용 저렴` `7대 보안약점 유형` `CWE·CVE` `위협 모델링`

**한줄:** 개발 보안=SDLC 전 단계에 보안 활동을 심는 것(빨리 잡을수록 비용이 싸다) / 행안부 시큐어 코딩 7대 유형=입력데이터 검증 및 표현·보안기능·시간 및 상태·에러처리·코드오류·캡슐화·API 오용

**왜 개발 단계에서 잡는가**

**소프트웨어 개발 보안(시큐어 코딩)** — 설계·구현 단계에서 **보안 약점(Weakness)**을 미리 제거해 **취약점(Vulnerability)**이 되지 않도록 하는 활동.**[핵심 근거]** 같은 결함을 고치는 비용은 **요구분석 단계 1이라면 운영 단계에서는 수십~수백 배**가 된다. "개발이 끝난 뒤 방화벽으로 막는다"는 접근이 실패하는 이유.

- **약점(Weakness)** = 잠재적 결함 → 목록이 **CWE**
- **취약점(Vulnerability)** = 실제 공격 가능한 결함 → 개별 사례 번호가 **CVE**
- 점수 체계 **CVSS**(0~10점으로 심각도 표현)

**SDLC 단계별 보안 활동**

① 요구사항 분석보안 요구사항 도출, 관련 법·규제 식별
→
② 설계**위협 모델링(STRIDE)**, 보안 설계 검토. **여기서 잡는 게 가장 저렴**
→
③ 구현(개발)**시큐어 코딩** 적용, **정적 분석(SAST)**·소스 코드 진단
→
④ 시험(테스트)**동적 분석(DAST)**·모의 침투 테스트·퍼징
→
⑤ 운영·유지보수패치 관리, 취약점 점검, 로그 모니터링, 폐기 시 데이터 파기

- **STRIDE** — 위협 분류: **S**poofing(위장)·**T**ampering(변조)·**R**epudiation(부인)·**I**nformation Disclosure(정보 노출)·**D**oS·**E**levation of Privilege(권한 상승)
- 관련 방법론: **MS SDL**, **CLASP**, **Seven Touchpoints**

**시큐어 코딩 7대 보안약점 유형 (행안부 기준 — 목록 통째로 출제)**

- **① 입력 데이터 검증 및 표현**: **가장 항목이 많다**. SQL 삽입, 코드 삽입, **XSS**, 운영체제 명령어 삽입, 경로 조작, **위험한 형식 파일 업로드**, XQuery·LDAP 삽입, 정수형 오버플로, **포맷 스트링**, 메모리 버퍼 오버플로

- **② 보안 기능**: **부적절한 인가**, **하드코딩된 중요정보(비밀번호·암호키)**, **취약한 비밀번호 허용**, 중요정보 평문 저장·전송, 취약한 암호 알고리즘 사용, 부적절한 인증서 검증, 충분하지 않은 키 길이

- **③ 시간 및 상태**: **경쟁 조건(TOCTOU)**, 종료되지 않는 반복문·재귀

- **④ 에러 처리**: 오류 메시지로 **정보 노출**(경로·DB 구조), 오류 상황 대응 부재, 부적절한 예외 처리

- **⑤ 코드 오류**: **널 포인터 역참조**, 부적절한 자원 해제, 해제된 자원 사용(Use-After-Free), 초기화되지 않은 변수 사용

- **⑥ 캡슐화**: 잘못된 세션에 의한 정보 노출, **제거되지 않은 디버그 코드**, 시스템 데이터 정보 노출, public 메서드에서 private 배열 반환

- **⑦ API 오용**: **DNS lookup에 의존한 보안 결정**, 취약한 API 사용(위험한 함수 `strcpy`·`gets`), 널 매개변수 미검사

**[암기]** **입·보·시·에·코·캡·API** — "입보시에 코캡API". 문항에서 특정 약점이 **어느 유형인지** 묻는 형태가 대부분이다.

> **시험 한줄정리:** 결함은 **앞 단계에서 잡을수록 싸다**(설계 단계 **위협 모델링 STRIDE**) / 약점=**CWE**, 취약점=**CVE**, 심각도=**CVSS** / 7대 유형 **①입력데이터 검증 및 표현(SQL삽입·XSS·업로드·포맷스트링) ②보안기능(부적절한 인가·하드코딩된 중요정보·취약한 비밀번호) ③시간 및 상태(경쟁조건) ④에러처리 ⑤코드오류(널포인터) ⑥캡슐화(디버그 코드) ⑦API 오용**

_관련 개념: owasp · sqli · reversing_

## SQL 삽입 — 일반 · 블라인드 · 매스 — SQL Injection / Blind / Mass SQL Injection

`애플리케이션 보안`  `' OR '1'='1` `블라인드=참·거짓만 보고 유추` `매스=대량 자동 감염` `파라미터화 쿼리가 정답` `저장 프로시저·최소권한`

**한줄:** 입력값에 SQL 구문을 섞어 쿼리 의미를 바꾸는 공격 / 결과가 안 보이면 참·거짓 반응만으로 캐내는 블라인드, 다수 사이트 DB에 악성 스크립트를 자동 삽입하면 매스 SQL 인젝션 / 근본 대책은 파라미터화(Prepared Statement) 쿼리

**원리 — 데이터가 코드로 해석된다**

```
-- 원래 의도한 쿼리
SELECT * FROM users WHERE id='입력값' AND pw='입력값';

-- 아이디에  ' OR '1'='1' --  을 넣으면
SELECT * FROM users WHERE id='' OR '1'='1' --' AND pw='';
→ 조건이 항상 참이 되고 뒤는 주석 처리 → 인증 우회
```

**[본질]** 사용자가 넣은 **데이터**를 DB가 **명령(코드)**으로 읽어버리는 것. 모든 인젝션 계열(OS 명령·LDAP·XPath)의 원리가 같다.

**유형 (구분해서 출제)**

- **일반(Union·Error 기반)**: **UNION SELECT**로 다른 테이블을 붙여 조회하거나, 일부러 **에러를 내 그 메시지에서** 테이블·컬럼명을 얻는다

- **블라인드 SQL 인젝션 (Blind)**: 결과나 에러가 **화면에 안 보일 때**, 참/거짓에 따른 **응답 차이**만으로 한 글자씩 유추.
**Boolean 기반**=화면이 달라지는지 / **Time 기반**=`SLEEP(5)`을 넣어 **응답이 늦어지는지**로 판단. **느리지만 확실**

- **매스 SQL 인젝션 (Mass)**: **자동화 도구**로 수많은 사이트의 DB에 **악성 스크립트 태그를 대량 UPDATE**. 방문자가 **악성코드에 감염**되게 만드는 **2차 피해형**. 2008년 대규모 사고로 유명

- **Stored(2차) SQL 인젝션**: 일단 DB에 저장해 두었다가 **나중에 다른 기능이 그 값을 쓸 때** 실행되게 한다

**대응 방법 (우선순위대로)**

- **① 파라미터화 쿼리 / Prepared Statement(바인딩 변수)** — **가장 확실한 근본 대책**. 쿼리 구조를 먼저 확정하고 값만 나중에 끼우므로 값이 **코드로 해석될 수 없다**
- **② 입력값 검증** — 화이트리스트 방식(허용 문자만), 자료형·길이 확인. 특수문자 제거는 보조 수단
- **③ 저장 프로시저** 사용(단, 내부에서 동적 SQL을 조합하면 소용없다)
- **④ 최소 권한** — 웹 애플리케이션 계정에 DBA 권한을 주지 않는다(성공해도 피해 최소화)
- **⑤ 에러 메시지 은닉** — 상세 DB 오류를 사용자에게 노출하지 않음
- **⑥ 웹 방화벽(WAF)** — 패턴 차단. 우회가 가능하므로 **보조 수단**

> **시험 한줄정리:** SQL 삽입=**데이터가 코드로 해석**(`' OR '1'='1' --`) / **블라인드=결과가 안 보여 참·거짓(Boolean)이나 지연(Time, SLEEP)으로 한 글자씩**, **매스=자동화로 다수 DB에 악성 스크립트를 대량 삽입해 방문자 감염** / 대책 1순위는 **파라미터화(Prepared Statement) 쿼리**, 그다음 입력 검증·최소 권한·에러 은닉

_관련 개념: injection · sqlcmd · owasp_

## 코드 삽입 · OS 명령어 삽입 · 포맷 스트링 · XXE — Code / OS Command Injection, Format String, XXE

`애플리케이션 보안`  `세미콜론·파이프로 명령 이어붙이기` `eval·system 함수` `%n=메모리 쓰기` `외부 엔티티로 파일 읽기` `화이트리스트 검증`

**한줄:** 사용자 입력이 명령·코드·서식 문자열로 해석되면서 생기는 계열 / OS 명령어 삽입은 ;·|로 명령을 덧붙이고, 포맷 스트링은 %n으로 메모리를 쓰며, XXE는 XML 외부 엔티티로 서버 파일을 읽는다

**코드 삽입 (Code Injection)**

입력값이 **프로그램 소스 코드로 실행**되는 취약점. `eval()`·`exec()`·역직렬화처럼 **문자열을 코드로 바꾸는 기능**이 원인.
- 예: `eval($_GET['x'])` → `?x=system('id')`
- **안전하지 않은 역직렬화**도 같은 계열(OWASP A08)
- 대책: **eval류 사용 금지**, 입력을 코드로 만들지 않기, 화이트리스트 검증

**운영체제 명령어 삽입 (OS Command Injection)**

웹 애플리케이션이 사용자 입력을 **셸 명령에 그대로 붙여** 실행할 때 발생.

```
ping 기능:  system("ping " . $ip);

입력:  8.8.8.8 ; cat /etc/passwd
실행:  ping 8.8.8.8 ; cat /etc/passwd   ← 두 번째 명령까지 실행
```

- 이어붙이는 문자: **`;` `&&` `||` `|` ``명령`` `$(명령)`**
- 피해가 가장 큼 — **웹 권한으로 서버 명령 실행 → 웹셸 설치·서버 장악**
- 대책: **셸 호출 자체를 피하고** 언어 내장 함수 사용, 부득이하면 **화이트리스트**로 입력 제한, 웹 서버를 **비특권 계정**으로 실행

**포맷 스트링 (Format String)**

C의 `printf` 계열에 **서식 문자열을 사용자 입력으로** 넘길 때 발생.

```
취약:  printf(user_input);        ← 입력이 서식 문자열로 해석됨
안전:  printf("%s", user_input);  ← 항상 서식은 고정
```

- **`%x`·`%s`** — 스택 메모리를 **읽어** 정보 유출
- **`%n`** — 지금까지 출력한 바이트 수를 **메모리에 쓴다** → **임의 주소 변조 → 코드 실행**. 포맷 스트링이 위험한 진짜 이유
- 대책: **서식 문자열을 상수로 고정**, 컴파일러 경고(`-Wformat-security`) 확인

**XXE 인젝션 (XML External Entity)**

XML 파서가 **외부 엔티티 참조를 처리**하도록 켜져 있을 때, 공격자가 그 참조로 **서버 내부 파일**을 읽어낸다.

```
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<foo>&xxe;</foo>      ← 응답에 /etc/passwd 내용이 실림
```

- 피해: **내부 파일 유출 · SSRF(내부망 스캔) · DoS(빌리언 러프 공격)**
- 대책: **외부 엔티티·DTD 처리 비활성화**가 정답. 가능하면 XML 대신 **JSON** 사용

> **시험 한줄정리:** **코드 삽입=eval류로 소스가 실행** / **OS 명령어 삽입=`;`·`|`·`$()`로 명령을 덧붙여 서버 장악**, 대책은 셸 호출 회피+화이트리스트 / **포맷 스트링=`%x` 읽기·`%n` 쓰기**, 대책은 `printf("%s", 입력)` / **XXE=외부 엔티티로 내부 파일 유출·SSRF**, 대책은 **외부 엔티티·DTD 비활성화**

_관련 개념: sqli · xss · sdlc_

## XSS와 CSRF — Cross-Site Scripting / Cross-Site Request Forgery

`애플리케이션 보안`  `저장형·반사형·DOM 기반` `쿠키 탈취` `CSRF=의도치 않은 요청` `CSRF 토큰·SameSite` `출력 시 인코딩`

**한줄:** XSS=피해자 브라우저에서 공격자의 스크립트가 실행되어 쿠키·세션을 훔치는 공격(저장형·반사형·DOM 기반) / CSRF=로그인된 피해자가 자기도 모르게 요청을 보내게 만드는 공격 — XSS는 정보 탈취, CSRF는 행위 강제

**XSS 3가지 유형**

- **저장형 (Stored / Persistent)**: 게시판·댓글에 스크립트를 **저장**해 두면 **글을 보는 모든 사람**에게 실행된다. **피해 범위가 가장 큼**

- **반사형 (Reflected)**: URL 파라미터에 스크립트를 넣고, 서버가 그 값을 **그대로 응답에 되비추는** 것을 이용. 피해자가 **조작된 링크를 클릭**해야 성립 → 피싱 메일과 결합

- **DOM 기반 (DOM-based)**: 서버를 거치지 않고 **브라우저 안 자바스크립트**가 URL 값을 `innerHTML` 등에 넣으며 실행. **서버 로그에 안 남아** 탐지가 어렵다

- 피해: **쿠키·세션 탈취**, 피싱 페이지 삽입, 키로깅, 악성코드 유포, 웜 확산
- 대책: **출력 시 인코딩(이스케이프)**이 핵심 — `<`→`&lt;`. 입력 검증(화이트리스트), **쿠키에 HttpOnly**(자바스크립트 접근 차단), **CSP**(허용된 출처의 스크립트만 실행)

**CSRF (사이트 간 요청 위조)**

이미 **로그인된 피해자**의 브라우저가 **인증 쿠키를 자동으로 첨부**한다는 점을 악용. 공격자가 만든 페이지·이미지 태그가 **피해자 이름으로 요청**을 보낸다.

```
<img src="https://bank.com/transfer?to=attacker&amount=1000000">
→ 피해자가 그 글을 열기만 해도 송금 요청이 나간다
```

- 공격자는 **응답을 볼 수 없다** — 오직 **행위(상태 변경)**를 시킬 뿐
- 대책: **CSRF 토큰**(예측 불가한 값을 폼에 넣고 서버가 검증) · **SameSite 쿠키** · **Referer/Origin 검증** · 중요 작업에 **재인증·CAPTCHA** · **상태 변경은 반드시 POST**

**XSS vs CSRF (비교 문제 단골)**

- **XSS**: 피해자 브라우저에서 **스크립트를 실행** → **정보(쿠키·세션) 탈취**. 사이트가 **사용자를 신뢰**해서 생김. 응답을 **읽을 수 있다**

- **CSRF**: 피해자 **권한으로 요청을 전송** → **행위(송금·설정 변경) 강제**. 사이트가 **브라우저(쿠키)를 신뢰**해서 생김. 응답은 **못 읽는다**

**[한 줄]** **XSS=훔친다, CSRF=시킨다.** XSS가 있으면 CSRF 방어(토큰)도 무력화되므로 **XSS 대응이 먼저**다.

> **시험 한줄정리:** XSS=**저장형(모든 열람자·피해 최대)·반사형(링크 클릭 유도)·DOM 기반(서버 로그에 안 남음)**, 대책 **출력 인코딩 + HttpOnly + CSP** / CSRF=로그인 쿠키 자동 첨부를 악용해 **행위를 강제**, 대책 **CSRF 토큰·SameSite·Referer 검증** / **XSS=훔친다(정보) vs CSRF=시킨다(행위)**

_관련 개념: injection · upload · owasp_

## 위험한 형식 파일 업로드 · 경로 조작 — Unrestricted File Upload / Path Traversal

`애플리케이션 보안`  `웹셸` `확장자 화이트리스트` `실행 권한 제거` `웹 루트 밖에 저장` `../ 경로 조작`

**한줄:** 실행 가능한 파일(.php·.jsp)을 올려 웹셸을 심는 공격 / 대책은 확장자 화이트리스트·웹 루트 밖 저장·실행 권한 제거·파일명 난수화 / 다운로드 쪽 쌍둥이 취약점이 ../를 이용한 경로 조작

**위험한 형식 파일 업로드 → 웹셸**

게시판 첨부·프로필 사진 기능에 **서버에서 실행되는 스크립트**를 올리고, 그 URL로 접근해 실행시키는 공격.
- 결과물이 **웹셸(WebShell)** — 브라우저로 서버 명령을 실행하는 백도어. **서버 장악의 시작점**
- 우회 기법: `.php.jpg` 이중 확장자, 대소문자(`.PhP`), **널 바이트**(`shell.php%00.jpg`), Content-Type 위조, **이미지 파일 안에 코드 삽입**

**대응 (한 가지만 하면 뚫린다)**

- **확장자 화이트리스트** — 허용 목록 방식(블랙리스트는 우회됨). **서버 측에서** 검사(자바스크립트 검사만으로는 무의미)
- **웹 루트(Document Root) 밖에 저장** — URL로 직접 접근 자체를 불가능하게. 다운로드는 별도 스크립트로 중계
- **업로드 디렉터리에 실행 권한 제거** — 아파치 설정에서 스크립트 실행 차단
- **파일명 난수화·변경**, 크기 제한, MIME 타입과 **실제 시그니처(매직 넘버) 확인**, 백신 검사

**경로 조작 (Path Traversal / Directory Traversal)**

파일 다운로드·열람 기능의 파라미터에 **`../`**를 넣어 **의도한 디렉터리를 벗어나** 시스템 파일을 읽는 취약점.

```
정상:  /download?file=notice.pdf
공격:  /download?file=../../../../etc/passwd
```

- 우회: **URL 인코딩**(`%2e%2e%2f`), 이중 인코딩, 절대경로 사용
- 대책: **경로 문자(`../`·`/`) 제거·거부**, **파일명을 직접 받지 말고 ID로 매핑**, 기준 디렉터리 안인지 **정규화 후 검증**, chroot·권한 최소화

> **시험 한줄정리:** 파일 업로드=**웹셸을 심어 서버 장악**, 우회는 **이중 확장자·널 바이트·Content-Type 위조** / 대책 **확장자 화이트리스트(서버 측) + 웹 루트 밖 저장 + 실행 권한 제거 + 파일명 난수화** / **경로 조작=`../`로 상위 디렉터리 접근**, 대책은 **경로 문자 제거·ID 매핑·정규화 후 검증**

_관련 개념: xss · sdlc · websec_

## SSO (통합 인증) — Single Sign-On

`애플리케이션 보안`  `한 번 인증으로 여러 시스템` `인증 서버 + 에이전트` `델리게이션 vs 프로퍼게이션` `커버로스·SAML` `단일 실패 지점`

**한줄:** SSO=한 번의 인증으로 여러 시스템을 이용하는 통합 인증 / 구성은 인증 서버+각 시스템의 에이전트+토큰 / 방식은 기존 인증을 대신해 주는 델리게이션과 인증 토큰을 전파하는 프로퍼게이션

**정의 · 필요성**

**SSO(Single Sign-On)** — **한 번만 로그인**하면 연계된 여러 시스템을 **다시 인증하지 않고** 사용하는 통합 인증 체계.
- **장점**: 사용자 편의(패스워드 하나) · **패스워드 재사용·메모 감소** · 계정 관리 **중앙화** · 감사 추적 용이 · 헬프데스크 비용 절감

- **단점**: **단일 실패 지점(SPOF)** — 인증 서버가 죽으면 **전부 마비** / 계정 하나가 뚫리면 **전 시스템이 뚫린다** → **2차 인증(OTP) 병행이 필수**

**[구별]** **SSO=인증(누구인가)의 통합**, **EAM/IAM=인증+인가(권한)+계정관리까지** 포함하는 더 큰 개념.

**개념도 — 구성요소와 흐름**

- **사용자** · **인증 서버(Authentication Server)** — 신원 확인과 **토큰 발급**을 전담
- **SSO 에이전트(Agent)** — 각 업무 시스템에 설치되어 **토큰을 검증**하고 접근을 허용
- **LDAP·통합 계정 저장소** — 사용자 정보를 한곳에 보관
① 로그인사용자가 인증 서버에 한 번 인증
→
② 토큰 발급인증 서버가 **서명된 인증 토큰**을 발급
→
③ 시스템 접근다른 시스템에 갈 때 **토큰을 함께** 제시
→
④ 토큰 검증에이전트가 서명·유효기간을 확인하고 **재로그인 없이** 허용

**종류 (방식별 구분)**

- **델리게이션 (Delegation, 위임형)**: 대상 시스템의 **인증 방식을 바꿀 수 없을 때**, SSO 에이전트가 사용자의 **ID·패스워드를 대신 저장했다가 대신 입력**해 준다. **기존 시스템 수정이 불필요**하지만 계정 정보를 보관해야 함

- **프로퍼게이션 (Propagation, 전파형)**: 인증 서버가 발급한 **토큰을 각 시스템에 전달·검증**하는 방식. **패스워드를 저장하지 않아 더 안전**하나 각 시스템이 토큰을 이해하도록 **연동 개발**이 필요

- 구현 기술: **쿠키 기반**(같은 도메인) · **커버로스(Kerberos)**(티켓 기반, 윈도우 AD) · **SAML**(XML 기반, 도메인이 다른 웹 서비스 간 SSO 표준) · **OAuth 2.0(인가)·OpenID Connect(인증)**
- 범위로 볼 때 **같은 도메인 내부용**과 **서로 다른 기업 간(Federation, 페더레이션)**으로도 나눈다

> **시험 한줄정리:** SSO=한 번 인증으로 여러 시스템, 구성=**인증 서버+에이전트+토큰** / 단점 **단일 실패 지점·한 계정 뚫리면 전부** → OTP 병행 / **델리게이션=ID·PW를 대신 입력(기존 시스템 수정 불필요)** vs **프로퍼게이션=토큰 전파(더 안전, 연동 필요)** / 기술은 **커버로스·SAML·OIDC**

_관련 개념: drm · otp · oauth_

## DRM · 워터마킹 · 핑거프린팅 — Digital Rights Management / Watermarking / Fingerprinting

`애플리케이션 보안`  `콘텐츠 사용 통제` `패키저·클리어링하우스` `워터마킹=소유권 증명` `핑거프린팅=유출자 추적` `스테가노그래피`

**한줄:** DRM=콘텐츠를 암호화하고 사용 권한을 통제하는 체계 / 워터마킹은 저작권자 정보를 숨겨 소유권을 증명하고, 핑거프린팅은 구매자 정보를 각기 다르게 심어 유출자를 추적한다

**DRM 구성요소**

**DRM(Digital Rights Management)** — 디지털 콘텐츠를 **암호화**해 배포하고, **인가된 사용자가 허용된 범위 안에서만**(기간·횟수·인쇄 여부) 쓰게 하는 저작권 보호 기술.
- **패키저(Packager)** — 콘텐츠를 **암호화하고 사용 규칙(라이선스 정보)을 묶는다**
- **클리어링 하우스(Clearing House)** — **라이선스(키) 발급과 과금·정산**을 담당하는 중앙 기관
- **콘텐츠 서버(배포자)** · **DRM 컨트롤러(사용자 단말)** — 권한을 확인하고 **복호화·재생을 통제**
- 기업용 문서보안도 같은 구조(**문서 DRM**: 반출 문서의 열람·인쇄·화면 캡처 제한)

**워터마킹 vs 핑거프린팅 (구분이 핵심)**

- **디지털 워터마킹**: **저작권자(판매자) 정보**를 콘텐츠에 삽입. **모든 사본에 같은 정보**가 들어간다.
목적 = **"이건 내 것이다" 소유권 증명**

- **핑거프린팅 (Fingerprinting)**: **구매자(사용자) 정보**를 삽입. **사본마다 다른 정보**가 들어간다.
목적 = 유출본을 보고 **"누가 유출했는지" 추적**(불법 배포자 식별)

- 요구 성질: **비가시성**(눈에 안 띔) · **강인성(Robustness)**(압축·크기변경·잡음에도 살아남음) · **위조 방지**
- **가시적 워터마크**(눈에 보이는 로고)와 **비가시적 워터마크**로도 나눈다

**스테가노그래피와의 차이**

- **스테가노그래피 (Steganography)**: 이미지·음성 파일에 **비밀 메시지 자체를 숨겨** 전달. 목적은 **메시지의 존재를 감추는 것(은닉 통신)**. LSB(최하위 비트) 삽입이 대표 기법

- **워터마킹**: 숨기는 것은 **저작권 정보**이고, 존재를 감추는 것보다 **지워지지 않는 것(강인성)**이 더 중요

**[한 줄]** **스테가노그래피=존재를 숨긴다**, **워터마킹=지워지지 않게 새긴다**, **핑거프린팅=누가 샀는지 다르게 새긴다**.

> **시험 한줄정리:** DRM=콘텐츠 암호화+사용 권한 통제, 구성 **패키저(암호화·규칙) · 클리어링 하우스(라이선스 발급·과금) · DRM 컨트롤러** / **워터마킹=저작권자 정보, 모든 사본 동일, 소유권 증명** vs **핑거프린팅=구매자 정보, 사본마다 다름, 유출자 추적** / **스테가노그래피=메시지 존재 자체를 은닉**

_관련 개념: forensic · sso_

## 디지털 포렌식 — 원칙과 휘발성 데이터 — Digital Forensics

`애플리케이션 보안`  `5대 원칙` `연계보관성(Chain of Custody)` `휘발성 우선 수집` `무결성=해시` `쓰기 방지 장치`

**한줄:** 디지털 포렌식=법적 증거능력을 갖추도록 디지털 증거를 수집·분석하는 절차 / 원칙은 정당성·재현성·신속성·연계보관성·무결성 / 수집은 사라지기 쉬운 휘발성 데이터부터

**5대 원칙 (증거능력의 조건)**

- **정당성의 원칙** — **적법한 절차**로 수집해야 한다(위법수집증거 배제)
- **재현의 원칙** — 같은 조건에서 **같은 결과**가 나와야 한다
- **신속성의 원칙** — **지체 없이** 수집해야 한다(휘발성 증거는 사라진다)
- **연계보관성(Chain of Custody)** — 수집→이송→분석→법정까지 **담당자·시각·장소가 끊김 없이 기록**돼야 한다. 한 단계라도 비면 증거능력 상실
- **무결성의 원칙** — 수집 후 **변경되지 않았음**을 증명. 수단이 **해시값(MD5/SHA)**과 **쓰기 방지 장치(Write Blocker)**, 원본이 아닌 **사본(이미지) 분석**

**휘발성 vs 비휘발성 데이터 (수집 순서 문제)**

- **휘발성 데이터 (Volatile)**: **전원이 꺼지면 사라진다** → **먼저 수집**.
레지스터·캐시 → **메모리(RAM)** → **네트워크 연결 상태·라우팅 테이블·ARP 캐시** → **실행 중인 프로세스** → 임시 파일 · 로그인 세션

- **비휘발성 데이터 (Non-volatile)**: 전원과 무관하게 남는다 → **나중에 수집**.
**하드디스크·SSD 파일** · 로그 파일 · 레지스트리 · 슬랙 공간·삭제된 파일 · 백업 매체 · 출력물

**[원칙]** **휘발성이 큰 것부터(Order of Volatility)**. 특히 **메모리 덤프를 뜨기 전에 시스템을 재부팅·종료하면 안 된다**는 것이 함정 문항으로 자주 나온다.

**절차와 분석 대상**

① 수사 준비도구·인력 준비
→
② 증거 수집휘발성 우선, **쓰기 방지 후 이미징**, 해시 산출
→
③ 보관·이송봉인·연계보관성 문서 작성
→
④ 분석**사본**으로 타임라인·삭제 파일 복구·아티팩트 분석
→
⑤ 보고제3자가 **재현 가능하게** 문서화

- 주요 아티팩트: **레지스트리**·이벤트 로그·프리페치·**MFT($MFT)**·**웹 브라우저 기록·쿠키**·링크 파일·휴지통
- **안티 포렌식** — 데이터 완전 삭제(와이핑)·암호화·**타임스탬프 변조**·스테가노그래피로 분석을 방해하는 행위

> **시험 한줄정리:** 포렌식 5원칙 **정당성·재현성·신속성·연계보관성(Chain of Custody)·무결성** / 무결성 수단 = **해시값 + 쓰기 방지 장치 + 사본 분석** / 수집은 **휘발성 우선**: **레지스터·캐시 → 메모리 → 네트워크 상태 → 프로세스 → 디스크·로그**, **함부로 재부팅·종료 금지**

_관련 개념: reversing · drm · webartifact_

## 리버스 엔지니어링 — 정적 분석과 동적 분석 — Reverse Engineering / Static & Dynamic Analysis

`애플리케이션 보안`  `역공학` `정적=실행 안 함·디스어셈블` `동적=실행하며 관찰` `샌드박스·디버거` `난독화·안티디버깅`

**한줄:** 리버스 엔지니어링=완성된 프로그램을 거꾸로 분석해 구조·동작을 알아내는 것 / 정적 분석은 실행하지 않고 코드를 보는 방식, 동적 분석은 실제 실행시켜 행위를 관찰하는 방식 — 악성코드 분석은 둘을 함께 쓴다

**정의 · 용도**

**리버스 엔지니어링(역공학)** — 실행 파일·바이너리를 **거꾸로 해석**해 내부 구조·알고리즘·동작을 파악하는 기술.
- 정당한 용도: **악성코드 분석**, 취약점 발견, 호환성 확보, 소스가 없는 시스템 유지보수
- 악용: 라이선스 우회(크래킹), **알고리즘 탈취**, 패치 분석으로 **취약점 역추적(1-day 공격)**
- 관련: **디컴파일**(바이너리→고급 언어 근사), **디스어셈블**(바이너리→어셈블리)

**정적 분석 vs 동적 분석 (비교 출제)**

- **정적 분석 (Static)**: **실행하지 않고** 코드·바이너리를 본다.
기법: 문자열 추출, **해시·시그니처** 확인, PE 헤더·API 목록 분석, **디스어셈블**
도구: **IDA Pro**·Ghidra·strings·PEiD, 소스 진단 **SAST**
장점 **안전(감염 위험 없음)·전체 경로 확인 가능** / 단점 **패킹·난독화에 무력**, 오탐이 많음

- **동적 분석 (Dynamic)**: **실제로 실행**하며 행위를 관찰한다.
기법: 프로세스·레지스트리·파일 변화, **네트워크 통신 감시**, **디버깅**
도구: **OllyDbg·x64dbg**·Process Monitor·Wireshark·**샌드박스(Cuckoo)**, 웹 **DAST**
장점 **실제 행위를 확인, 난독화·패킹을 우회** / 단점 **감염 위험(격리 필요)**, 실행된 경로만 보임

**[실무]** 정적으로 **얼개를 파악**하고, 동적으로 **실제 행위를 확인**하는 **병행**이 표준. 개발 보안에서는 **SAST(구현 단계)** → **DAST(시험 단계)** 순으로 매핑된다.

**분석 방해 기법 (악성코드 쪽 대응)**

- **패킹(Packing)** — 실행 파일을 압축·암호화해 **정적 분석을 막는다**. 대응은 **언패킹**
- **난독화(Obfuscation)** — 코드·문자열을 알아보기 어렵게 변형
- **안티 디버깅** — 디버거가 붙었는지 탐지해 **동작을 바꾸거나 종료**
- **가상머신·샌드박스 탐지** — 분석 환경이면 **악성 행위를 하지 않는다**(분석 회피)
- 정상 소프트웨어에서도 **지식재산 보호** 목적으로 난독화·안티디버깅을 쓴다

> **시험 한줄정리:** 리버스 엔지니어링=바이너리를 거꾸로 분석(디스어셈블·디컴파일) / **정적=실행 안 하고 코드·문자열·PE 분석(IDA, 안전하나 패킹·난독화에 취약)** vs **동적=실행하며 행위·통신 관찰(OllyDbg·샌드박스, 정확하나 감염 위험)** — **병행이 표준** / 개발 보안 대응은 **SAST(구현)·DAST(시험)**, 방해 기법은 **패킹·난독화·안티디버깅·샌드박스 탐지**

_관련 개념: forensic · sdlc · diffing_
