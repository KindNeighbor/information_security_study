## 전자화폐 — 정의 · 요구조건 · 종류 — Electronic Cash / Electronic Money

`애플리케이션 보안`  `불추적성(익명성)` `이중사용 방지` `양도성·분할성·독립성` `IC 카드형=몬덱스·비자캐시` `네트워크형`

**한줄:** 전자화폐=현금의 성질을 전자적으로 옮긴 지불수단 / 요구조건은 불추적성(익명성)·이중사용 방지·양도성·분할성·독립성 / IC 카드형(몬덱스·비자캐시) vs 네트워크형(사이버캐시·이캐시)

**정의**

**전자화폐(Electronic Cash)** — 은행이 발행한 **현금의 가치를 전자적 정보로 바꿔** IC 카드나 컴퓨터에 저장했다가 지불에 쓰는 수단. 신용카드(**후불·기명**)와 달리 **선불·익명**이 원칙이라 "디지털 현금"이라 부른다.**[핵심 난제]** 현금은 물건이라 한 번 주면 내 손을 떠나지만, 전자화폐는 **데이터라서 복사가 된다**. 그래서 **이중사용(Double Spending) 방지**가 설계의 중심에 온다.

**요구조건 (가장 많이 나오는 목록)**

- **불추적성(익명성, Untraceability)** — 누가 어디에 썼는지 **추적할 수 없어야** 한다. 현금의 가장 큰 특성 → 구현 기법이 **은닉서명(Blind Signature)**
- **이중사용 방지(Double Spending 방지)** — 같은 화폐를 **두 번 쓸 수 없어야** 한다
- **양도성(Transferability)** — 사람에서 사람으로 **그대로 넘길 수 있어야** 한다
- **분할성(Divisibility)** — 1만원을 **쪼개서** 3천원만 지불할 수 있어야 한다
- **독립성(휴대성, Independence)** — 물리적 매체·장소에 **얽매이지 않고** 저장·이동 가능해야 한다
- **위조 불가능성(Unforgeability)** — 복제·변조가 불가능해야 한다
**[은닉서명]** 메시지 내용을 **가린 채로** 서명받는 기법. 은행은 액면만 보증하고 **누구의 화폐인지는 모르게** 되어 익명성이 성립한다.

**저장 매체에 따른 분류**

- **IC 카드형 (전자지갑형)**: **스마트카드 안의 칩**에 가치를 저장. 오프라인 소액 결제에 강함.
예) **몬덱스(Mondex)** — 영국, **사람 간 직접 양도(양도성) 가능**이 특징 / **비자캐시(VisaCash)** — 비자, 양도는 안 되고 가맹점에 지불만 / 국내 **K-CASH**

- **네트워크형 (소프트웨어형)**: PC·서버의 **소프트웨어**에 저장하고 통신망으로 주고받음. 온라인 결제용.
예) **e-Cash**(디지캐시, 은닉서명 사용) · **사이버캐시(CyberCash)** · **퍼스트버추얼**

**[구분 요령]** **몬덱스=양도 가능**, **비자캐시=양도 불가**로 짝지어 나온다. 이캐시는 **은닉서명·익명성**과 함께 묶인다.

> **시험 한줄정리:** 전자화폐=선불·익명의 디지털 현금 / 요구조건 **불추적성(은닉서명)·이중사용 방지·양도성·분할성·독립성·위조 불가** / **IC 카드형=몬덱스(양도 O)·비자캐시(양도 X)·K-CASH**, **네트워크형=e-Cash·사이버캐시**

_관련 개념: set · ssl_

## SET · 이중서명 — Secure Electronic Transaction / Dual Signature

`애플리케이션 보안`  `신용카드 지불 표준` `이중서명` `상점은 카드번호를 못 봄` `전자봉투` `구현 복잡해 사장`

**한줄:** SET=비자·마스터카드가 만든 신용카드 지불 프로토콜 / 핵심은 이중서명 — 주문정보는 상점만, 지불정보는 PG만 보게 나누면서도 둘이 한 거래임을 증명한다

**정의 · 참여자**

**SET(Secure Electronic Transaction)** — 1996년 **비자·마스터카드**가 공동 개발한 **인터넷 신용카드 결제 보안 프로토콜**. 참여자 전원이 **인증서(X.509)**를 갖는 것이 특징.
- **고객(Cardholder)** — 전자지갑(Electronic Wallet) 소프트웨어 사용
- **상점(Merchant)** — 물건을 파는 쪽
- **지불 게이트웨이(PG, Payment Gateway)** — 인터넷과 기존 금융망을 잇는 중계
- **발급기관(Issuer) · 매입기관(Acquirer) · 인증기관(CA)**

**이중서명(Dual Signature) — 왜 쓰는가 (최다 출제)**

문제 상황: 고객은 **상점에게 카드번호를 보여주기 싫고**, **은행(PG)에게는 무엇을 샀는지 알리기 싫다**. 그런데 두 정보가 **같은 하나의 거래**라는 건 증명돼야 한다.

- **주문정보 OI (Order Information)**: **상점만** 본다. PG는 못 본다

- **지불정보 PI (Payment Information)**: 카드번호 등. **PG만** 본다. **상점은 못 본다**

```
이중서명 만드는 순서
1) H(OI) = 주문정보 해시,  H(PI) = 지불정보 해시
2) 두 해시를 이어붙여 다시 해시 → H( H(PI) || H(OI) )
3) 그 값을 고객의 개인키로 서명 = 이중서명(Dual Signature)
```

- 상점은 **OI 원문 + H(PI)**만 받는다 → 카드번호는 **해시라서 볼 수 없지만** 서명 검증은 된다
- PG는 **PI 원문 + H(OI)**만 받는다 → 무엇을 샀는지는 모른다
- 양쪽 모두 **같은 이중서명 값을 검증**할 수 있어 **두 정보가 한 거래임**이 증명된다
**[한 줄 이유]** **기밀성(서로 필요 없는 정보는 감춤)과 연결성(한 거래임을 입증)을 동시에** 달성하려고 쓴다.

**거래 절차 · 사용 기술**

① 구매 요청고객이 상점에 주문. 인증서를 교환해 서로 확인
→
② 이중서명 전송고객이 OI+H(PI)는 상점에게, PI+H(OI)는 (상점을 거쳐) PG에게
→
③ 지불 승인 요청상점이 PG에 승인 요청 → PG가 금융망으로 카드사 확인
→
④ 승인 응답 · 상품 인도승인이 오면 상점이 상품·서비스를 제공
→
⑤ 대금 청구(Capture)상점이 나중에 대금 지급을 요청

- **전자봉투(Digital Envelope)** — 데이터는 **대칭키**로 암호화하고, 그 **대칭키를 수신자 공개키**로 암호화해 함께 보냄. SET·PGP 공통 방식
- 기밀성=DES, 무결성·인증=RSA 전자서명, 신원=X.509 인증서

**SET의 한계 (SSL과 비교해서 출제)**

- **SET**: **보안은 강하다**(상점이 카드번호를 못 봄, 부인방지 가능). 그러나 **참여자 전원이 인증서를 갖고 전자지갑을 깔아야** 하고 **처리가 느리고 복잡** → **사실상 사장**

- **SSL**: 브라우저에 기본 내장이라 **추가 설치 없이 간편**. 단 **상점이 카드번호를 그대로 보게 되고**, 부인방지가 없다 → **실제로는 SSL이 승리**

> **시험 한줄정리:** SET=비자·마스터의 신용카드 결제 프로토콜, 전원이 **인증서** 보유 / **이중서명 = 서명[ H( H(PI) || H(OI) ) ]** — **상점은 카드번호(PI)를, PG는 주문내역(OI)을 못 보면서** 같은 거래임을 증명 / **전자봉투**(대칭키 암호화 + 대칭키를 공개키로 암호화) / 안전하나 **복잡해서 SSL에 밀려 사장**

_관련 개념: ssl · ecash · sslimpl_

## SSL/TLS — 보안 서비스 · 구성요소 · 핸드셰이크 — Secure Sockets Layer / Transport Layer Security

`애플리케이션 보안`  `전송-응용 계층 사이` `기밀성·무결성·인증` `Handshake·Record·CCS·Alert` `Pre-Master Secret` `443/HTTPS`

**한줄:** SSL/TLS=전송계층과 응용계층 사이에서 동작하는 보안 프로토콜 / 서비스=기밀성·무결성·서버(선택적 클라이언트) 인증 / 상위 4개 프로토콜 중 핵심은 Handshake(키 합의)와 Record(실제 암호화)

**정의 · 위치**

**SSL(Secure Sockets Layer)** — 넷스케이프가 만든 보안 프로토콜. 표준화되며 이름이 **TLS(Transport Layer Security)**로 바뀌었다. **SSL 3.0 → TLS 1.0 → 1.2 → 1.3**. 현재 **SSL 전 버전과 TLS 1.0/1.1은 취약해 사용 금지**, **TLS 1.2 이상**을 쓴다.
- 위치: **전송 계층(TCP) 위, 응용 계층(HTTP) 아래**. 그래서 HTTP·FTP·SMTP 등 **여러 응용을 그대로 감쌀 수 있다**
- **HTTPS = HTTP over SSL/TLS**, 포트 **443**

**제공하는 보안 서비스 (하나가 빠져 있음에 주의)**

- **기밀성(Confidentiality)** — 대칭키 암호(AES 등)로 데이터 암호화
- **무결성(Integrity)** — **MAC(HMAC)**으로 변조 탐지
- **인증(Authentication)** — **서버 인증은 필수**, **클라이언트 인증은 선택**(X.509 인증서)
**[함정]** SSL은 **부인방지(Non-repudiation)를 제공하지 않는다**. 부인방지는 SET·전자서명의 몫. "SSL이 제공하지 않는 것은?" → **부인방지**가 정답.

**구성요소 — 상위 4개 + Record**

- **Handshake Protocol**: 가장 복잡하고 중요. **버전·암호 방식(Cipher Suite) 합의, 인증서 교환·검증, 세션 키 생성**을 담당

- **Change Cipher Spec Protocol**: **1바이트**짜리 가장 단순한 프로토콜. "**지금부터 합의한 암호를 적용한다**"는 전환 신호

- **Alert Protocol**: 오류·경고 전달(**warning / fatal**). fatal이면 즉시 연결 종료

- **Handshake 계층의 응용 데이터**: 실제 HTTP 데이터가 위에서 내려온다

- **Record Protocol (하위)**: 위 모든 것을 받아 **단편화 → 압축 → MAC 부착 → 암호화 → 헤더 추가** 순으로 처리해 TCP로 내려보낸다. **실제 기밀성·무결성을 실행하는 층**

**Handshake 세부 과정 (순서 문제 단골)**

① ClientHello클라이언트 → 서버. **SSL 버전, 클라이언트 난수, 세션 ID, 지원하는 Cipher Suite 목록** 제시
↓
② ServerHello서버가 목록 중 **사용할 버전·암호 방식을 선택**하고 **서버 난수**를 보냄
↓
③ Certificate (+ ServerKeyExchange, CertificateRequest)서버가 **X.509 인증서(공개키)** 전달. 필요하면 클라이언트 인증서를 요구
↓
④ ServerHelloDone서버 쪽 인사 끝 신호
↓
⑤ ClientKeyExchange클라이언트가 인증서를 검증한 뒤 **Pre-Master Secret을 만들어 서버 공개키로 암호화**해 전송. **여기서 키가 넘어간다**
↓
⑥ ChangeCipherSpec → Finished (클라이언트)"이제 암호 적용" 후 지금까지 주고받은 메시지의 해시를 담은 Finished 전송
↓
⑦ ChangeCipherSpec → Finished (서버)서버도 같은 전환·확인 → **이후 응용 데이터는 암호화되어 오간다**

**[키 유도]** **Pre-Master Secret + 클라이언트 난수 + 서버 난수 → Master Secret → 세션 키(암호화 키·MAC 키·IV)**. 난수를 섞는 이유는 **재전송 공격 방지**다.

> **시험 한줄정리:** SSL/TLS=**TCP 위·응용 아래**, HTTPS **443** / 제공: **기밀성·무결성(MAC)·서버 인증(클라이언트는 선택)**, **부인방지는 제공 안 함** / 구성: **Handshake(합의·인증·키) · ChangeCipherSpec(1바이트 전환) · Alert(warning·fatal) · Record(단편화→압축→MAC→암호화)** / 순서 **ClientHello→ServerHello→Certificate→ServerHelloDone→ClientKeyExchange(Pre-Master)→CCS·Finished**

_관련 개념: sslimpl · set · httpheader_

## OpenSSL · S-HTTP — OpenSSL / Secure HTTP

`애플리케이션 보안`  `OpenSSL=오픈소스 구현체` `하트블리드` `S-HTTP=메시지 단위` `SSL=연결 단위` `S-HTTP는 HTTP 전용`

**한줄:** OpenSSL=SSL/TLS를 구현한 대표 오픈소스 라이브러리(하트블리드 취약점의 무대) / S-HTTP=HTTP 메시지 하나하나를 암호화하는 별개 방식으로, 연결 전체를 감싸는 SSL에 밀려 사라졌다

**OpenSSL**

**OpenSSL** — SSL/TLS 프로토콜과 각종 암호 알고리즘을 구현한 **오픈소스 라이브러리·명령행 도구**. 아파치·nginx 등 대부분의 서버가 이것을 쓴다.

```
# 개인키 생성
openssl genrsa -out server.key 2048

# 인증서 서명 요청(CSR) 생성
openssl req -new -key server.key -out server.csr

# 자체 서명 인증서 생성
openssl x509 -req -days 365 -in server.csr -signkey server.key -out server.crt

# 서버의 인증서·프로토콜 확인
openssl s_client -connect www.example.com:443
```

**하트블리드 (Heartbleed, CVE-2014-0160)**

OpenSSL의 **하트비트(Heartbeat) 확장**에서, 보낸 데이터의 **실제 길이를 검증하지 않아** 발생한 **버퍼 오버리드(경계 검사 미비)** 취약점.
- 공격자가 "1바이트 보내며 길이는 64KB"라고 속이면 서버가 **인접 메모리 64KB를 그대로 응답**
- 유출 대상: **개인키·세션 쿠키·패스워드** — 암호화가 뚫린 게 아니라 **구현 버그**였다는 점이 포인트
- 대응: OpenSSL 패치, **인증서·개인키 재발급**, 세션·패스워드 초기화
**[같이 나오는 것]** **POODLE**(SSL 3.0 패딩 공격 → SSL 3.0 폐기), **BEAST·CRIME**, **FREAK/Logjam**(약한 수출용 암호 강제). 대응은 공통적으로 **취약 버전·취약 Cipher Suite 비활성화**.

**S-HTTP vs SSL (비교로만 출제)**

**S-HTTP(Secure HTTP)** — HTTP **메시지 자체**를 암호화·서명해 주고받도록 만든 프로토콜.
- **S-HTTP**: 보호 단위 = **HTTP 메시지 하나하나**. **HTTP 전용**(다른 프로토콜엔 못 씀). 응용 계층에서 동작. **전자서명으로 부인방지 가능**. 널리 안 쓰여 **사장**

- **SSL/TLS**: 보호 단위 = **연결(세션) 전체**. HTTP·FTP·SMTP 등 **어떤 응용이든** 감쌀 수 있음. 전송~응용 사이에서 동작. **현재 표준**

**[암기]** **S-HTTP=메시지 단위·HTTP 전용**, **SSL=연결 단위·범용**. URL도 `shttp://` vs `https://`로 달랐다.

> **시험 한줄정리:** **OpenSSL**=SSL/TLS 오픈소스 구현체(`genrsa`·`req`·`x509`·`s_client`), **하트블리드=하트비트 길이 미검증으로 메모리 64KB 유출 → 개인키 재발급** / **S-HTTP=메시지 단위·HTTP 전용·사장** vs **SSL=연결 단위·범용·표준**

_관련 개념: ssl · set · websec_

## OTP — 정의와 동기화 방식 — One Time Password

`애플리케이션 보안`  `일회용 비밀번호` `시간 동기화` `이벤트(계수) 동기화` `질의응답(비동기)` `S/KEY`

**한줄:** OTP=한 번 쓰고 버리는 비밀번호로 재사용·스니핑 공격을 무력화 / 동기식은 시간 동기화·이벤트(계수) 동기화, 비동기식은 질의응답(Challenge-Response) 방식

**정의 · 필요성**

**OTP(One Time Password)** — **매번 다른 값**이 생성되어 한 번만 유효한 비밀번호.
- 고정 패스워드는 **스니핑·재전송(Replay)·키로깅**으로 훔치면 계속 쓸 수 있다
- OTP는 훔쳐도 **이미 만료**라 재사용이 불가능 → **재전송 공격 대응**
- **2단계 인증(2FA)**의 대표 수단: 지식(패스워드) + **소유(OTP 토큰)**

**동기식 — 시간 동기화 vs 이벤트(계수) 동기화**

- **시간 동기화 방식 (Time Synchronous, TOTP)**: **현재 시각 + 비밀키**로 값 생성. **보통 60초(30초)마다 자동 변경**.
장점: 사용이 간편(버튼만 보면 됨)
단점: **시간이 어긋나면 인증 실패**(시각 동기화 필요), 유효시간 안에는 재사용 위험

- **이벤트(계수) 동기화 방식 (Event/Counter, HOTP)**: **사용 횟수(카운터) + 비밀키**로 값 생성. **버튼을 누를 때마다** 다음 값.
장점: 시간 동기화가 필요 없음
단점: 사용자가 버튼을 헛눌러 **카운터가 어긋나면(비동기화) 재동기화 필요**

**비동기식 — 질의응답 방식**

**질의응답(Challenge-Response) 방식** — 서버가 **매번 다른 난수(Challenge)**를 보내면, 사용자가 그 값을 토큰에 **입력**해 나온 결과(Response)를 답한다.
- 장점: 시간·카운터 동기화가 필요 없고 **보안이 가장 강함**
- 단점: 사용자가 **질의 값을 직접 입력**해야 해 **번거롭다**
- **S/KEY** — 해시를 **여러 번 연쇄 적용**해 만든 패스워드 목록을 **역순으로** 하나씩 쓰는 초기 OTP 방식(사전 등록형)
**[형태]** 하드웨어 토큰·카드형 · **휴대폰 앱(소프트 OTP)** · SMS. 단 **SMS는 심 스와핑·중간 탈취에 취약**해 권장도가 낮다.

> **시험 한줄정리:** OTP=일회용 비밀번호로 **재전송·스니핑 무력화**, 소유 기반 2차 인증 / **동기식 = 시간 동기화(TOTP, 60초마다) · 이벤트(계수) 동기화(HOTP, 버튼 누를 때)** / **비동기식 = 질의응답(Challenge-Response), 가장 안전하지만 불편** / **S/KEY=해시 연쇄를 역순 사용**

_관련 개념: ssl · set_

## 전자문서 · EDI · ebXML — Electronic Document / EDI / ebXML

`애플리케이션 보안`  `전자문서 요건` `공인전자문서센터` `EDI=정형 전자문서 교환` `ebXML 4대 구성요소` `CPP/CPA`

**한줄:** 전자문서=전자적 형태로 작성·송수신·저장된 문서로 법적 효력을 인정받는다 / EDI는 정형 서식의 기업 간 문서 교환, ebXML은 이를 XML 기반으로 표준화한 전자상거래 프레임워크

**전자문서 — 정의와 요건**

**전자문서** — 정보처리시스템에 의해 **전자적 형태로 작성·변환되거나 송수신·저장된 정보**. 「전자문서 및 전자거래 기본법」에 따라 **전자적 형태라는 이유만으로 효력을 부인당하지 않는다**.
- **내용 열람 가능** · **형태 그대로 재현 가능**하면 서면으로 인정
- **작성자·수신자·송수신 시기**가 확인돼야 한다
- **공인전자문서센터(공인전자문서중계자)** — 전자문서를 안전하게 보관·유통해 주는 제3의 신뢰기관
- 보안 요소: **전자서명(위·변조 방지, 부인방지)** + **타임스탬프(작성 시점 증명)**

**EDI (전자문서교환)**

**EDI(Electronic Data Interchange)** — 주문서·송장 같은 **정형화된 서식**을 기업 간에 **표준 전자 형식**으로 자동 교환하는 방식.
- 사람이 다시 입력할 필요가 없어 오류·시간을 줄인다
- 표준: **UN/EDIFACT**(국제), ANSI X.12(미국)
- 한계: **전용망(VAN)** 기반이라 비용이 크고 **중소기업이 참여하기 어렵다** → 그 대안이 **ebXML**

**ebXML — 4대 구성요소 (출제 포인트)**

**ebXML(electronic business XML)** — **UN/CEFACT와 OASIS**가 만든, **XML 기반의 개방형 전자상거래 표준 프레임워크**. 인터넷 위에서 누구나 참여 가능하게 하는 것이 목표.
- **① 비즈니스 프로세스 (BP)**: 거래 절차·주고받는 문서의 **순서를 정의**

- **② 핵심 컴포넌트 (Core Components)**: 거래에 쓰이는 **데이터 항목을 재사용 가능한 단위**로 표준화

- **③ 등록저장소 (Registry / Repository)**: 위 정의와 **기업 프로파일을 등록·검색**하는 곳. 상대를 찾는 **노란 전화번호부** 역할

- **④ 거래 당사자 (CPP / CPA)**: **CPP(Collaboration Protocol Profile)**=우리 회사가 **할 수 있는** 거래 능력 명세
**CPA(Collaboration Protocol Agreement)**=두 회사의 CPP를 맞춰 만든 **합의서(계약)**

- **+ 전송·교환·패키징 (ebMS)**: 실제 메시지를 **SOAP 기반**으로 안전하게 전달

**[CPP vs CPA]** **P=Profile=혼자서 낸 이력서**, **A=Agreement=둘이 맺은 계약서**로 구분한다.

> **시험 한줄정리:** 전자문서=전자적 형태여도 **효력 인정**(열람·재현 가능, 작성자·시기 확인), 보관은 **공인전자문서센터**, 보호는 **전자서명+타임스탬프** / **EDI=정형 서식 교환(EDIFACT), 전용망이라 비쌈** / **ebXML=XML 기반 개방형**, 4요소 **비즈니스 프로세스·핵심 컴포넌트·등록저장소·CPP(프로파일)/CPA(합의서)**

_관련 개념: websvc · set_

## 웹 서비스(SOAP·WSDL·UDDI)와 XML 보안 — Web Services / XML Security

`애플리케이션 보안`  `SOAP=메시지` `WSDL=설명서` `UDDI=등록소` `XML 서명·XML 암호화` `XKMS·SAML·XACML`

**한줄:** 웹 서비스 3요소=SOAP(주고받는 메시지)·WSDL(서비스 사용설명서)·UDDI(찾는 등록소) / XML 보안은 XML 서명·XML 암호화가 기본이고, 키는 XKMS·인증정보는 SAML·접근권한은 XACML이 맡는다

**XML이란**

**XML(eXtensible Markup Language)** — 데이터의 **구조와 의미를 태그로 표현**하는 확장 가능한 마크업 언어. HTML이 "보여주기"용이라면 XML은 **"데이터를 주고받기"**용이며, 태그를 **사용자가 직접 정의**한다.
- 플랫폼·언어에 **독립적**이라 이기종 시스템 간 데이터 교환 표준으로 쓰인다(ebXML·SOAP의 토대)
- 구조 정의: **DTD** 또는 **XML Schema(XSD)**
- 취약점: **XXE(XML External Entity)** — 외부 엔티티 참조를 악용해 **서버 내부 파일 유출·SSRF**. 대응은 **외부 엔티티 처리 비활성화**

**웹 서비스 3요소 (역할 짝짓기로 출제)**

- **SOAP (Simple Object Access Protocol)**: **주고받는 메시지의 형식**. XML로 된 봉투(Envelope=Header+Body)를 **HTTP 등에 실어** 전송. **"어떻게 말할까"**

- **WSDL (Web Services Description Language)**: 서비스가 **어떤 기능·매개변수·주소를 갖는지** XML로 기술한 **사용설명서**. **"무엇을 어떻게 부를까"**

- **UDDI (Universal Description, Discovery and Integration)**: 서비스를 **등록하고 검색**하는 **전화번호부(등록소)**. **"어디에 있을까"**

① 등록제공자가 UDDI에 서비스와 WSDL 위치를 등록
→
② 검색이용자가 UDDI에서 찾아 WSDL을 받음
→
③ 호출WSDL대로 SOAP 메시지를 만들어 서비스를 호출

**XML 보안 기술 (역할 구분이 핵심)**

- **XML 서명(XML Signature)** — XML 문서 **전체 또는 일부(요소 단위)**에 전자서명. **무결성·인증·부인방지**
- **XML 암호화(XML Encryption)** — 문서 **일부 요소만 골라** 암호화 가능. **기밀성**
- **XKMS(XML Key Management Specification)** — **공개키의 등록·검증·폐기**를 웹 서비스로 처리(PKI를 쉽게 쓰게 해 주는 **키 관리**)
- **SAML(Security Assertion Markup Language)** — **인증·인가 정보를 주고받는** 표준. **SSO(Single Sign-On)의 핵심**. "이 사람은 로그인된 사람이다"라는 **보증서(Assertion)**를 전달
- **XACML(eXtensible Access Control Markup Language)** — **접근통제 정책**을 기술하는 언어. "누가 무엇에 접근 가능한가"의 **규칙**
**[3형제 구분]** **XKMS=키**, **SAML=인증정보(누구인가·SSO)**, **XACML=권한 정책(무엇을 할 수 있나)**. 바꿔 내는 문제가 많다.

> **시험 한줄정리:** XML=태그를 직접 정의하는 데이터 교환 표준(취약점 **XXE**) / 웹 서비스 **SOAP=메시지(봉투) · WSDL=설명서 · UDDI=등록·검색 전화번호부** / XML 보안 **XML 서명(무결성·부인방지) · XML 암호화(기밀성, 일부 요소만 가능) · XKMS(키 관리) · SAML(인증정보·SSO) · XACML(접근통제 정책)**

_관련 개념: edoc · ssl · oauth_
