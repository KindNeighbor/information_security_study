# 접근 통제 (PART 04) — 식별·인증·인가·MAC/DAC/RBAC·모델·SecureOS·대칭키·공개키

> 자동 생성 — 원본은 `cards/access.js`. 직접 수정 금지.

## 접근 통제 개요 — 식별 · 인증 · 인가 — Access Control / Identification, Authentication, Authorization

`정보보안 일반`  `주체·객체·접근` `식별→인증→인가→책임추적` `최소 권한` `직무 분리` `알 필요성`

**한줄:** 접근 통제=주체가 객체에 접근하는 것을 정책에 따라 허용·거부하는 것 / 단계는 식별(주장)→인증(증명)→인가(권한 부여)→책임추적성(기록) / 원칙은 최소 권한·직무 분리·알 필요성

**기본 용어 — 주체 · 객체 · 접근**

- **주체(Subject)** — 접근을 **요구하는 능동적 존재**. 사용자·프로세스·프로그램
- **객체(Object)** — 접근 **대상이 되는 수동적 자원**. 파일·DB·프린터·메모리
- **접근(Access)** — 주체가 객체에 하는 행위. **읽기(R)·쓰기(W)·실행(X)·삭제·생성**
- **접근 통제(Access Control)** — 인가되지 않은 주체의 접근을 막고, 인가된 주체에게도 **허용된 범위만** 열어 주는 것. **기밀성·무결성·가용성을 모두 떠받치는 기본 수단**

**정보 접근의 단계 (순서 문제 단골)**

① 식별 (Identification)"나는 홍길동이다"라고 **주장**. 사용자 ID·계정. **고유해야 하며 공유하면 안 된다**
→
② 인증 (Authentication)그 주장이 맞음을 **증명**. 패스워드·OTP·생체. **식별과 인증은 다른 단계**
→
③ 인가 (Authorization)인증된 주체에게 **어디까지 할 수 있는지** 권한을 부여. "권한 확인"이 여기
→
④ 책임추적성 (Accountability)한 행위를 **로그로 남겨 주체까지 되짚는다**. 감사(Audit)

**[구분 요령]** **식별=누구라고 말하기(ID) · 인증=그게 맞음을 증명(PW) · 인가=무엇을 할 수 있는지(권한)**. 셋을 바꿔 내는 문항이 매우 흔하다.

**접근 통제의 3대 원칙**

- **최소 권한(Least Privilege)** — 업무 수행에 **꼭 필요한 최소한**의 권한만. 반대 개념이 **최대 권한(편의 위주)**
- **직무 분리(Separation of Duties)** — **한 사람이 처음부터 끝까지** 처리하지 못하게 나눔(요청자와 승인자 분리, 개발자와 운영자 분리). **내부자 부정·공모 없이는 사고가 어렵게** 만든다
- **알 필요성(Need to Know)** — 등급이 충분해도 **업무상 알 필요가 없으면 접근 불가**. 기밀성과 직결
- 보조 원칙: **직무 순환(Job Rotation)**·**강제 휴가** — 부정을 드러나게 하는 관리적 통제

**참조 모니터 (Reference Monitor)**

주체가 객체에 접근할 때마다 **반드시 거쳐야 하는 검사 지점**이라는 **추상 개념**. 이를 구현한 소프트웨어가 **보안 커널(Security Kernel)**이다.
- **완전성(Completeness)** — **우회가 불가능**해야 한다(모든 접근이 반드시 통과)
- **격리성(Isolation)** — 변조로부터 **보호**되어야 한다
- **검증가능성(Verifiability)** — **충분히 작아서** 분석·검증이 가능해야 한다
**[연결]** 윈도우의 구현체가 **SRM(Security Reference Monitor)** — 상세 내용은 **PART 01 「보안 참조 모니터(SRM)」 카드**에 있다.

> **시험 한줄정리:** 주체(능동)→객체(수동) / **식별(ID 주장) → 인증(증명) → 인가(권한 부여) → 책임추적성(로그)** / 원칙 **최소 권한 · 직무 분리 · 알 필요성** / 참조 모니터의 3요건 = **완전성(우회 불가)·격리성(변조 불가)·검증가능성(작아서 검증 가능)**, 구현체가 **보안 커널**

_관련 개념: macdac · accessmatrix · srm_

## 접근 통제 기술 — MAC · DAC · RBAC — Mandatory / Discretionary / Role-Based Access Control

`정보보안 일반`  `MAC=관리자·보안등급 강제` `DAC=소유자 재량` `RBAC=역할 기반` `규칙 기반 vs 신분 기반` `RBAC은 Non-DAC`

**한줄:** MAC은 관리자가 정한 보안등급으로 시스템이 강제하고, DAC은 소유자가 재량으로 권한을 주며, RBAC은 역할에 권한을 묶어 사람에게 역할을 부여한다

**세 방식 한눈에 비교 (최다 출제)**

- **MAC — 강제적 접근통제 (Mandatory)**: 권한 결정 주체 = **시스템(관리자 정책)**. **객체의 보안 등급(Label)**과 **주체의 취급 인가(Clearance)**를 비교해 **자동 결정**. **소유자도 바꿀 수 없다**
= **규칙 기반(Rule-based)** / 군·정부 등 **기밀성이 최우선**인 환경. 대표 구현 **SELinux**

- **DAC — 임의적 접근통제 (Discretionary)**: 권한 결정 주체 = **객체의 소유자**. 소유자가 **자기 재량으로** 남에게 권한을 준다
= **신분 기반(Identity-based)** / 리눅스 **rwx 퍼미션**, SQL의 **GRANT**, 윈도우 **DACL**이 전부 DAC

- **RBAC — 역할 기반 접근통제 (Role-Based)**: 권한 결정 주체 = **조직의 역할·직무**. 권한을 **역할**에 주고 사람에게 **역할을 부여**
= **비임의적(Non-DAC)** / **인사이동·퇴사에 강해 기업에서 가장 현실적**

**MAC의 주요 특징과 종류**

- 모든 객체에 **보안 레이블(등급 + 카테고리)**을 붙인다. 예: **1급비밀 > 2급비밀 > 3급비밀 > 대외비 > 일반**
- 주체의 **인가 등급이 객체 등급 이상**이고 **알 필요성(카테고리)까지 맞아야** 접근 허용
- **장점** — 중앙에서 일관되게 통제, **보안성이 가장 강함**, 사용자 실수로 정보가 새지 않음
- **단점** — **구현·운영이 복잡하고 비용이 크며 유연성이 떨어진다**(성능 저하)
- 종류: **다중 수준 보안(MLS)**·**다중 등급 보안** 기반의 **규칙 기반 접근통제**, 등급 격자를 쓰는 **격자(Lattice) 기반 모델**

**DAC의 종류 · RBAC의 구조**

- **DAC의 종류**: **신분 기반**: **개별 사용자 단위**(User-directed) / **그룹 단위**
**혼합 방식**: 사용자+그룹을 함께 지정
단점 = **권한이 전파되어 통제가 어렵다**(받은 사람이 또 줄 수 있음), **트로이 목마에 취약** — 사용자가 실행한 악성 프로그램이 **그 사용자의 권한을 그대로** 쓰기 때문

- **RBAC의 구조**: **사용자 – 역할 – 권한** 3단 구조. 여기에 **세션**이 붙는다
제약: **역할 계층(상위 역할이 하위 권한 상속)**, **직무 분리(상충되는 두 역할 동시 보유 금지)**, **기수 제약(한 역할의 인원 수 제한)**
장점 = **관리 부담이 크게 줄고 최소 권한·직무 분리를 자연스럽게 구현**

**[암기]** **MAC=규칙(등급)·시스템 강제**, **DAC=신분·소유자 재량**, **RBAC=역할·조직 구조**. "누가 권한을 정하는가"만 물으면 다 풀린다.

> **시험 한줄정리:** **MAC=관리자가 정한 보안등급으로 시스템이 강제(규칙 기반, 보안 최강·복잡, SELinux)** / **DAC=소유자 재량(신분 기반, rwx·GRANT·DACL, 권한 전파와 트로이 목마에 취약)** / **RBAC=역할에 권한을 묶는 Non-DAC(역할 계층·직무 분리·기수 제약, 기업에 가장 현실적)**

_관련 개념: accessctl · accessmatrix · accessmodel_

## 접근 통제 매트릭스 — ACL과 자격 목록 — Access Control Matrix / ACL / Capability List

`정보보안 일반`  `행=주체·열=객체` `ACL=객체(열) 기준` `CL=주체(행) 기준` `희소 행렬이라 비효율` `능력(Capability)=티켓`

**한줄:** 접근 통제 매트릭스는 행에 주체·열에 객체를 놓고 권한을 적은 표 / 이 표를 열(객체) 기준으로 쪼개면 ACL, 행(주체) 기준으로 쪼개면 자격 목록(Capability List)

**접근 통제 매트릭스**

**접근 통제 행렬(Access Control Matrix)** — **행(가로)에 주체**, **열(세로)에 객체**를 놓고 칸마다 **허용된 접근 권한**을 적은 표. 접근 통제를 표현하는 **가장 기본적인 개념 모델**.

```
파일A      파일B      프린터
홍길동      R, W       R          -
김철수      R          R, W, X    W
관리자      R, W, X    R, W, X    W
```

**[한계]** 주체와 객체가 늘면 **표가 폭발적으로 커지고 대부분의 칸이 비어(희소 행렬)** 그대로 저장하기엔 비효율적이다. 그래서 **행 단위·열 단위로 쪼개서** 구현한다.

**ACL vs 자격 목록 (쪼개는 방향이 핵심)**

- **ACL (Access Control List) — 열(객체) 기준**: **객체마다** "누가 나에게 무엇을 할 수 있는지" 목록을 붙인다.
예: 파일A → {홍길동: RW, 김철수: R}
장점 **"이 파일에 누가 접근 가능한가"를 바로 알 수 있다**
단점 **"이 사용자가 접근 가능한 자원 전체"를 알려면 모든 객체를 뒤져야** 한다
구현: **리눅스 퍼미션·윈도우 DACL·방화벽 룰**

- **자격(능력) 목록 — Capability List, 행(주체) 기준**: **주체마다** "내가 무엇에 무엇을 할 수 있는지" 목록(**티켓**)을 들려 준다.
예: 홍길동 → {파일A: RW, 파일B: R}
장점 **주체별 권한 파악·이양이 쉽다**, 분산 환경에 적합
단점 **객체 기준으로 누가 접근하는지 파악이 어렵고, 티켓 위조·회수(폐기)가 까다롭다**
구현: **커버로스 티켓**, 케이퍼빌리티 기반 OS

**[한 줄]** **ACL=문에 붙인 출입 명단(객체 중심)**, **Capability=손에 쥔 출입증(주체 중심)**.

> **시험 한줄정리:** 접근 통제 행렬 = **행(주체) × 열(객체)**, 희소해서 쪼개 구현 / **ACL=열(객체) 기준 — 문에 붙인 명단**(리눅스 퍼미션·DACL·방화벽 룰), "이 자원에 누가?"에 강함 / **Capability List=행(주체) 기준 — 손에 쥔 출입증**(커버로스 티켓), "이 사람이 무엇을?"에 강하지만 **회수·위조 관리가 어렵다**

_관련 개념: macdac · accessctl · kerberos_

## 접근 통제 모델 — BLP · Biba · 클락-윌슨 · 만리장성 — Bell-LaPadula / Biba / Clark-Wilson / Chinese Wall

`정보보안 일반`  `BLP=기밀성` `No Read Up·No Write Down` `Biba=무결성` `No Read Down·No Write Up` `만리장성=이해충돌 방지`

**한줄:** BLP는 기밀성 모델로 위를 못 읽고 아래로 못 쓰며(NRU·NWD), Biba는 무결성 모델로 아래를 못 읽고 위로 못 쓴다(NRD·NWU) / 클락-윌슨은 상용 무결성, 만리장성은 이해충돌 방지 모델

**벨-라파듈라 모델 (BLP) — 기밀성**

미 국방부용으로 만들어진 **최초의 수학적 보안 모델**. 목표는 오직 **기밀성**(정보가 아래로 새지 않게).
- **단순 보안 규칙(ss-property) = No Read Up** — 자기 등급보다 **높은 등급을 읽을 수 없다**
- **성형 규칙(*-property) = No Write Down** — 자기 등급보다 **낮은 등급에 쓸 수 없다**(높은 등급자가 기밀을 아래로 흘리는 것을 막음)
- **강제 접근통제(MAC)**의 이론적 토대
- 한계: **무결성을 전혀 보장하지 못한다** — 낮은 등급자가 **높은 등급 문서에 쓰는 것(Write Up)은 허용**되어 오염될 수 있다(Blind Write 문제)

**비바 모델 (Biba) — 무결성**

BLP를 **거꾸로 뒤집은** 모델. 목표는 **무결성**(더러운 정보가 위로 올라오지 않게).
- **단순 무결성 규칙 = No Read Down** — 자기보다 **낮은 무결성 등급을 읽을 수 없다**(신뢰도 낮은 정보에 오염되지 않게)
- **성형 무결성 규칙 = No Write Up** — 자기보다 **높은 무결성 등급에 쓸 수 없다**
- 기밀성은 고려하지 않는다

- **BLP (기밀성)**: **NRU + NWD** — "위를 못 읽고, 아래로 못 쓴다"

- **Biba (무결성)**: **NRD + NWU** — "아래를 못 읽고, 위로 못 쓴다"

**[암기]** **기밀성은 새 나가는 게 문제라 "아래로 쓰기" 금지**, **무결성은 오염이 문제라 "위로 쓰기" 금지**. 이 한 줄만 잡으면 네 규칙이 다 따라온다.

**클락-윌슨 · 만리장성 모델**

- **클락-윌슨 (Clark-Wilson) — 상업용 무결성**: 금융·회계 등 **상업 환경의 무결성**에 초점. 사용자가 데이터를 **직접 건드리지 못하게** 하고 **검증된 프로그램(Well-formed Transaction)**을 통해서만 변경하게 한다. **직무 분리**를 모델에 명시적으로 포함

- **만리장성 (Chinese Wall / Brewer-Nash)**: **이해 충돌(Conflict of Interest) 방지** 모델. 컨설팅·법률 회사에서 **A사 자료를 본 사람은 경쟁사인 B사 자료를 볼 수 없게** 벽을 세운다. **이전에 접근한 이력에 따라 권한이 동적으로 바뀌는** 것이 특징

- **기타**: **접근 통제 행렬 모델**(HRU) · **격자(Lattice) 모델**(등급 격자로 상·하한 결정) · **정보 흐름 모델**

> **시험 한줄정리:** **BLP=기밀성: No Read Up + No Write Down**(무결성 미보장) / **Biba=무결성: No Read Down + No Write Up** / **클락-윌슨=상업용 무결성, 검증된 프로그램으로만 변경 + 직무 분리** / **만리장성(Brewer-Nash)=이해충돌 방지, 접근 이력에 따라 권한이 동적으로 변함**

_관련 개념: macdac · secureos · accessctl_

## Secure OS와 Secure DBMS — Secure OS / Trusted Computing Base

`정보보안 일반`  `보안 커널·TCB` `참조 모니터 구현` `커널 레벨 강제 통제` `TCSEC 등급` `다중 등급 DBMS`

**한줄:** Secure OS=기존 OS 커널에 보안 커널(참조 모니터)을 심어 강제 접근통제를 적용한 운영체제 / TCB는 보안을 책임지는 신뢰 구성요소 전체 / Secure DBMS는 여기에 다중 등급·추론 방지를 더한 DBMS

**Secure OS (보안 운영체제)**

기존 OS의 **커널 수준에 보안 기능을 내장**해, 응용 프로그램이나 root조차 **정책을 우회할 수 없게** 만든 운영체제.
- 핵심 구성 = **참조 모니터 개념 + 이를 구현한 보안 커널**
- **TCB(Trusted Computing Base, 신뢰 컴퓨팅 기반)** — 시스템의 보안을 책임지는 **하드웨어·펌웨어·소프트웨어의 총합**. **작을수록 검증이 쉬워 안전**하다
- 주요 기능: **강제적 접근통제(MAC)** · 사용자 식별·인증 · **해킹 방어(루트 권한 제한)** · **감사 기록** · 객체 재사용 방지 · 침입 탐지
- 대표: **SELinux**, AppArmor, Trusted Solaris
**[가치]** 애플리케이션이 뚫려도 **커널이 정책으로 막아 피해 확산을 차단**한다. 방화벽·백신이 못 하는 "마지막 방어선" 역할.

**평가 기준 (TCSEC · CC)**

- **TCSEC(오렌지북)** — 미국의 옛 기준. **D(최소) → C(임의적 보호, C1·C2) → B(강제적 보호, B1·B2·B3) → A(검증된 보호)**. **B등급부터 MAC 적용**이 포인트
- **ITSEC** — 유럽 기준. 기능과 **보증(Assurance)**을 분리해 평가
- **CC(Common Criteria, ISO/IEC 15408)** — **현재의 국제 공통 평가 기준**. 보증 등급 **EAL1~EAL7**(숫자가 클수록 엄격). 용어 **PP(보호 프로파일)**·**ST(보안 목표명세서)**·**TOE(평가 대상)**

**Secure DBMS (보안 DBMS)**

일반 DBMS의 접근통제(DAC)에 더해 **등급 기반 강제 통제**를 적용한 DBMS.
- **다중 등급 보안(MLS)** — 테이블·행·**컬럼(셀) 단위**까지 보안 등급을 매겨 통제
- **다중 인스턴스화(Polyinstantiation)** — 같은 키에 등급별로 다른 행을 두어 **추론·존재 노출 차단**
- **추론·집성 방지**, **감사 기록 보호**, 저장 데이터 암호화
- 상세 기법은 **PART 03 「데이터베이스 보안 기법」 카드**와 이어진다

> **시험 한줄정리:** Secure OS=**커널에 보안 커널(참조 모니터)을 심어 root도 못 뚫는 MAC 적용**, **TCB는 작을수록 안전**, 대표 **SELinux** / 평가 **TCSEC(D→C→B→A, B등급부터 MAC) · CC(EAL1~7, PP·ST·TOE)** / Secure DBMS=**다중 등급 보안 + 다중 인스턴스화로 추론 차단**

_관련 개념: accessmodel · dbsecway · macdac_

## 대칭키 암호 — 정의와 종류 — Symmetric Key Cryptography

`정보보안 일반`  `암호화·복호화 키가 같음` `빠르다·키 분배가 문제` `블록 vs 스트림` `DES·AES·SEED·ARIA` `n(n-1)/2개의 키`

**한줄:** 대칭키=암호화와 복호화에 같은 키를 쓰는 방식 / 빠르고 대용량에 적합하지만 키 분배와 키 개수(n(n-1)/2)가 근본 문제 / 블록 암호(DES·AES·SEED·ARIA)와 스트림 암호(RC4)로 나뉜다

**정의 · 장단점**

**대칭키(비밀키·관용) 암호** — **암호화 키와 복호화 키가 같다**. 송·수신자가 **미리 같은 키를 공유**해야 한다.
- **장점**: **속도가 매우 빠르다**(공개키보다 수백~수천 배) → **대용량 데이터 암호화에 적합**, 키 길이가 짧아도 안전

- **단점**: **키 분배(교환) 문제** — 키를 안전하게 전달할 방법이 없다
**키 관리 문제** — n명이 서로 통신하려면 **n(n-1)/2개**의 키가 필요(100명이면 4,950개)
**부인방지 불가** — 둘 다 같은 키를 가져 제3자에게 증명이 안 된다

**[계산]** 키 개수 문제는 계산으로 출제된다. **대칭키 = n(n−1)/2**, **공개키 = 2n**(각자 한 쌍씩).

**블록 암호 vs 스트림 암호**

- **블록 암호 (Block Cipher)**: 평문을 **일정 길이 블록(64·128비트)으로 잘라** 암호화. **혼돈(Confusion)과 확산(Diffusion)**을 반복.
운용 모드 **ECB·CBC·CFB·OFB·CTR**(ECB는 같은 평문이 같은 암호문이 되어 **사용 금지**)

- **스트림 암호 (Stream Cipher)**: 키 스트림을 만들어 평문과 **비트 단위 XOR**. **매우 빠르고 하드웨어 구현이 간단**해 **실시간·무선 통신**에 적합.
예: **RC4**(취약해 폐기), A5(GSM), LFSR 기반. 이론적 완전 비밀은 **일회용 패드(OTP)**

**주요 대칭키 알고리즘 (숫자로 외운다)**

- **DES** — 블록 **64비트**, 키 **56비트**(패리티 포함 64), **Feistel 구조 16라운드**. **키가 짧아 전수조사로 깨짐**
- **3DES** — DES를 **3번** 적용(EDE). 안전하지만 **느리다**
- **AES** — **DES를 대체한 현재 표준**. 원래 이름 **Rijndael**, 블록 **128비트**, 키 **128·192·256비트**, **SPN 구조**(Feistel 아님)
- **SEED** — **한국(KISA)** 개발, 블록 128비트, 키 128/256비트
- **ARIA** — **한국 국가 표준**, 블록 128비트, 키 128/192/256, **ISPN 구조**. 이름은 학·연·관(Academy·Research Institute·Agency)에서 유래
- **HIGHT** — 한국, **경량**(RFID·센서용), 블록 64비트
- 기타: **IDEA**(PGP에 사용) · **Blowfish·Twofish** · **RC5** · **LEA**(한국 경량 고속)
**[구조 구분]** **Feistel 구조 = DES·3DES·SEED**(암·복호화 구조가 같음), **SPN 구조 = AES·ARIA**. 이 짝을 바꿔 내는 문항이 흔하다.

> **시험 한줄정리:** 대칭키=**같은 키**, **빠르지만 키 분배·키 개수 n(n−1)/2·부인방지 불가** / **블록(ECB·CBC·CTR)** vs **스트림(XOR, RC4)** / **DES=블록64·키56·Feistel16 → AES=Rijndael·블록128·키128/192/256·SPN** / 한국 **SEED(Feistel)·ARIA(ISPN)·HIGHT·LEA**

_관련 개념: pubkey · accessctl_

## 공개키 암호 — 키 분배 원리와 종류 — Public Key (Asymmetric) Cryptography

`정보보안 일반`  `공개키로 암호화·개인키로 복호화` `키 분배 문제 해결` `RSA=소인수분해` `ECC=타원곡선·짧은 키` `디피-헬만=키 교환`

**한줄:** 공개키 암호=키를 공개키·개인키 한 쌍으로 나눠 공개키로 암호화하고 개인키로 복호화 / 대칭키의 키 분배 문제를 풀었고 전자서명이 가능해졌지만 속도가 느려 실제로는 하이브리드로 쓴다

**원리 — 왜 키 분배 문제가 풀리는가**

**공개키(비대칭) 암호** — 수학적으로 연결된 **공개키(누구나 알아도 됨)**와 **개인키(절대 비공개)** 한 쌍을 쓴다. **한쪽으로 잠그면 다른 쪽으로만 열린다.**
- **기밀성 — 수신자의 공개키로 암호화**: 누구나 **수신자의 공개키**로 암호화할 수 있지만, **수신자의 개인키를 가진 본인만** 열 수 있다 → **키를 미리 나눠 가질 필요가 없다**

- **인증·부인방지 — 송신자의 개인키로 서명**: **송신자의 개인키**로 서명하면 **송신자의 공개키**로 누구나 검증 가능 → **전자서명**이 성립(대칭키로는 불가능했던 것)

**[함정]** **"무엇으로 암호화하나"가 목적에 따라 다르다.** 기밀성=**수신자 공개키**, 서명=**송신자 개인키**. 이걸 바꿔 내는 문항이 가장 많다.

**주요 알고리즘 (근거가 되는 수학 문제로 구분)**

- **RSA** — **소인수분해의 어려움**에 기반. **암호화와 전자서명 모두 가능**한 가장 대표적인 알고리즘. 키 길이 **2048비트 이상** 권장
- **디피-헬만(Diffie-Hellman)** — **이산대수 문제** 기반. **암호화가 아니라 "키 교환(공유)" 전용**. 공개된 채널에서 서로 비밀 키를 만들어 낸다. **인증 기능이 없어 중간자 공격에 취약** → 서명과 함께 써야 함
- **ElGamal** — 이산대수 기반. **암호화와 서명 모두** 가능
- **DSA** — 이산대수 기반. **전자서명 전용**(암호화 불가)
- **ECC(타원곡선)** — **타원곡선 이산대수** 기반. **훨씬 짧은 키로 같은 안전성**(ECC 256비트 ≈ RSA 3072비트) → **모바일·IoT에 유리**
- **Rabin**(소인수분해) · **배낭(Knapsack)**(부분합 문제, 깨짐)

**대칭키 vs 공개키 비교 (표로 통째 출제)**

- **대칭키**: 키: **암·복호화 동일** / 속도 **매우 빠름** / 키 개수 **n(n−1)/2** / **키 분배가 어렵다** / **부인방지 불가** / 용도: **대용량 데이터 암호화**

- **공개키**: 키: **공개키·개인키 쌍** / 속도 **느림**(수백~수천 배) / 키 개수 **2n** / **키 분배 문제 해결** / **부인방지 가능(전자서명)** / 용도: **키 교환·전자서명·인증**

**[실제 사용 — 하이브리드]** 둘 중 하나만 쓰지 않는다. **데이터는 빠른 대칭키로 암호화하고, 그 대칭키만 공개키로 암호화해** 함께 보낸다. 이것이 **전자봉투**이며 **SSL/TLS·PGP·SET**가 모두 이 방식이다.

> **시험 한줄정리:** 공개키=**기밀성은 수신자 공개키로 암호화, 서명은 송신자 개인키로** / **RSA=소인수분해(암호화+서명)**, **디피-헬만=이산대수·키 교환 전용(중간자 취약)**, **DSA=서명 전용**, **ECC=짧은 키로 같은 안전성(모바일)** / 대칭키는 **빠름·n(n−1)/2·부인방지 불가**, 공개키는 **느림·2n·부인방지 가능** → 실제로는 **하이브리드(전자봉투)**

_관련 개념: symkey · ssl · set_
